# H18.27 native generated images

Generated: 2026-10-09 UTC. Base/head at design: `da7c8a222c2cd0cb658b192c967194bc9c88efa3`. Branch: `codex/mobile-generated-images-20261009`.

Goal: expose the existing local, approval-gated image proposal and resulting PNG on native Media, with honest status and an explicit saved copy. Keep the exact submitted prompt and latest task ID across the Approvals tab handoff under the existing opaque chat scope.

Non-goals: cloud generation, reachability claims from configuration, automatic proposal/retry, backend changes, image editing/upscaling/model selection, gallery, native approval decision, or an implicit copy to device photos. This slice does not make a failed execution distinguishable from backend `uncertain` when the task projection cannot do so.

Paths: new `mobile/src/api/generatedImages.ts` and `mobile/src/api/__tests__/generatedImages.test.ts` for transport/validation; new `mobile/src/storage/generatedImageTask.ts` and its tests for scoped task metadata; new `mobile/src/screens/GeneratedImages.tsx` and `frontend/native-tests/generated-images.test.tsx` for the user flow; minimal `mobile/src/screens/MediaScreen.tsx` and `mobile/App.tsx` insertion; native file/image test mocks. `mobile/src/api/client.ts` stays untouched. Root owns parity/status/ledger updates.

Contract: `GET /api/media` reports `local_image.configured`, `local`, `approval_required`, and `reachable:null`. A submit sends exactly `{kind:'image',prompt:<unchanged text>,cloud:false}` to `POST /api/media/generate` only after user action; only HTTP 202 plus `approval_required` and a positive bounded task ID is accepted as queued. `GET /api/media/generation-tasks/{id}` requires the admin token and projects `awaiting_approval | queued | generating | ready | rejected | deferred | refused | uncertain` with a strict artifact only for ready. `GET /api/media/generated/{32 lowercase hex}` uses user auth and returns PNG up to 16 MiB. Both configured user and admin headers are sent where required; credentials never enter metadata or files.

Transport: finite deadlines guard fetch and response consumption with `Promise.race` and abort; an already-aborted signal dispatches nothing. There is no automatic retry. Before POST, storage must confirm a scoped unknown-delivery marker; if that write fails, no proposal is sent. While POST is pending, Start new is disabled. Timeout, network loss, 5xx, or malformed success after dispatch leave that marker and direct the user to check Approvals before a deliberate new submit; a valid 202 replaces it with the task ID. JSON text is capped at 64 Ki UTF-16 code units (not a UTF-8 byte cap) after native `Response.text()` buffers it; a supplied Content-Length above the cap is rejected earlier. PNG requires exact image/png media type, a matching Content-Length and Blob length no larger than 16 MiB, plus PNG signature and encoded length. Native Blob/FileReader buffer the response, so the header guard limits expected size but cannot prevent a dishonest or headerless transport from buffering before rejection. Write a transient preview in app cache only after explicit Preview, then copy to app-private documents only on explicit Save. This is not a system Photos/Downloads export. Preview files are cleaned on scope/task/artifact change, write/decode failure, and unmount; saved copies are retained as the user's explicit choice.

State: task metadata is keyed by the opaque `chatScope`, validated on restore, and contains only a positive task ID plus exact prompt or an unknown-delivery marker plus exact prompt. Maximum prompt length is 4,000 UTF-16 code units; serialized metadata can expand to 25,000 code units through JSON escapes. A keyed child renders no previous-scope prompt, task, or preview during a hub change. Scope/unmount/new-task generation fences cancel network work and suppress stale state and file writes; task read ordering and artifact identity prevent old status or pixels from replacing newer ones. Approvals unmounts Media, so return rehydrates the task or delivery-unknown marker. Task polling is manual Refresh, and configuration has an explicit Refresh after an off/error result. The exact stored prompt remains visible even if configuration later turns off. Task states `rejected`, `deferred`, `refused`, and `uncertain` have separate labels. Status and task-read errors use a generic retry message; submit errors retain the unknown-delivery marker, while PNG download errors have a separate preview message.

Tests: red-first API request/body/header/deadline/envelope/PNG checks; scoped metadata and escaped exact prompt; native mounted flow including off/configured states, explicit submit, Approvals return during an unresolved POST, changed hub with pending download, changed ready artifact, preview decode failure, save, and cleanup. Run focused native Jest/Vitest and native TypeScript check; root handles broader suites and review.

Rollback: revert this mobile-only unit. Existing backend artifacts and approval tasks remain on the hub, saved native copies remain explicit user files, and scoped task metadata can be removed without affecting credentials or hub state.

Dependencies: existing Expo FileSystem legacy, AsyncStorage, ServerContext chat scope, local image endpoints and Approvals tab. No new provider, credential, or npm package.

D1Information architecture RESOLVED · prototyped

~30 capability areas, 228 endpoints, 16 agents. How does every surface get a calm, reachable home without becoming a wall of tabs?

◆
Left rail of modes + ⌘K universal jumpRECOMMENDED
Cockpit · Agents · Trust · Memory · Autonomy · Build · Observe · Interop · Admin. Eight-or-so modes always visible; the command palette jumps anywhere. Scales to 30 surfaces because each mode owns its own sub-navigation.
○
Top tab-bar of modes
Same model, horizontal. Cleaner on wide displays but runs out of room past ~8 items and reads less like a cockpit. Built as a live alternative in the prototype's Tweaks → Navigation.
○
Single dense dashboard, everything via ⌘K + overlays
Most "Bloomberg", least discoverable. Power-user ceiling is high but the learning curve is steep and ambient glanceability suffers.
In protoBoth rail and tabs ship as a toggle so you can feel the difference. Rail is the default. ⌘K palette is live (try ⌘K → "Go to").
D2Build stack APPROVED · Vite + React + TS

The prototype is React-via-Babel in the browser (zero build step) — perfect for design iteration, not for a 24/7 production surface. What does the real thing run on?

◆
Vite + React + TypeScript, bundledRECOMMENDED
Keeps the component model the prototype already uses, adds type-safety for the 228-endpoint API surface, tree-shakes, and self-hosts fonts/assets. Lowest-friction graduation path from the current code.
○
Keep vanilla + Web Components
Matches the existing v0.3 shell, no framework lock-in, but state orchestration across 30 surfaces gets hand-rolled and brittle.
○
Full framework (Next/SvelteKit)
Overkill for a single-user, mostly-client, always-on app with a local backend. Adds SSR complexity you don't need.
DriverThe component boundaries in the prototype (shell / modes / primitives / data) map 1:1 onto a Vite project — the handoff doc lays out that migration.
D3HUD / Admin unification APPROVED · unify

Today the HUD and the Admin/Settings surface are effectively two apps with two visual languages. Do they become one?

◆
Unify — Admin becomes a mode in the same shellRECOMMENDED
One design system, one nav, one mental model. Admin sits in the rail like any other mode (it's already stubbed there). Reduces context-switching for a single owner who runs the whole machine.
○
Keep separate, share tokens only
Less migration now; Admin keeps its current structure but adopts the v2 palette/type. Faster, but the seam stays visible.
NoteThe brief leans unify. The v2 token system (CSS variables for look/accent/density) is built to absorb Admin with zero new colors.
D4v1 scope RESOLVED · prototyped

Which of the ~30 surfaces actually ship in v1? Everything-at-once dilutes the craft; too little doesn't prove the thesis.

◆
Cockpit + Agents + Trust + MemoryRECOMMENDED
The four that carry the north star: the daily driver (Cockpit), the cast (Agents), the safety story (Trust), and the thing that makes it feel alive over time (Memory). All four are built at fidelity in the prototype.
○
+ Autonomy & Observe in v1
Tempting, but the decision-inbox and eval surfaces need their own deep passes. Stubbed in the rail as "soon" — fast-follow for v1.1.
○
Cockpit-only
Ships fastest but undersells the platform — Trust and Memory are what differentiate this from a chat window.
In protoAll four modes are live and signature interactions are nailed: cognition trace, network brain + focus, Merkle audit chain, % local meter, bitemporal KG slider.

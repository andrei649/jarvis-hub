## Confirmed findings

1. **H040 persistent configuration is lost on normal application restart (high confidence).** `E2ESync.__init__` initializes peers/policies/label empty and calls `_load_state()` only if an explicit `state_path` was passed (lines 265–278). Production orchestration constructs `E2ESync` with no arguments (`orchestrator.py:869`), while `_save_state` does save to the default resolved `e2e_sync_state.json`. Thus added peers and disabled-skill policies are saved but never restored by ordinary startup; later saves can replace the old state. Tests inject explicit state paths and miss the production constructor. [Constructor](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/e2e_sync.py#L265), [production registration](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/orchestrator.py#L869).

2. **H040 skill sync is disconnected from real skill discovery (high confidence).** Default collector/installer uses `data_path("synced_skills")` (`e2e_sync.py:301–302`), and production injects no alternate directory. The actual skill loader discovers bundled `SKILLS_DIR` and `user_skills_dir()` (`skills/loader.py:399–407`), and generated/imported skills go to that user root (`:193–200`). Consequently existing user skills are not collected by normal sync, and successfully downloaded skills are stored outside the discovery roots and do not appear as usable skills. H040 tests construct separate custom `skills_dir` trees and assert file existence; they never load the result through the real skill loader. [Sync directory](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/e2e_sync.py#L301), [loader roots](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/skills/loader.py#L399), [test setup](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/tests/test_h040_device_sync.py#L44).

3. **H040 stale peer snapshots overwrite newer local changes (high confidence at published lot4).** `pull_state` gathers all mailbox/transport manifests and deduplicates only inside that single invocation (`:707–726`); it maintains no applied revision or timestamp cursor. `apply_synced_artefacts` blindly applies settings imports (`:613–623`) and writes SKILL.md (`:646–648`). Sequence: B pulls A; B edits a setting/skill; B pulls the unchanged A mailbox again; A's old value overwrites B's edit. With multiple peers, fetch/list order decides the winner. `sync_now` pulls first and then pushes, amplifying the stale state. This is a material data-loss/conflict gap for bidirectional device sync. Parent reports a proposed LWW fix only on published but unintegrated WIP branch `lot5-bench` commit `bd93bff5caf993bd150828a87d3cd1b4bfd88fa5`; that does not repair the reviewed published head and was not independently inspected here. [Pull path](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/e2e_sync.py#L702), [unconditional apply](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/e2e_sync.py#L613).

## H657 scope qualification

Room failover is a manually orchestrated replica/promotion/demotion protocol, not demonstrated automatic failover or prevention of split-brain writes. Promotion returns a fencing proof; it does not send it to the old owner, and `add_message` checks only local `authority_role`. The author's test explicitly succeeds at writing `"split-brain attempt on host-alpha"` after beta promotion, then manually calls `host_a.demote(...)` before checking refusal. Useful manual recovery primitives exist, but claims of safe transparent failover need this limitation stated. [Write check](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/rooms.py#L272), [promotion](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/agents/core/rooms.py#L609), [author's split-brain test](https://github.com/andrei649/jarvis-hub/blob/ffbfce81a2733f4b10dc2e60463b2931a51cdadf/tests/test_h657_room_failover.py#L79).

H690 tests simulate most signing/boot behavior; the real macOS test is platform-gated. Stable ad-hoc identifier and a boot test alone do not establish actual TCC-grant persistence across a managed Python upgrade. No macOS runtime was available in this review.

# H22.5 — LRU model manager for the fast↔deep swap (design)

> Spec for an LRU-evicting model manager so the fast (VRAM) and deep (DDR5)
> local slots swap on the single 24GB GPU without OOM-thrash.
> Owner: Andrei · S:5 · Priority: P3 · Dep: H22.2, H22.4 · **Needs GPU validation**
> Lineage: Fooocus/ComfyUI `model_management.free_memory()` (see
> `docs/research/2026-06-20-oss-adoption-perf-velocity.md` §A).
> Distinct from H21.C (LLM↔diffusion swap for idle image-gen).

## Problem

`hybrid_router.select_backend()` routes light prompts to the fast slot
(`DEFAULT_LOCAL_MODEL`, VRAM) and heavy prompts to the deep slot
(`DEFAULT_DEEP_MODEL`, DDR5 spillover) — H7.5. Today nothing tracks what is
actually resident: the backends (LM Studio / Ollama) load on demand and evict on
their own TTL. Under back-to-back fast→deep→fast traffic on a 24GB card this can
thrash (load deep while fast is still resident → near-OOM → slow reload), adding
latency exactly when the deep path is already the slow one.

## Approach (mirror ComfyUI `free_memory()` + LRU)

A small `ModelManager` that tracks resident local models with last-used
timestamps and **explicitly evicts the LRU model before loading another**, keeping
a VRAM headroom reserve.

```
ModelManager (agents/core/llm/model_manager.py)
  state: {model_id -> last_used_ts}, capacity hints
  ensure_resident(model_id):
     if model_id already resident: touch ts; return
     while not enough_headroom():            # estimate vs reserve
         evict(lru_model)                     # LMStudioController.unload / Ollama keep_alive:0
     load(model_id)                           # warm path (H22.2)
     touch ts
```

### Integration

- `HybridRouter.select_backend()` stays the *decision*; the manager is the
  *residency side-effect*. After a route resolves to a local model, call
  `await model_manager.ensure_resident(model)` (best-effort, never blocks the
  decision — on failure, fall through to today's behavior).
- Reuse `LMStudioController` (`llm/lmstudio_control.py`) for LM Studio
  load/unload; for Ollama use `keep_alive: 0` to evict and the H22.2 warm-up to
  load. Both already exist.
- Headroom estimate: start coarse — a static `JARVIS_VRAM_RESERVE_MB` (default
  ~2048) and per-model size hints from `lms load --estimate-only` / Ollama
  `/api/show`. Refine after measuring.

### Gating & safety

- `JARVIS_MODEL_MANAGER=0` kill-switch (default on once validated; **default off
  until GPU-validated**).
- Never evict the model serving an in-flight request (ref-count residents).
- Strict-local agents (`frigga/ultron/howard`) unaffected — eviction is about
  *which* local model is hot, never about falling back to cloud.

## Acceptance (on the GPU box)

1. Alternating fast/deep prompts: no OOM, deep-slot p95 stable vs a thrash baseline.
2. The LRU model is the one evicted; an in-flight model is never evicted.
3. Kill-switch off → exactly today's behavior.

## Why not done in this PR

The whole value is preventing real VRAM contention — unmeasurable in CI (no GPU
runner). Build behind the kill-switch, validate against `nvidia-smi` + the
deep-slot latency benchmark on the actual 5090, then flip the default.

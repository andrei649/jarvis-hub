# H22.9 — Expose governed routes via the MCP server (design)

> Spec for making the hub "agent-native": expose allow-listed FastAPI routes as
> MCP tools alongside agents, so any MCP client can drive the hub.
> Owner: Andrei · S:5 · Priority: P3 · **Post-1.0** · Dep: existing `mcp/server.py`
> Lineage: BuilderIO/agent-native `defineAction()` *pattern* (TS lib not adopted;
> see `docs/research/2026-06-20-oss-adoption-perf-velocity.md` §C).

## Today

`agents/core/mcp/server.py:JarvisMCPServer` exposes **agents** as governed tools
(`ask_<agent>`, allow-listed via `_exposed()`, `list_tools()`/`call_tool()`). The
~298 HTTP routes are **not** reachable over MCP — an MCP client can talk to agents
but can't, say, read memory, run a workflow, or fetch status through governed
tools.

## Approach

Generate an **action manifest** from the FastAPI app (OpenAPI is already free via
Pydantic) and expose a curated, allow-listed subset of routes as MCP tools next to
the agent tools, reusing the existing permission gate.

```
FastAPI app.openapi()  ──►  route manifest (path, method, params schema, summary)
        │                         │  filter: ROUTE_TOOL_ALLOWLIST (explicit opt-in)
        ▼                         ▼
JarvisMCPServer.list_tools()  ─►  ask_<agent>  +  route_<name> tools
JarvisMCPServer.call_tool()   ─►  dispatch route_<name> → in-process call,
                                   through _admin_guard/_user_guard equivalents
```

### Design points

1. **Allow-list, never auto-expose.** A route is exposed only if it's in an
   explicit `ROUTE_TOOL_ALLOWLIST` (curated, read-mostly first: `/status`,
   `/api/memory/search`, `/dashboard`, workflow run). Mirrors the agent
   allow-list — no blanket surface.
2. **Schema from OpenAPI.** Tool input schema = the route's Pydantic/query model
   straight from `app.openapi()`; no hand-written tool schemas to drift.
3. **Governance reuse.** `call_tool("route_…")` runs the same guard the HTTP route
   uses (`_admin_guard`/`_user_guard`). A tool call carries an identity/token; an
   admin route stays admin over MCP. Mutating routes require explicit opt-in +
   the user guard.
4. **In-process dispatch**, not a loopback HTTP call (avoid re-auth round-trips
   and a second network hop).

### Gating

- `JARVIS_MCP_ROUTE_TOOLS=0` kill-switch (default off until reviewed).
- Audit every `route_*` invocation through the existing `AuditLogger`.

## Acceptance

1. An MCP client lists `route_*` tools only for allow-listed routes.
2. Calling an admin `route_*` without admin identity is refused (same as HTTP).
3. A read route (`route_status`) returns the same payload as its HTTP endpoint.
4. Kill-switch off → only `ask_<agent>` tools exposed (today's behavior).

## Why post-1.0

It widens the externally-drivable surface of the hub — that deserves the security
review the pre-1.0 audit gate is doing on the HTTP surface first (route-auth
matrix, SEC-1..4). Land the manifest generator early (read-only tools), defer
mutating route-tools until after 1.0.

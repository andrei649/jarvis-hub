## 1. Hosted Group Chat rooms (gateway-owned Bot Mode rooms)

### Gateway-hosted Group Chat rooms (durable room identity + append-only log)  `id: delta-27-31.hosted-rooms-store`
- **Surface:** Core
- **Where:** No direct UI. Backing store for Desktop → Bot Mode → "Group Chats" and for the `groups.*` JSON-RPC methods on the TUI/Desktop gateway.
- **What it does:** Gives every Bot Mode Group Chat a durable identity and a monotonic, replayable event log that lives in the gateway's `state.db` instead of in the Desktop renderer. A Group Chat therefore survives the Desktop app being closed, restarted, or replaced.
- **How it works:** New module `gateway/hosted_rooms.py` (2446 lines). `PROTOCOL_VERSION = 2` (`gateway/hosted_rooms.py:25`). SQLite schema created by `_initialize_schema()` (`gateway/hosted_rooms.py:440`) in the gateway root `state.db` (`default_db_path()`, `gateway/hosted_rooms.py:269`), WAL + `BEGIN IMMEDIATE` transactions (`_transaction`, `:1174`). Seven tables:
  - `hosted_rooms(room_id PK, name, members_json, authority_gateway_id, authority_epoch>=1, next_seq>=1, event_bytes>=0, revision>=1, created_at, updated_at, disbanded_at)`
  - `hosted_room_events(room_id, seq>=1, event_id, kind, actor_json, authority_epoch, payload_json, created_at, PK(room_id,seq), UNIQUE(room_id,event_id))`
  - `hosted_room_retired_ids(room_id PK, retired_at)` — permanent tombstone registry so a stale coordinate never names a different room
  - `hosted_room_links(room_id, member_id, target_url, target_profile, grant, catalog_json, cancellation_scope_id, trace_id, transport_security, status, updated_at)`
  - `hosted_room_remote_runs(room_id, home_install_id, authority_gateway_id, authority_epoch, member_id, task_id, execution_generation, target_install_id, target_profile, run_id, session_id, created_at, updated_at)`
  - `hosted_room_revoked_grants(scope_key PK, expires_at, revoked_before)`
  - `hosted_room_peer_reservations(room_id, member_id, target_profile, authority_gateway_id, authority_epoch, expires_at, revoked_at, created_at, updated_at)`
  Index `idx_hosted_room_events_cursor(room_id, seq)`. Migrations backfill `authority_gateway_id` (default `'legacy'`), `authority_epoch` (1), `event_bytes` (recomputed by SUM of member byte lengths), and `actor_json` (default `{"kind":"system","id":"legacy"}`) for pre-contract draft rows; `_schema_is_current()` (`:606`) hard-fails the module if a migration did not complete.
  Public API: `create_room` (`:1414`), `list_rooms` (`:1588`), `rename_room` (`:1621`), `append_event` (`:1713`), `probe_hosted_room` (`:1869`), `probe_peer_room_reservation` (`:1910`), `room_state` (`:1960`), `request_room_stop` (`:1999`), `claim_authority` (`:2027`), `disband_room` (`:2195`), `read_events` (`:2351`), `prune_disbanded_rooms` (`:1386`), plus link/grant/receipt helpers (`list_room_link_records`, `upsert_room_link_record`, `update_room_link_status`, `delete_room_link_records`, `revoke_room_grant_scope`, `reserve_peer_room`, `peer_room_is_reserved`, `peer_room_grant_is_current`, `room_grant_is_revoked`, `upsert_remote_run_receipt`, `list_remote_run_receipts`, `remote_run_receipt`).
- **Inputs / options:** Typed event kinds, gated by actor kind (`_EVENT_KINDS_BY_ACTOR`, `gateway/hosted_rooms.py:133`):
  - actor `user` → `message.user`
  - actor `member` → `message.member`
  - actor `gateway` → `member.unavailable`, `room.activity`, `room.stop_requested`, `turn.deferred`, `turn.reassigned`, `turn.cancelled`, `turn.failed`, `turn.settled`, `turn.started`
  - actor `system` → `authority.claimed`, `authority.lost`, `room.created`, `room.disbanded`, `room.members_changed`, `room.renamed`
  Actor fields allowed: `kind`, `id`, `display_name`, `profile`, `connection_id` (`_ACTOR_FIELDS`, `:156`). Identifiers must match `^[A-Za-z0-9][A-Za-z0-9._:-]*$`; event kinds `^[a-z][a-z0-9_.-]*$`.
- **Outputs / side effects:** Rows in the gateway's `state.db`; `read_events` returns a monotonic delta page; `disband_room` writes a permanent tombstone into `hosted_room_retired_ids`.
- **Config / env:** No dedicated config key; DB location follows `HERMES_HOME` / the active profile's gateway root.
- **Edge cases / guards:** Hard caps — `MAX_ROOM_ID_CHARS=128`, `MAX_EVENT_ID_CHARS=128`, `MAX_ROOM_NAME_CHARS=200`, `MAX_EVENT_KIND_CHARS=64`, `MAX_ACTOR_ID_CHARS=128`, `MAX_ACTOR_LABEL_CHARS=200`, `MAX_MEMBERS=128`, `MAX_MEMBERS_JSON_BYTES=128KiB`, `MAX_EVENT_JSON_BYTES=256KiB`, `MAX_LOG_LIMIT=500`, `MAX_LOG_PAGE_BYTES=2MiB`, `MAX_ROOM_LIST_LIMIT=500`, `MAX_ACTIVE_ROOMS=256`, `MAX_DISBANDED_ROOM_TOMBSTONES=512`, `DISBANDED_ROOM_RETENTION_SECONDS=90 days`, `MAX_EVENTS_PER_ROOM=50 000`, `MAX_ROOM_EVENT_BYTES=256MiB`, `MAX_GATEWAY_EVENT_BYTES=16MiB`, `CONTROL_EVENT_COUNT_RESERVE=64`, `CONTROL_EVENT_BYTE_RESERVE=1MiB` (`gateway/hosted_rooms.py:26-48`). Error taxonomy: `HostedRoomError`, `RoomNotFoundError`, `RoomHistoryExpiredError`, `RoomConflictError`, `RoomProbeUnavailableError`, `EventConflictError`, `AuthorityConflictError`, `AuthoritySupersededError` (`:159-193`).
- **Rebuild notes:** One SQLite table for room identity + one for an append-only log keyed `(room_id, seq)` with a UNIQUE `event_id` for idempotent sends; stamp every row with `authority_gateway_id` + `authority_epoch` so a second host can be fenced. Reserve capacity for control events so a full room can still be stopped/disbanded. A better version would move the log to a WAL-shipping replicated store so takeover needs no manual confirm, and would expose per-room retention policy rather than one global 90-day tombstone window.

### Same-gateway Group Chat driver (lease + task state machine)  `id: delta-27-31.hosted-room-driver`
- **Surface:** Core
- **Where:** Not user-visible; drives every hosted Group Chat turn. Status surfaces through `groups.state` → `driver_status` and the Desktop Group Chat pane's hold/attention badges.
- **What it does:** Owns the exclusive lease on a hosted room and the lifecycle of each member turn (queued → running → settled/failed/cancelled/indeterminate/deferred), so exactly one gateway process runs a room's turns and a crashed run can be recovered instead of silently dropped.
- **How it works:** New `gateway/hosted_room_driver.py` (1778 lines). Own SQLite schema (`_initialize_schema`, `:353`) validated by `_validate_schema` (`:378`) with a status-constraint migration (`_migrate_task_status_constraint`, `:426`). Dataclasses `TaskIdentity` (`:270`), `DriverLease` (`:288`), `TaskAttempt` (`:301`). Operations: `acquire_lease` (`:638`), `renew_lease` (`:757`), `release_lease` (`:798`), `admit_task` (`:851`), `start_task` (`:911`), `settle_task` (`:987`), `settle_stopping_task` (`:1055`), `resolve_indeterminate_task` (`:1110`), `resolve_indeterminate_cancellation` (`:1184`), `requeue_indeterminate_task` (`:1244`), `defer_indeterminate_task` (`:1298`), `requeue_deferred_task` (`:1363`), `requeue_not_admitted_task` (`:1419`). Clock is injected (`Clock = Callable[[], float]`) so recovery/fencing is testable.
- **Inputs / options:** `TASK_STATUSES = {queued, running, settled, failed, cancelled, indeterminate, deferred, …}`; `TERMINAL_STATUSES = {settled, failed, cancelled}` (`:41`, `:51`). Task payload required fields `_TASK_PAYLOAD_REQUIRED_FIELDS` plus optional `target_member_id` (`:54-57`).
- **Outputs / side effects:** Lease + task rows in `state.db`; terminal rows are pruned.
- **Config / env:** n/a (limits are constants).
- **Edge cases / guards:** `MAX_IDENTIFIER_CHARS=128`, `MAX_PROMPT_BYTES=128KiB`, `MAX_RESULT_JSON_BYTES=256KiB`, `TERMINAL_TASK_RETENTION_SECONDS=30 days`, `MAX_RETAINED_TERMINAL_TASKS=2048`, `MAX_TASK_PRUNE_BATCH=1000` (`:35-40`). Errors: `DriverStateError`, `DriverValidationError`, `RoomUnavailableError`, `LeaseHeldError`, `StaleLeaseError`, `TaskConflictError`, `StaleTaskError`, `InvalidTaskTransitionError` (`:119-148`).
- **Rebuild notes:** A leased single-writer task table with fencing tokens (epoch + lease id) and an explicit `indeterminate` state for "we lost the answer, ask the user" is the whole design. A better version would settle indeterminate turns automatically by re-reading the provider's run receipt instead of asking the user to press Retry.

### Deterministic Group Chat Discussion policy  `id: delta-27-31.hosted-room-discussion`
- **Surface:** Core
- **Where:** Decides who speaks next in a Desktop Group Chat; its output becomes a driver task and the room-log publication plan.
- **What it does:** Turns a frozen member roster plus the full typed room log into exactly one next task, deterministically — so a restart reconstructs the same discussion state without a second queue.
- **How it works:** New `gateway/hosted_room_discussion.py` (1461 lines), pure (no I/O). Dataclasses `DiscussionMember` (`:126`), `DiscussionRoom` (`:137`), `DiscussionTaskPlan` (`:148`), `DiscussionDecision` (`:161`), `EventPlan` (`:173`), `PublicationPlan` (`:198`). Key functions: `validate_user_payload` (`:272`), `validate_roster` (`:360`), `validate_room` (`:448`), `is_pass_text` (`:484`), `resolve_mentions` (`:494`), `derive_member_watermarks` (`:782`), `_build_prompt` (`:883`), `_turn_id` (`:937`). Mentions parse as `@([A-Za-z0-9][A-Za-z0-9._:-]*)` (`_MENTION_RE`, `:44`); turn ids are derived (`_TURN_ID_RE`, `:45`).
- **Inputs / options:** Member target kinds `local` (`{kind, profile}`) and `peer` (`_PEER_TARGET_FIELDS`); user payload fields `{text, thread_id}`; member message fields `_MEMBER_MESSAGE_FIELDS`; terminal event kinds `turn.settled`/`turn.failed`/`turn.cancelled`/`turn.deferred`; room activity fields `_ROOM_ACTIVITY_FIELDS`; stop fields `{cancel_id}`.
- **Outputs / side effects:** A `DiscussionDecision` naming one task + a `PublicationPlan` of events to append. No side effects of its own.
- **Config / env:** n/a
- **Edge cases / guards:** `MIN_DISCUSSION_MEMBERS=2`, `MAX_DISCUSSION_MEMBERS=6`, `MAX_DISCUSSION_ROUNDS=3`, `MAX_DISCUSSION_MESSAGES=10`, `MAX_DISCUSSION_DELTA_LINES=24`, `MAX_USER_TEXT_BYTES=64KiB`, `MAX_MEMBER_TEXT_BYTES=64KiB` (`:29-35`); over-long replies get `_TRUNCATED_REPLY_NOTICE` (`:36`). Errors: `DiscussionPolicyError`, `DiscussionValidationError`, `DiscussionReconstructionError`.
- **Rebuild notes:** Keep the policy a pure function of (roster, log) so a restart is a replay, not a resume. A better version would let a room configure its own turn-taking policy (round-robin, moderator, free-for-all) instead of hard-coding 3 rounds / 10 messages.

### Bounded policy checkpoint for busy rooms  `id: delta-27-31.hosted-room-policy-checkpoint`
- **Surface:** Core
- **Where:** Internal; makes the Group Chat poll cheap on long rooms.
- **What it does:** Materializes just enough state (the active discussion and its thread transcript) so a busy room does not replay its whole history on every poll.
- **How it works:** New `gateway/hosted_room_policy_checkpoint.py` (682 lines): `PolicySnapshot` (`:31`) and `HostedRoomPolicyCheckpoint` (`:40`), persisted alongside the room log. `_TRANSCRIPT_SCHEMA_VERSION = 1`.
- **Inputs / options:** n/a (driven by the room log).
- **Outputs / side effects:** A durable projection row per room.
- **Config / env:** n/a
- **Edge cases / guards:** `MAX_ACTIVE_POLICY_EVENTS = 64`, `MAX_THREAD_TRANSCRIPT_EVENTS = 24`, terminal kinds `{turn.settled, turn.failed, turn.cancelled, turn.deferred}` (`:19-27`). The append-only log stays the user-visible source of truth; the checkpoint is a cache that can be rebuilt.
- **Rebuild notes:** Store (last terminal seq, active thread id, bounded transcript) per room and rebuild from the log when the schema version changes.

### Group Chat log replication + fenced authority takeover  `id: delta-27-31.hosted-room-replicas`
- **Surface:** Core / Gateway
- **Where:** `groups.replicate`, `groups.replica_state`, `groups.promote`, `groups.demote` JSON-RPC methods.
- **What it does:** Lets every *other* participating gateway keep a durable copy of a room's log, and lets a survivor continue the room (at `epoch + 1`) when the authority host dies — then fence the old host if it comes back.
- **How it works:** New `gateway/hosted_room_replicas.py` (570 lines). `ingest_page()` (`:159`) persists a verbatim `groups.log` page idempotently, refusing sequence gaps (`ReplicaGapError`) and authority-epoch regressions (`ReplicaEpochRegressionError`). `promote_replica()` (`:329`) instantiates the replica as a locally-owned room at `epoch + 1` and writes an `authority.claimed` event carrying lineage. `demote_room()` (`:467`) records `authority.lost` when shown proof of a newer epoch. `replica_state()` (`:296`) reports coverage + lineage.
- **Inputs / options:** `ingest_page(room_id, room_name, members, page)`; `promote_replica(room_id, reason="authority-unreachable")`; `demote_room(room_id, observed_gateway_id, observed_epoch)`.
- **Outputs / side effects:** Replica tables in `state.db`; promotion mutates local room ownership.
- **Config / env:** n/a
- **Edge cases / guards:** `MAX_REPLICA_ROOMS = 256`, `MAX_REPLICA_EVENT_BYTES = 256MiB` (`:46-47`). Storage primitives only — nothing here decides *when* takeover is safe; the RPC layer requires an explicit `confirm: true`.
- **Rebuild notes:** Ship pages verbatim (they already carry the authority stamp), refuse gaps, and make promotion write a lineage-proving event. A better version would add a quorum/lease so promotion needs no human `confirm`.

### RoomLink — cross-gateway Group Chat members  `id: delta-27-31.hosted-room-peer`
- **Surface:** Core / API
- **Where:** `groups.peer.invite` / `groups.peer.revoke` / `groups.peer.register` RPC + `POST /v1/room-members/invitations`, `GET /v1/room-members/capabilities`, `POST /v1/room-members/grants/refresh`, `POST /v1/room-members/grants/revoke` HTTP.
- **What it does:** Lets a Group Chat member live on a *different* Hermes install. The target gateway mints a scoped, signed grant; the home gateway registers a route and dispatches turns to it over HTTP. The Desktop only bootstraps the invitation — it is never the issuer or the courier.
- **How it works:** New `gateway/hosted_room_peer.py` (887 lines), `PROTOCOL_VERSION = 2` (`:35`). Grant secret is per-install: `gateway_room_grant_secret()` (`:114`) reads/creates `<hermes root>/.room-link-grant-secret` (`_ROOM_GRANT_SECRET_FILE`, `:59`); `derive_room_grant_secret(api_key)` (`:133`) derives one from the API server key. `issue_room_grant()` (`:703`) HMAC-signs claims; `verify_room_grant()` (`:779`) / `decode_room_grant()` (`:811`) validate them; `room_grant_needs_dispatch_refresh()` (`:867`) drives renewal. `GatewayRoomCatalog` (`:212`) is the capability catalog (installation id, protocol versions, link modes, text/attachments flags, target profile, execution policy, `catalog_digest`). `HostedMemberDispatch` (`:527`) is the wire task; `RoomLinkProbe` (`:644`) + `select_room_link` (`:653`) pick a route (`_LINK_PRIORITY`, `:40`). `validate_room_link_url()` (`:491`) returns `(url, TransportSecurity)` and rejects unsafe targets.
- **Inputs / options:** Grant claim fields `_GRANT_FIELDS` (`:683`) + `status_expires_at` on refresh (`_GRANT_REFRESH_FIELDS`, `:698`): `grant_id`, `room_id`, `home_install_id`, `authority_gateway_id`, `authority_epoch`, `member_id`, `target_install_id`, `target_profile`, `execution_policy_digest`, `expires_at`. Permissions used by callers: `dispatch`, `status`, `approve`, `stop`. `MAX_TOKEN_BYTES=16KiB`, `MAX_PROMPT_BYTES=256KiB`, `MAX_DISPATCH_GRANT_TTL_SECONDS=24h`, `MAX_STATUS_GRANT_TTL_SECONDS=30 days`.
- **Outputs / side effects:** A grant token string (opaque, never logged or included in reprs); reservations and revocations in `hosted_room_peer_reservations` / `hosted_room_revoked_grants`.
- **Config / env:** RoomLink endpoint URL is read from config (`_room_link_url_from_config`, `:449`, `_configured_room_link_url`, `:469`).
- **Edge cases / guards:** Identifiers `^[A-Za-z0-9][A-Za-z0-9._:@/-]{0,255}$`; digests must be 64 lowercase hex (`_DIGEST_RE`). Grants are never included in status payloads or exception messages. Secret file permissions are checked (`stat` import). Errors: `HostedRoomPeerError`, `HostedRoomGrantError`.
- **Rebuild notes:** Target-issued HMAC grants scoped to (room, epoch, member, target profile, execution-policy digest) with short dispatch TTLs and long status TTLs; verify the digest on every renewal so a changed policy forces re-authorization. A better version would use asymmetric keys so the home never needs a shared secret with each target.

### Session-persistent Python kernels for `execute_code` (local)  `id: delta-27-31.code-kernel`
- **Surface:** Tool
- **Where:** The `execute_code` tool, on every surface. Visible in the tool description: *"Calls run in a persistent session kernel: variables, imports, and loaded data survive across execute_code calls, so build on earlier work instead of re-loading it. A timed-out or interrupted call loses that state."*
- **What it does:** `execute_code` now keeps one Python child process alive per conversation instead of spawning a fresh one per call, so variables, imports and loaded data survive between calls and across user turns.
- **How it works:** New `tools/code_kernel.py` (846 lines). One kernel per key `(owner, mode, child_python, child_cwd, tool-set)` (`_kernel_key`, `:346`); the owner is the conversation's approval session key, with `::child::{id}` for delegated subagents (`_resolve_owner`, `:306`). `SessionKernel` (`:248`) holds the `subprocess.Popen`, reader threads (`_stdout_reader`, `:475`; `_stderr_reader`, `:535`) and the per-cell RPC loop (`_rpc_forever`, `:427`). The child runs `KERNEL_RUNNER_SOURCE` (`:74`), a small REPL loop. Wire protocol: requests are one JSON object per line on stdin (`{"id": str, "code": str}`); responses are framed on stdout as `<SENTINEL> <byte-length>\n<json-payload>` where SENTINEL is a per-kernel random token from `HERMES_KERNEL_SENTINEL`; unframed bytes are raw fd output attributed to the running cell (calls are serialized per kernel). Env is built by the same `_build_child_env` the per-call path uses (secret scrubbing, tool whitelist, PYTHONPATH) and is **frozen at spawn**. Entry point `execute_in_session_kernel()` (`:631`); teardown `_teardown` (`:404`), `shutdown_all_kernels` (`:351`), `shutdown_kernels_for_owner` (`:360`), LRU eviction `_evict_over_cap_unlocked` (`:388`), idle reaping `_reap_unlocked` (`:376`).
- **Inputs / options:** `execute_code(code: str, reset: bool)` — `reset` = *"Discard the kernel's persistent state and start fresh before running this code."* Lifecycle bounds come from config; module defaults `DEFAULT_MAX_SESSION_KERNELS = 4`, `DEFAULT_KERNEL_IDLE_TIMEOUT = 1800` (`:287-288`), inline capture cap `_RUNNER_CAPTURE_BYTES = 1_000_000` (`:72`).
- **Outputs / side effects:** A live child process per conversation; the result payload names the kernel so a frozen env is diagnosable. Kernels die with the session (session clear/new), on idle timeout, on LRU eviction, on `reset=true`, and on cell timeout/interrupt.
- **Config / env:** `code_execution.kernel_idle_timeout` (default `1800`), `code_execution.max_session_kernels` (default `4`), `code_execution.mode` (`project` | `strict`). Child env vars `HERMES_KERNEL_SENTINEL`, `HERMES_KERNEL_SPILL_DIR`.
- **Edge cases / guards:** A timed-out or interrupted cell **kills the whole kernel process tree** and drops the registry entry (state lost by design — one cell cannot be safely interrupted in place). Tool-RPC authority is rebound per cell (`CellAuthority`, `:175`), so a later cell's tool calls run under that cell's approval/session context. A script printing a forged frame can only lie to its own caller. Windows branch guarded by `_IS_WINDOWS` (`:68`).
- **Rebuild notes:** Long-lived interpreter + line-delimited JSON requests + length-framed replies with a random sentinel; kill on timeout instead of trying to interrupt. A better version would checkpoint the namespace so a timeout does not lose state, and would allow explicit named kernels the user can list and kill.

### Session-persistent kernels for REMOTE terminal backends  `id: delta-27-31.code-kernel-remote`
- **Surface:** Tool
- **Where:** `execute_code` when the session's terminal backend is `docker`, `ssh`, `modal` (and equivalents).
- **What it does:** Brings the same persistent-kernel behavior to remote execution backends, which previously re-shipped and re-ran a fresh script per call and lost all interpreter state (closes upstream #96873).
- **How it works:** New `tools/code_kernel_remote.py` (498 lines). The transport offers only run-to-completion `env.execute(cmd)`, so three primitives are rebuilt on top: (1) the runner is started detached with `nohup … &` and its PID recorded, later probed with `kill -0` (`_is_alive`, `:165`); (2) a file-based CELL protocol in the kernel dir — `cell_req_NNNNNN.json` / `cell_res_NNNNNN.json` — sits beside the existing file-based TOOL-RPC `req_`/`res_` protocol, which is reused unchanged, with the host-side `_rpc_poll_loop` started per cell using the calling thread's context (that is what gives per-cell tool authority); (3) death detection — a failed liveness probe reads as *kernel died: state lost* and the next call respawns and says so. `RemoteKernel` (`:146`), `_spawn_remote_kernel` (`:225`), `execute_in_remote_kernel` (`:300`), `_kill` (`:182`), `shutdown_all_remote_kernels` (`:202`), `shutdown_remote_kernels_for_owner` (`:210`). - **Inputs / options:** Same `execute_code(code, reset)` surface. Kernel key is `(owner, env_type, task_env_id)` (`:161`). `_CELL_POLL_INTERVAL = 0.5 s` (`:53`).
- **Outputs / side effects:** A detached process inside the remote environment plus a kernel directory of request/response files.
- **Config / env:** Same `code_execution.*` keys; `HERMES_KERNEL_DIR` inside the remote env.
- **Edge cases / guards:** Every wait is bounded by the cell timeout — never a hung poll. **Spawn failure fails OPEN** to the per-call path with a note, so a degraded remote host does not block execution. Owner resolution is imported from `tools.code_kernel` so the two paths cannot drift.
- **Rebuild notes:** When you only have run-to-completion exec, a detached runner + a file mailbox + `kill -0` liveness gives you a kernel. A better version would use a real bidirectional channel (ssh multiplexed session / docker attach) instead of file polling.

### `hermes config set|unset` handles literal dots in key names  `id: delta-27-31.config-literal-dots`
- **Surface:** CLI
- **Where:** `hermes config set <key> <value>`, `hermes config unset <key>`, `hermes config get <key>`.
- **What it does:** Config keys whose *name* contains a dot (model ids like `grok-4.6`, `glm-5.3`, Matrix room ids like `!room:chat.example.cc`, versioned provider names) can now be addressed — previously they were silently split into bogus nested segments.
- **How it works:** `hermes_cli/config.py`:
  - `_split_key_path(key)` (`:1058`) honors backslash-escaped dots: `providers.qwen3\.5-397b.api_key` → `["providers", "qwen3.5-397b", "api_key"]`. Backslashes before any other character are preserved verbatim; keys without escapes behave exactly like `key.split(".")`.
  - `_greedy_literal_match(container, parts)` (`:1093`) — when navigating an EXISTING mapping, prefer an existing literal key equal to the dot-join of the next N segments, longest match first. Backward compatible: with no multi-segment literal key the only candidate is `parts[0]`, i.e. the historic plain split.
  - `_phantom_sibling(container, part)` (`:1118`) — when a write is about to CREATE a new intermediate mapping named `part` and the mapping already holds a literal dotted key starting with `part + "."` (e.g. creating `grok-4` beside an existing `grok-4.5`), the write **fails loudly** with a `ValueError` instead of silently writing a phantom the runtime never reads.
  Applied consistently in `_set_nested` (`:1161`), `_unset_nested` (`:1260`) and the read path (`:1290`).
- **Inputs / options:** Backslash escaping (`\.`) plus automatic greedy literal matching.
- **Outputs / side effects:** Correct nesting in `config.yaml`; a loud error instead of a phantom sibling.
- **Config / env:** n/a
- **Edge cases / guards:** Users typing `providers.myprov.models.grok-4.6.context_length` do not know the escape syntax exists — that is exactly the case greedy matching handles.
- **Rebuild notes:** Dots in key names are the norm; prefer an existing literal key over a blind split, and refuse to create a sibling that shadows one.

### Stable per-install identity (`install_id`)  `id: delta-27-31.install-identity`
- **Surface:** Core
- **Where:** `<hermes root>/install_id`; consumed by hosted-room authority (`local_authority_gateway_id()`), RoomLink catalogs, and the Desktop connections registry.
- **What it does:** Gives one physical install a stable opaque identity shared by all its profiles, so authority fencing and connection registries can name a machine.
- **How it works:** New `hermes_cli/install_identity.py` (153 lines). `read_or_create_install_id(root=None)` (`:73`) reads `<root>/install_id` (must match `^[0-9a-f]{32}$`) or atomically mints `uuid4().hex`: `mkstemp` in the root, write + `flush` + `fsync`, `os.replace`, then `_fsync_directory(root)` (`:57`, POSIX only). Publication is fenced by `_install_id_file_lock(root)` (`:24`) on `<root>/.install_id.lock` — `fcntl.flock(LOCK_EX)` on POSIX, `msvcrt.locking(LK_LOCK, 1)` on Windows (with a 1-byte file pre-write because Windows byte-range locks need content) — plus an in-process `_INSTALL_ID_PUBLICATION_LOCK` because Windows byte-range locks can report a same-process conflict instead of waiting. `get_install_id()` (`:126`) caches per root with `_INSTALL_ID_LOCK`.
- **Inputs / options:** Optional `root`; optional injected `cache` dict for tests.
- **Outputs / side effects:** The file `<hermes root>/install_id` (32 lowercase hex + newline) and a lock file.
- **Config / env:** Root from `hermes_constants.get_default_hermes_root()` (honors `HERMES_HOME`).
- **Edge cases / guards:** Returns `None` when the id can neither be read nor persisted — **an ephemeral id would violate the authority and connection-registry contract**, so callers must handle `None` rather than get a random value. Corrupt/undecodable file → `None`.
- **Rebuild notes:** Atomic mint under a cross-process file lock, verify by re-reading after replace, and never fall back to an ephemeral value for an identity other machines will compare against.

### macOS TCC anchor for the uv-managed interpreter  `id: delta-27-31.macos-tcc-anchor`
- **Surface:** Core (macOS)
- **Where:** Runs during install/update; state readable via `tcc_anchor_state()`.
- **What it does:** Keeps macOS privacy (TCC) grants — Screen Recording, Accessibility, Files — attached to Hermes across Python patch bumps, by giving the interpreter one stable absolute path.
- **How it works:** New `hermes_cli/macos_tcc_anchor.py` (444 lines). macOS keys TCC grants to the resolved absolute path of the client binary, and Hermes' uv-managed interpreter lives at a versioned store path, so every patch bump orphaned every prior grant. `ensure_tcc_anchor(project_root=None)` (`:368`) copies the store interpreter to `venv/bin/python` and pins the signature by identifier, so TCC attribution stays on the stable venv path. A marker file `.tcc-anchor-source` records the source.
- **Inputs / options:** `ensure_tcc_anchor(project_root)`; `tcc_anchor_state(project_root)` → `(state, detail)`.
- **Outputs / side effects:** `venv/bin/python` (+ `python3`, `python3.N` copies), possibly `venv/lib/libpython*`, and the `.tcc-anchor-source` marker.
- **Config / env:** n/a
- **Edge cases / guards:** No-op on non-macOS and for interpreters that are not uv-managed; best-effort — never raises to callers. A surplus provisioned dylib left in `venv/lib/` after a rollback is harmless.
- **Rebuild notes:** If the OS keys permissions to a path, own that path; and gate any interpreter surgery behind a real launch test with rollback.

### Worktree disk reclamation for pushed PR lanes + cron-tick pruning  `id: delta-27-31.worktree-reclaim`
- **Surface:** CLI | Core
- **Where:** `hermes -w` startup pruner, `hermes worktree prune`, `hermes worktree list`, and the cron scheduler tick.
- **What it does:** Closes two disk-growth leaks: pushed open-PR worktrees are now reclaimed, and gateway-driven boxes prune worktrees on the scheduler tick instead of only on `hermes -w` launches.
- **How it works:** Commit `3a351a9665`. (1) Managed installs fetch with a single-branch refspec (`+refs/heads/main:…`), so pushed PR branches never get `refs/remotes/*` entries and `git log HEAD --not --remotes` misreports them as unpushed forever — the dominant survivor class (24 of 33 preserved trees, ~18 GB on the reporting box). New `_fetch_remote_branch_heads(repo_root, timeout=20)` (`cli.py:2395`) makes ONE `git ls-remote --heads origin` call per sweep, returning `{branch: sha}` for every branch on origin, so callers pay a single bounded network round-trip instead of per-tree probes. When a clean tree's branch head EXACTLY matches origin, the checkout is redundant: **reap the TREE, keep the BRANCH ref** (shielded from the orphaned-branch pass). Anything diverged or unverifiable stays preserved. Applied to both the startup pruner and `hermes worktree prune`/`list`. (2) The scheduler tick dispatches the same conservative pruner on a daemon thread, throttled to once per 6 h, against the install checkout plus job-workdir repos that have a `.worktrees/` dir.
- **Inputs / options:** n/a (existing `hermes worktree` subcommands).
- **Outputs / side effects:** Deleted worktree directories; branch refs preserved.
- **Config / env:** n/a
- **Edge cases / guards:** `ls-remote` is lazy and bounded (20 s); unverifiable state always preserves the tree.
- **Rebuild notes:** One remote listing per sweep, and never delete a branch ref when you delete its checkout.

### `dashboard.trusted_proxies`  `id: delta-27-31.dashboard-trusted-proxies`
- **Surface:** Config | Web dashboard
- **Where:** `dashboard.trusted_proxies` in `config.yaml`.
- **What it does:** Names the reverse proxies allowed to supply `X-Forwarded-Proto` / `X-Forwarded-For` to the dashboard server, so arbitrary clients cannot spoof their scheme or source address.
- **How it works:** New key `dashboard.trusted_proxies: []`. `hermes_cli/web_server.py:19495 _dashboard_forwarded_allow_ips()` starts from `_DEFAULT_DASHBOARD_FORWARDED_ALLOW_IPS` (uvicorn's default: loopback, always trusted) and extends it with validated entries. - **Surface:** Provider (memory)

### `state.db` corruption containment and FTS recovery  `id: delta-27-31.state-db-recovery`
- **Surface:** Core | CLI | Docs
- **Where:** `hermes sessions repair [--check-only] [--no-backup]`, `hermes doctor`; documented in the NEW `docs/state-db-recovery.md`.
- **What it does:** A corrupt full-text-search index no longer turns a live message write or search into an unbounded full-transcript rebuild — canonical writes keep working and searches fall back — and the explicit repair path is now documented.
- **How it works:** New doc `docs/state-db-recovery.md` states the contract: `sessions` and `messages` are canonical; `messages_fts*` and their sync triggers are derived indexes that may be detached temporarily. When an FTS write or search reports the corruption error class, `SessionDB` (1) records the durable `fts_stale` marker, (2) removes the FTS sync triggers in the same transaction, (3) retries canonical writes without the derived-index sinks, and (4) serves searches from canonical rows through the `LIKE` fallback. **The failing live operation never runs `FTS5('rebuild')`** (commit `18ac3c4fb6` "defer corrupt FTS rebuilds past live operations"); a later `SessionDB` open may rebuild under the cross-process admission lock and foreign-holder guard, and if that guarded rebuild cannot run, FTS stays detached, canonical writes stay available, and `hermes doctor` reports the explicit repair command. Supporting fixes in the same range: fail closed on unscoped corruption (`96739033c4`), quarantine a 0-byte truncated `state.db` and record store provenance (`a071fc80da`), serialize startup across zero-byte check/quarantine/connect/schema commit (`69245e65bd`), cap read connections per process (`0e9b57d310`) and per file (`e8c41568ca`), isolate background reads from the writer connection (`94869e5a0d`), route post-repair journal-mode restore through the canonical path (`e40f1be759`, `db63afb9d7`, `786e65bf4f`), make `state.db` `synchronous` configurable on every platform (`ef29fc63d7`), warn when an existing DB's `journal_mode` is flipped to WAL (`d5d42b96ef`) or when a configured `journal_mode: delete` is overridden by an on-disk WAL (`9aeb582e38`), stamp the launch-profile name on new session rows instead of NULL (`6874b99d49`), and stop the empty-session sweep from deleting an archived transcript (`0bfe715e4d`).
- **Inputs / options:** `hermes sessions repair` — `--check-only` (*"Only report whether the database opens cleanly; do not modify it"*), `--no-backup` (*"Skip the timestamped backup copy (not recommended)"*). Help: *"Recover a state.db whose schema is malformed (e.g. 'table messages_fts already exists'), which makes Desktop/Dashboard show no sessions. A backup is made first; sessions and messages are preserved and the FTS search index is rebuilt if needed."*
- **Outputs / side effects:** A SQLite backup by default; a repaired database promoted through the guarded snapshot-and-promotion path; the `fts_stale` marker in `state_meta`.
- **Config / env:** `database.journal_mode`, `database.synchronous`.
- **Edge cases / guards:** Documented procedure: stop every process that can open the profile database (`hermes gateway stop`) and keep them stopped for the whole repair and verification window; **never** copy `state.db`, `state.db-wal` and `state.db-shm` independently with `cp` — they are one live SQLite image. Verify afterwards with `hermes sessions repair --check-only` plus the `fts_stale` and `sqlite_master` queries in the doc.
- **Rebuild notes:** Split canonical from derived storage explicitly, degrade the derived half instead of blocking writes, and document the offline repair as the only rebuild path.

### Desktop heals a session bound to a runtime the gateway no longer holds  `id: delta-27-31.desktop-runtime-gone`
- **Surface:** Desktop app
- **Where:** Any session view (chat or tile) whose backend runtime was reaped.
- **What it does:** A view bound to a dead runtime now recovers instead of staying bound to a phantom for the rest of its life.
- **How it works:** New `apps/desktop/src/store/runtime-gone.ts` (+ test).

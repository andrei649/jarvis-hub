# Gap-fill — Desktop self-update: version-skew toasts and the Settings → About updates card

This shard closes four uncovered i18n strings in the desktop **self-update / version-check** area
(`notifications.backendOutOfDateTitle`, `notifications.installMethodUnsupportedTitle`,
`notifications.updateReadyMessageUnknown`, `notifications.seeWhatsNew`). It documents the three
renderer-side update toasts produced by `apps/desktop/src/store/updates.ts` (backend-contract skew,
unsupported install method, update-ready) plus the **Settings → About** updates card that carries the
same "See what's new" label, and the background poller that drives all of them.
Deliberately left to sibling shards: the Electron-main update *machinery* — check/apply/hand-off/marker/
progress IPC (`desktop-main.updates-*`), the **Updates overlay** dialog and its stage views
(`desktop-a.updates-overlay`), the statusbar version pills (`desktop-a.statusbar-version-client` /
`-backend`), fleet fan-out (`desktop-main.update-all`), the notification-center chrome itself, and the
CLI `hermes update` command (`cli-f`).

---

### Update-ready toast ("Update ready" / "See what's new")  `id: gapfill-desktop-main.update-ready-toast`
- **Surface:** Desktop app
- **Where:** Top-centre toast stack (the `default` placement — errors/warnings/action toasts, portaled at `left-1/2 top-[calc(var(--titlebar-height,34px)+0.75rem)]`, `apps/desktop/src/components/notifications.tsx:122`). Title verbatim **"Update ready"** (`i18n: notifications.updateReadyTitle`); body is either **"`<count>` new change`(s)` available."** (`i18n: notifications.updateReadyMessage`, e.g. "7 new changes available." / "1 new change available.") or, when the exact count is unknowable, **"A new update is available."** (`i18n: notifications.updateReadyMessageUnknown`); single action button **"See what's new"** (`i18n: notifications.seeWhatsNew`); close button `aria-label` **"Dismiss notification"** (`i18n: notifications.dismiss`). Icon is the codicon `gift`.
- **What it does:** Tells the user, at most once per 24-hour window, that a newer Hermes is available, and gives them one click into the changelog/update overlay.
- **How it works:** `maybeNotifyUpdateAvailable(status)` (`apps/desktop/src/store/updates.ts:209-246`) is called from `checkUpdates()` (`:407`, client/local checkout via the Electron bridge `window.hermesDesktop.updates.check()`) and from `checkBackendUpdates()` (`:376`, remote mode via REST `checkHermesUpdate(true)` mapped by `mapBackendCheck`, `:350`). It bails when: `!status`, `status.supported === false`, `status.error` is set, `!status.targetSha`, when `(behind ?? 0) <= 0 && !status.updateAvailable`, when the toast is snoozed, or when `$updateApply.get().applying` is already true. Otherwise it calls `notify({ action:{label: notifications.seeWhatsNew, onClick}, durationMs: 0, icon: 'gift', id: 'desktop-update-available', kind: 'info', message, onDismiss, title: notifications.updateReadyTitle })`. `behind` is a first-class tri-state: a number > 0 → counted copy, `null` (shallow clone with no merge-base) + `updateAvailable` → the count-free `updateReadyMessageUnknown` copy (`updates.ts:216-224`, test `store/updates.test.ts:178-183`). Both the action click and the dismiss call `snoozeUpdateToast()` (`:85`), which persists `Date.now() + 24h` into `localStorage` key `hermes:update-toast-snooze-until` through `persistString` (`src/lib/storage.ts` `writeKey`, try/catch-guarded); `isUpdateToastSnoozed()` (`:89`) suppresses re-shows until then. Snoozing is deliberately **time-based, not per-sha**: the upstream repo lands ~100 commits a day, so a "don't show this exact sha again" guard re-popped on every new commit (comment `updates.ts:78-81`). The toast id is also dismissed at the start of an apply (`dismissNotification(UPDATE_TOAST_ID)` at `:437` for the client and `:639` for the backend) and reused at `:504` for the success toast **"You're all set"** / **"Hermes will pick up the new version next time you launch it."** (`i18n: updates.allSetTitle` / `updates.manualPickedUp`, `durationMs: 8000`, `kind: 'success'`, `placement: 'default'`). Checks are driven by `startUpdatePoller()` (`updates.ts:956-995`): one immediate `checkUpdates()` + `checkBackendUpdates()` + `refreshDesktopVersion()` at mount, a `$connection` subscription that re-checks the backend when the mode flips to `remote`, a window `focus` listener throttled to once per 5 min (`onFocus`, `:1011`), and a `setInterval` every **30 minutes** (`30 * 60 * 1000`, `:988`). `stopUpdatePoller()` (`:997`) tears all of it down.
- **Inputs / options:** Action button **"See what's new"** → `snoozeUpdateToast()` then `openUpdatesWindow()` (`updates.ts:251`), which calls `openUpdateOverlayFor(isRemoteMode() ? 'backend' : 'client')` — i.e. sets `$updateOverlayTarget`, opens `$updateOverlayOpen`, and kicks a fresh check for that target. Close (×) button → `dismissNotification('desktop-update-available')` → `onDismiss` → `snoozeUpdateToast()`. No other controls; `durationMs: 0` means it never auto-expires.
- **Outputs / side effects:** A toast in `$notifications` (the store caps the stack at 4, newest first, `store/notifications.ts:178`); `localStorage['hermes:update-toast-snooze-until']`; opening the Updates overlay.
- **Config / env:** n/a (no config key gates it; the tracked branch it implicitly reports comes from `<userData>/updates.json`).
- **Edge cases / guards:** Never renders a fabricated commit count — `behind: null` maps to the generic sentence. Suppressed entirely while an update is applying, so the toast cannot fight the overlay. `notify()` replaces any existing toast with the same id rather than stacking duplicates. Storage failures (private mode, quota) are swallowed by `writeKey`/`readKey`, in which case the snooze silently degrades to "show every check". In remote mode the toast describes the *backend*, not the desktop client — `targetSha` is synthesised as `` `backend:${res.current_version}` `` (`:358`).
- **Rebuild notes:** Emit one deduplicated, non-expiring info toast per update-availability signal, keyed by a stable id, with a persisted time-based snooze restarted by BOTH the action and the dismiss. Keep "count unknown" as a distinct render path. A better version would batch the changelog headline into the toast body and offer a "remind me at next launch" alongside the 24 h snooze, and would key the snooze to the *branch* so switching update branches re-notifies immediately.

### Backend-out-of-date (contract skew) toast  `id: gapfill-desktop-main.backend-contract-skew-toast`
- **Surface:** Desktop app
- **Where:** Top-centre toast stack, warning tone (amber `AlertTriangle`, `notifications.tsx:25`). Title verbatim **"Backend out of date"** (`i18n: notifications.backendOutOfDateTitle`); body verbatim **"Your Hermes backend is older than this desktop build and may not work correctly. Update to align them."** (`i18n: notifications.backendOutOfDateMessage`); action button **"Update Hermes"** (`i18n: notifications.updateHermes`); close button **"Dismiss notification"**.
- **What it does:** Warns when the connected `tui_gateway` backend advertises an RPC contract older than the one this desktop build was written against, and offers a one-click backend update that self-heals the skew.
- **How it works:** `reportBackendContract(contract)` (`apps/desktop/src/store/updates.ts:151-180`) compares `contract ?? 0` against the module constant `REQUIRED_BACKEND_CONTRACT = 6` (`:104`). The number arrives as `desktop_contract` on the session runtime info payload the backend sends (`tui_gateway/methods_session.py:158`, `tui_gateway/server.py:7560`, `:10549`, `:10897` — all echo `DESKTOP_BACKEND_CONTRACT`) and is fed in by `applyRuntimeInfo(info)` (`apps/desktop/src/app/session/hooks/use-session-actions/utils.ts:1611`), which runs on every `session.create` / `session.resume` / `session.activate`. When satisfied it calls `dismissNotification('backend-contract-skew')` **and clears the snooze** (`persistString(SKEW_TOAST_SNOOZE_KEY, null)`, `:156`) so a later regression warns immediately (test `store/updates.test.ts:232-236`). When behind and not snoozed it fires `notify({ action:{label: notifications.updateHermes, onClick}, durationMs: 0, id: 'backend-contract-skew', kind: 'warning', message: notifications.backendOutOfDateMessage, onDismiss, title: notifications.backendOutOfDateTitle })`. Snooze: `localStorage['hermes:backend-skew-toast-snooze-until']`, cooldown `24 * 60 * 60 * 1000` (`:111-121`) — without it the warning re-popped on every thread the user opened, because the check runs on every session open (comment `:106-110`). The documented contract ladder (comment `:96-103`): **v2** = the `file.attach` RPC (remote-gateway non-image file upload); **v3** = `approvals.mode` config RPCs + `session.info` reconciliation; **v4** = explicit Fast-off session creation and session-scoped Fast edits; **v5** = raised WebSocket frame size for large one-shot `file.attach`; **v6** = key-addressed `plugins.manage` rows (keyless rows render read-only in Settings → Plugins).
- **Inputs / options:** Action button **"Update Hermes"** → `snoozeSkewToast()` then `applyBackendUpdate()` (the remote-backend apply path, `runBackendUpdate`, `updates.ts:638`). Close (×) → `onDismiss` → `snoozeSkewToast()`. `durationMs: 0` (never auto-dismisses; warnings default to 0 anyway, `store/notifications.ts:51-56`).
- **Outputs / side effects:** A warning toast; `localStorage['hermes:backend-skew-toast-snooze-until']`; clicking the action starts a backend update (which itself dismisses the update-ready toast and drives `$backendUpdateApply` through the `updates.applyStatus.*` copy).
- **Config / env:** n/a
- **Edge cases / guards:** A backend that reports **no** `desktop_contract` at all (a pre-GUI checkout) is treated as contract `0` and warns (test `updates.test.ts:199-203`). The toast is app/profile-level, not session-level — the comment at `use-session-actions/utils.ts:1608-1610` notes a tile's runtime reports skew just as usefully. Because both this toast and the update-ready toast can be live at once, they use distinct ids so neither replaces the other.
- **Rebuild notes:** Version the client↔server RPC surface with a single monotonic integer the server echoes on every session payload; compare it client-side, warn with a one-click remedy, snooze on dismissal, and **clear the snooze the moment the contract is satisfied** so a downgrade is not silently swallowed. A better version would name the specific missing capability ("this backend cannot attach files") instead of a generic "may not work correctly", and would degrade the affected UI affordances rather than only toasting.

### Unsupported install method toast  `id: gapfill-desktop-main.install-method-unsupported-toast`
- **Surface:** Desktop app
- **Where:** Top-centre toast stack, warning tone. Title verbatim **"Unsupported install method"** (`i18n: notifications.installMethodUnsupportedTitle`); body is the backend-supplied warning string verbatim (no client-side copy); close button **"Dismiss notification"**. No action button.
- **What it does:** Surfaces a backend-authored warning that the running installation cannot be auto-updated (or otherwise cannot be managed) from inside the app, so the user knows to update by the method that installed it.
- **How it works:** `reportInstallMethodWarning(message)` (`apps/desktop/src/store/updates.ts:182-201`). A falsy/absent message immediately calls `dismissNotification('install-method-not-supported')` — the condition clearing itself retracts the toast. Otherwise, if not snoozed, it fires `notify({ durationMs: 0, id: 'install-method-not-supported', kind: 'warning', message, onDismiss: () => snoozeInstallMethodToast(), title: notifications.installMethodUnsupportedTitle })`. Snooze: `localStorage['hermes:install-method-toast-snooze-until']`, cooldown `24 * 60 * 60 * 1000` (`:124-139`); the comment at `:125-127` explains why it exists — the warning is re-derived from **every** `session.info` (`session.create` / `session.resume` / `session.activate` all route through `applyRuntimeInfo`), so it would re-pop on every session switch. Two call sites feed it: `applyRuntimeInfo(info)` → `reportInstallMethodWarning(info.install_warning)` (`app/session/hooks/use-session-actions/utils.ts:1619`) and the streaming `session_info` gateway event → `reportInstallMethodWarning(payload?.install_warning)` (`app/session/hooks/use-message-stream/gateway-event/session-info.ts:409`, only when `apply` is true, i.e. the foreground context). The wire field is typed as `install_warning?: string` in `apps/desktop/src/types/hermes.ts:704` and `apps/desktop/src/lib/chat-messages/types.ts:88`. The equivalent surface in the TUI renders it inline in the branding header as `! {info.install_warning}` in the warn colour (`ui-tui/src/components/branding.tsx:484-486`, type at `ui-tui/src/types.ts:190`). The concept the message describes lives in `hermes_cli/config.py`: `detect_install_method(project_root)` and `recommended_update_command_for_method(method)` (`config.py:623-633`) map `nix`/`nixos`/`home-manager` → the long `_NIX_UPDATE_MSG`, `docker` → `docker pull nousresearch/hermes-agent:latest`, `apt` (Termux) → `pkg upgrade hermes-agent`, everything else → `hermes update`; the code-scoped stamp is written to `<project_root>/.install_method` (`config.py:593-611`).
- **Inputs / options:** Close (×) button only → `dismissNotification('install-method-not-supported')` → `onDismiss` → `snoozeInstallMethodToast()`. `durationMs: 0`, so it persists until dismissed or retracted.
- **Outputs / side effects:** A warning toast; `localStorage['hermes:install-method-toast-snooze-until']`.
- **Config / env:** n/a
- **Edge cases / guards:** The body text is 100 % backend-authored and is **not** translated client-side — only the title is localised (`ar.ts` has no `installMethodUnsupportedTitle` key at all as of v2026.8.31, so Arabic falls back to English for this title, whereas `ja.ts:141`, `zh.ts:136` and `zh-hant.ts:136` do translate it). In this checkout no Python code path actually populates `install_warning` (grep across the repo finds only the TypeScript consumers and the type declarations), so the toast is wired end-to-end but dormant unless a backend build sets the field — a forward-compatible channel rather than a live one. Passing `undefined` is the retraction signal, so a backend that stops sending the field clears the toast on the next session event.
- **Rebuild notes:** Give the server one free-text "your install cannot self-update, do X instead" channel on the session payload, render it as a sticky warning toast with a stable id, treat "field absent" as retraction, and snooze on dismissal because the field is re-sent on every session event. A better version would send a structured `{method, reason, command}` triple so the client can render a copy-to-clipboard command button (as the Updates overlay's ManualView already does) instead of a bare sentence, and would localise the reason client-side.

### Settings → About → Updates card  `id: gapfill-desktop-main.about-updates-card`
- **Surface:** Desktop app
- **Where:** **Settings → About** (`apps/desktop/src/app/settings/about-settings.tsx`, 212 lines). Header block: brand mark, heading **"Hermes Desktop"** (`i18n: settings.about.heading`) and **"Version `<value>`"** (`settings.about.version`) or **"Version unavailable"** (`settings.about.versionUnavailable`). Section heading **"Updates"** (`settings.about.updates`, `RefreshCw` icon). Buttons in the card, left to right: **"Check now"** / **"Checking…"** (`settings.about.checkNow` / `checking`), **"Update now"** (`settings.about.updateNow`), **"See what's new"** (`settings.about.seeWhatsNew`), and right-aligned **"Release notes"** (`settings.about.releaseNotes`). Below: the read-only row **"Automatic updates"** (`settings.about.automaticUpdates`).
- **What it does:** Shows the running desktop version, whether an update is waiting, when the last check ran, and offers check / update / changelog / release-notes actions, plus the app-build-skew warning and the uninstall section.
- **How it works:** `AboutSettings()` (`about-settings.tsx:49-211`). Subscribes to `$desktopVersion`, `$updateStatus`, `$updateApply`, `$updateChecking` from `store/updates.ts`; `useEffect(() => { void refreshDesktopVersion() }, [])` on mount re-reads the version because the atom is loaded once at boot and would show a stale number right after a self-update (comment `:56-59`). Derived state: `behind = status?.behind ?? 0`; `updateAvailable = behind > 0 || Boolean(status?.updateAvailable)`; `supported = status?.supported !== false`; `applying = apply.applying || apply.stage === 'restart'`. The status line + tone (`'idle' | 'available' | 'error'`) is a ladder (`:78-96`): `!supported` → `status.message` or **"This build can't update itself from inside the app."** (`cantUpdate`, error tone); `status.error` → **"We couldn't reach the update server."** (`cantReach`, error); `applying` → **"An update is currently installing."** (`installing`, available); `updateAvailable` → **"A new update is ready (`<n>` change`(s)` included)."** (`updateReady`) when `behind > 0` else **"A new update is ready."** (`updateReadyUnknown`), available tone; a `status` with nothing pending → **"You're on the latest version."** (`onLatest`); no status yet → **"Tap "Check now" to look for updates."** (`tapCheck`). Sub-line: **"Last checked `<age>`"** (`lastChecked`) where `relativeTime()` (`:27-46`) renders **"never"** (`never`), **"just now"** (`justNow`), **"`<n>` min ago"** (`minAgo`), **"`<n>` hours ago"** (`hoursAgo`) or **"`<n>` days ago"** (`daysAgo`), with **" · just now"** (`justNowSuffix`) appended right after a manual check. Icons: codicon `cloud-download` for the available tone, `CheckCircle2` (emerald) for idle, none for error.
- **Inputs / options:**
  - **"Check now"** button (`variant="textStrong"`, `RefreshCw` icon) — `disabled={checking || applying || !supported}`; `onClick` → `handleCheck()` → `setJustChecked(false)`, `await checkUpdates()`, `setJustChecked(Boolean(next))`. While in flight the label becomes **"Checking…"** with a spinning `Loader2`.
  - **"Update now"** button (primary) — rendered only when `updateAvailable && supported && !applying`; `onClick` → `startActiveUpdate()` (`store/updates.ts:275-282`), which opens the overlay and applies for the active target, or fans out through `applyEverythingUpdate()` when `hasMultipleUpdateTargets()`.
  - **"See what's new"** button (`variant="textStrong"`) — same render condition; `onClick` → `openUpdatesWindow()` → `openUpdateOverlayFor('backend' | 'client')`.
  - **"Release notes"** link-button (`variant="text"`, `ml-auto`, `ExternalLink` icon) — `href` `https://github.com/NousResearch/hermes-agent/releases` (`RELEASE_NOTES_URL`, `:24`); the click handler `preventDefault()`s and calls `window.hermesDesktop?.openExternal?.(RELEASE_NOTES_URL)` so it opens in the OS browser, not in the app.
  - **"Get the installer"** button (`bundleOutOfSyncAction`) — rendered only inside the amber banner when `version.bundleOutOfSync`; banner title **"App build out of date"** (`bundleOutOfSync`) and description **"The Hermes runtime was updated, but the desktop app itself is still an older build — new interface features (like Bot Mode) will be missing until it updates. Run the update below to rebuild the app. If that doesn't clear this warning, reinstall from the latest desktop installer."** (`bundleOutOfSyncDesc`); opens `https://hermes-agent.nousresearch.com/` (`INSTALLER_URL`, `:25`) via `openExternal`.
  - **"Automatic updates"** `ListRow` — non-interactive; description **"Hermes checks for updates automatically in the background and lets you know when one is ready."** (`automaticUpdatesDesc`), hint **"Branch `<branch>` · Commit `<sha7>`"** (`branchCommit`, both defaulting to the literal `unknown`).
  - `<UninstallSection />` renders below (documented with the uninstall entries).
- **Outputs / side effects:** `checkUpdates()` refreshes `$updateStatus` and can fire the update-ready toast; `startActiveUpdate()` opens the Updates overlay and begins an apply; the two link buttons open external URLs through the Electron `openExternal` bridge.
- **Config / env:** Reads the tracked branch/sha out of the update status (backed by `<userData>/updates.json`). No config keys of its own.
- **Edge cases / guards:** `Check now` is disabled for unsupported installs so the user cannot poll an install method that can never self-update. `behind === null` (shallow clone) is rendered by `updateReadyUnknown`, never as a number. External links always go through `openExternal` — an in-app navigation to GitHub would strand the user inside the app shell.
- **Rebuild notes:** One card that answers three questions — what am I running, is something waiting, when did we last look — with an explicit last-checked timestamp so silence is legible. A better version would show the changelog headline inline (instead of requiring the overlay), expose the tracked-branch picker here rather than only in the updates settings row, and mark whether the last check failed vs. never ran.

### First-run setup choice screen ("Set up Hermes Desktop")  `id: gapfill-desktop-main.install-overlay-setup-choice`
- **Surface:** Desktop app
- **Where:** Full-screen modal on the very first launch of Hermes Desktop, before anything else renders (`fixed inset-0 z-(--z-setup)` over `bg-background/90 backdrop-blur-md`, `apps/desktop/src/components/desktop-install-overlay.tsx:399-470`); mounted once per non-auxiliary window at `apps/desktop/src/app/contrib/wiring.tsx:1145` (`{!isAuxiliaryWindow() && <DesktopInstallOverlay />}`). Verbatim strings: heading **"Set up Hermes Desktop"** (`i18n: install.setupChoiceTitle`, `en.ts:2676`), subtitle **"Connect this app to a Hermes gateway you already run, or install Hermes locally on this computer."** (`i18n: install.setupChoiceDesc`, `en.ts:2677`); left card **"Connect to existing Hermes"** (`i18n: install.connectExistingTitle`, `en.ts:2679`) with **"Use a remote backend with a session token or browser sign-in. No local install will start."** (`i18n: install.connectExistingDesc`, `en.ts:2681`); right card **"Install Hermes locally"** (`i18n: install.installLocalTitle`, `en.ts:2682`) with **"Download Hermes, create its Python environment, and run the backend on this computer."** (`i18n: install.installLocalDesc`, `en.ts:2683`); footer line **"Will install to"** (`i18n: install.installTo`, `en.ts:2674`) followed by the monospace `activeRoot` path.
- **What it does:** Asks the user, once, whether this desktop app should install the Hermes Python backend on this machine or attach to a gateway that already exists somewhere else, and parks the boot until they answer.
- **How it works:** Electron main emits a `setup-choice` bootstrap event (`promptFirstRunSetupChoice(backend)`, `apps/desktop/electron/main.ts:1975-1982`) carrying `{ active: true, platform, activeRoot }` whenever the backend resolver returns the `bootstrap-needed` sentinel; the overlay folds it into its local snapshot (`applyEvent`, `desktop-install-overlay.tsx:181-196` — the branch clears `active`, `manifest`, `stages`, `error` and `unsupportedPlatform`, defaulting `platform` to `'unknown'` and `activeRoot` to `''`). `shouldShow` (`:373-389`) renders whenever `state.active || state.error || state.unsupportedPlatform || state.setupChoice`. Choosing **"Install Hermes locally"** calls `window.hermesDesktop.continueBootstrapLocal()` → IPC `hermes:bootstrap:continue-local` (`electron/preload.ts:476`, handler `electron/main.ts:14550-14555`, which logs `[bootstrap] local install selected by renderer; continuing first-launch bootstrap` and resolves the first-run gate with decision `'continue-local'`). Choosing **"Connect to existing Hermes"** sets local state `remoteOpen = true` (`:279`), which short-circuits the render to `<FirstRunRemoteForm onBack={() => setRemoteOpen(false)} />` (`:395-397`) — no IPC at all until the user applies. Transient click state lives in `localStart = { root, starting, error }` (`:352-362`) and is **keyed by the `activeRoot` it was produced under** (`forActiveRoot = localStart.root === activeRoot`), so a stale error from a previous root can never paint over a fresh choice; the code comment (`:340-351`) explains why deriving beats clearing in an effect.
- **Inputs / options:** Exactly two clickable cards and no other control: (1) card button **"Connect to existing Hermes"** (globe icon `Globe`, `lib/icons`); (2) card button **"Install Hermes locally"** (monitor icon `Monitor`, replaced by a spinning `Loader2` while `localStarting`), `disabled={localStarting}` with `disabled:cursor-wait disabled:opacity-60`. No keyboard shortcut, no close/escape affordance — the modal is not dismissible, matching the gate that is holding boot. The footer is text-only (**"Will install to"** + `<code>` path).
- **Outputs / side effects:** Local install → the first-run gate resolves and `runBootstrap` starts, replacing this screen with the staged progress screen. Connect existing → the remote form replaces this screen in place. Failure to reach the IPC entry point renders the destructive inline row described below.
- **Config / env:** No config keys. The path shown comes from `ACTIVE_HERMES_ROOT` on the main side (see `desktop-main.hermes-home` / `desktop-main.backend-resolution`).
- **Edge cases / guards:** Rendering the choice requires an Electron preload with `onBootstrapEvent`; without it the effect returns early (`:302-304`) and the app falls through to its normal onboarding. `getBootstrapState()` rejection is swallowed (older Electron build, `:314-318`). The card is disabled while a start is in flight so a double click cannot fire two bootstraps. Auxiliary windows never mount the overlay.
- **Rebuild notes:** Gate the first launch on one binary question, render it from a *snapshot + event stream* so a devtools reload recovers the same screen, and keep the "connect remote" branch entirely client-side until the user applies, so backing out still leaves a clean local install possible. A better version would remember a previously used gateway URL, offer LAN/mDNS discovery of running Hermes instances as a third card, and let the user pick the install root here instead of only reporting it.

### "Local installation could not start." inline error  `id: gapfill-desktop-main.install-local-start-unavailable`
- **Surface:** Desktop app
- **Where:** Setup-choice screen, destructive inline row under the two cards (`AlertCircle` glyph + message, `desktop-install-overlay.tsx:455-460`). Verbatim: **"Local installation could not start. Restart Hermes Desktop and try again."** (`i18n: install.localStartUnavailable`, `en.ts:2684`).
- **What it does:** Tells the user that the desktop app cannot begin a local install because its own IPC bridge is missing, and that relaunching is the fix.
- **How it works:** The **"Install Hermes locally"** click handler throws `new Error(copy.localStartUnavailable)` when `window.hermesDesktop` is absent or `continueBootstrapLocal` is not a function (`:431-435`); the `catch` stores `{ root: activeRoot, starting: false, error: errorMessage(err) }` (`:439-441`). `errorMessage()` (`:161-163`) renders an `Error` as its `.message`, anything else as `String(err || 'Unknown error')` — so a rejected `continueBootstrapLocal()` surfaces the main-process message in the same row.
- **Inputs / options:** n/a (read-only row; the user retries by clicking the card again or relaunching).
- **Outputs / side effects:** Renderer-local state only; nothing is written to disk and the boot gate stays parked.

- **Outputs / side effects:** Up to N toasts (the stack keeps the newest 4); an `hermes update` dispatched on every eligible registered instance; the Updates overlay opened on `'backend'` and then `'client'`; ultimately an app relaunch/hand-off when the client itself updates.
- **Config / env:** n/a
- **Edge cases / guards:** Rows are reported individually so one unreachable box never wedges the batch; Hermes Cloud rows come back `skipped` with their platform-managed reason. The active backend and `local` are excluded from the fan-out because steps 1 and 3 handle them. `$updateEverything.running` is the guard a UI can use to disable the affordance while a fan-out is live. Regression coverage: `apps/desktop/src/store/updates.test.ts:419-565` (ordering, exclusion list, singleton behaviour).
- **Rebuild notes:** Sequence a fleet update as active-backend → others → self, exclude the rows you handle yourself, and report per row rather than as one aggregate success/failure. A better version would render the fan-out as a single grouped progress panel (one row per instance with a live state) instead of N transient toasts, and would retry a failed row without re-dispatching the successful ones.

# Gap-fill — Desktop Settings: Appearance rows, the Pet section, Advanced device prefs, Quick Entry, credential fields and the Connections registry

This shard closes the uncovered i18n strings of five desktop **Settings** areas that no sibling shard
documented: **Settings → Appearance** (chat backdrop, message-reaction switch, floating composer, vibe
hearts, inline embeds, tool-call display, the theme importer copy and per-theme removal), the embedded
**Pet (petdex)** section of that page, the two device-local **Advanced** toggles (keep-awake, F12 block)
plus the Quick Entry rows rendered beside them, the shared **credential field / env-var actions** copy,
and the whole **Registered gateways** (connections registry v2) section of Settings → Gateways.
Deliberately left to sibling shards: config-schema-driven field rows and the Settings frame itself
(`desktop-settings.md`), the chat-side tapback/embed/composer-popout runtime (`desktop-b.md`), the
Electron-main machinery for Quick Entry, keep-awake, updates, the connections registry file, SSH and the
fleet fan-out (`desktop-main.md`), the Cmd-K palette pages themselves (`desktop-a.md`), and the About
page's updates card (`gapfill-desktop-main-r0.md`).

### Chat Backdrop  `id: gapfill-desktop-settings-1.appearance-backdrop`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, row titled **"Chat Backdrop"** (`i18n: settings.appearance.backdropTitle`) with the description **"The faint statue image behind the conversation."** (`i18n: settings.appearance.backdropDesc`). Rendered at `apps/desktop/src/app/settings/appearance-settings.tsx:700-717`; the row's DOM id is `setting-field-appearance.backdrop` (`appearanceSettingElementId(APPEARANCE_SETTING_IDS.backdrop)`, ids table at `apps/desktop/src/app/settings/settings-search.ts:13-22`). Also reachable from the settings/command search as the catalog entry with the same label + description and keywords `background`, `blur` (`apps/desktop/src/app/settings/use-settings-search.ts:154-162`).
- **What it does:** Turns on a very faint statue photograph painted behind the whole chat transcript.
- **How it works:** A single boolean atom `$backdrop` (`apps/desktop/src/store/backdrop.ts:8`), seeded with `storedBoolean('hermes.desktop.backdrop.v1', false)` and mirrored back on every change through `persistBoolean` — device-local, never config.yaml, never the gateway. `setBackdrop(on)` (`backdrop.ts:12`) is the only writer. The consumer is `<Backdrop />` (`apps/desktop/src/components/Backdrop.tsx`): when off it renders `null`; when on it renders `<div aria-hidden className="pointer-events-none absolute inset-0 z-2 opacity-[0.025] mix-blend-difference">` wrapping `<img alt="" fetchPriority="low" src={assetPath('ds-assets/filler-bg0.jpg')} className="h-[160dvh] w-auto min-w-dvw object-cover object-left-top [filter:invert(var(--backdrop-invert-mul,1))]">`. So the image is 2.5 % opaque, difference-blended, inverted by the theme variable `--backdrop-invert-mul`, and 1.6x the viewport height so it never tiles.
- **Inputs / options:** One `SegmentedControl` with exactly two options — **"Off"** (id `off`, `i18n: common.off`) and **"On"** (id `on`, `i18n: common.on`); selecting fires `triggerHaptic('selection')` then `setBackdrop(id === 'on')`.
- **Outputs / side effects:** `localStorage['hermes.desktop.backdrop.v1']` = `"true"` / `"false"`; the image layer appears/disappears immediately in every open window of this device that reads the atom.
- **Config / env:** No config key, no env var — purely a renderer preference.
- **Edge cases / guards:** Default is **off**. `persistBoolean`/`storedBoolean` swallow storage exceptions (private mode), in which case the choice lasts only for the session. Because the layer is `absolute inset-0` inside the chat column with `pointer-events-none`, it can never intercept clicks or scroll.
- **Rebuild notes:** One persisted boolean → one aria-hidden, pointer-events-none image layer at ~2.5 % opacity behind the transcript, blended so it works in both themes from a single asset. A better version would let the user pick or drop in their own image (and a per-profile choice), and would swap to a lighter-weight CSS gradient when the machine reports reduced motion / low power.

### Message Reactions (Appearance switch)  `id: gapfill-desktop-settings-1.appearance-reactions`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, row **"Message Reactions"** (`i18n: settings.appearance.reactionsTitle`) with the description **"iMessage-style emoji tapbacks — react to messages, and Hermes can react to yours."** (`i18n: settings.appearance.reactionsDesc`). `apps/desktop/src/app/settings/appearance-settings.tsx:745-761`.
- **What it does:** Master switch for tapbacks: it shows/hides every reaction affordance in the transcript **and** tells the backend whether the agent may use its own `react_to_message` tool.
- **How it works:** `$reactionsEnabled` (`apps/desktop/src/store/reactions-enabled.ts:21`) is seeded from `storedString('hermes.desktop.reactions.v1') === 'on'` — **off by default**, because reactions add affordances to every message row and hand the agent a new tool (module comment `reactions-enabled.ts:1-11`). The store uses `.listen()` (fire on CHANGE only), never `.subscribe()`, so app startup can neither write config nor clobber another window's setting (comment `:28-30`). On change it (1) persists `'on'`/`'off'` and (2) mirrors into the gateway with `activeGateway()?.request('config.set', { key: 'display.message_reactions', value: enabled ? 'true' : 'false' })`, catching failures silently when the gateway is not yet connected. The backend uses `display.message_reactions` to gate the agent's `react_to_message` tool and the model-context annotation. The transcript-side behaviour (quick tapback row, double-click gesture, one-reaction-per-author rule) is documented separately as `desktop-b.thread-reactions`.
- **Inputs / options:** `SegmentedControl` with **"Off"** (`common.off`) / **"On"** (`common.on`); `triggerHaptic('selection')` then `setReactionsEnabled(id === 'on')`.
- **Outputs / side effects:** `localStorage['hermes.desktop.reactions.v1']`; a `config.set` RPC writing `display.message_reactions` on the connected gateway.
- **Config / env:** `display.message_reactions` (gateway config, written by this toggle).
- **Edge cases / guards:** Turning it **off gates the UI only** — reactions already persisted still render, so a tapback set earlier does not vanish from history (comment `reactions-enabled.ts:9-11`). A `config.set` that fails (no gateway yet) is swallowed; the next toggle re-sends it.
- **Rebuild notes:** One renderer-owned boolean that both hides the affordances and flips the server-side tool gate, written on change only. A better version would make it per-profile rather than per-device, and would ask the backend to confirm the mirrored config value rather than fire-and-forget.

### Floating Composer (composer pop-out gestures)  `id: gapfill-desktop-settings-1.appearance-composer-popout`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, `ToggleRow` labelled **"Floating Composer"** (`i18n: settings.appearance.composerPopoutTitle`) with the description **"Allow dragging the composer out of its dock. Turn this off to keep it locked at the bottom."** (`i18n: settings.appearance.composerPopoutDesc`). `apps/desktop/src/app/settings/appearance-settings.tsx:738-743`.
- **What it does:** Enables or disables the drag gesture that peels the composer off its dock into a floating bar; with it off the composer is permanently docked at the bottom.
- **How it works:** `$composerPopoutGesturesEnabled` / `setComposerPopoutGesturesEnabled` from `apps/desktop/src/store/composer-popout.ts`, persisted under `localStorage['hermes.desktop.composerPopout.gesturesEnabled']` (`POPOUT_GESTURES_ENABLED_STORAGE_KEY`, read at load with `storedBoolean(..., true)` → **on by default**). The same module owns the per-zone pop-out state under `hermes.desktop.composerPopout.zones.v1` (`{ poppedOut, position: { bottom, right } }` per layout zone, default `{ bottom: 24, right: 24 }`, `POPOUT_WIDTH_REM = 19.5`) and migrates the pre-zone keys `hermes.desktop.composerPopout.enabled` / `.position` by seeding the first zone the user touches (`legacySeed`). The drag/dock behaviour itself is `desktop-b.composer-popout`.
- **Inputs / options:** One `Switch` (`ToggleRow` renders `<Switch aria-label="Floating Composer">`), on/off; `triggerHaptic('selection')` fires inside `ToggleRow` before `setComposerPopoutGesturesEnabled(on)`.
- **Outputs / side effects:** `localStorage['hermes.desktop.composerPopout.gesturesEnabled']`; the composer's transparent grab margin stops responding to drags/double-clicks when off.
- **Config / env:** n/a (device-local).
- **Edge cases / guards:** Default **true** (the gesture ships enabled). Secondary windows never allow pop-out regardless of this toggle (`popoutAllowed`). Turning the gesture off does not force an already-floating composer home — the stored zone state stays until the user docks it.
- **Rebuild notes:** Keep the *gesture* flag separate from the *position* state so disabling the affordance does not destroy where the user had put the box. A better version would offer a third state ("floating only when I ask") and a keyboard command to dock/undock without a drag.

### Vibe Hearts  `id: gapfill-desktop-settings-1.appearance-vibe-hearts`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, row **"Vibe Hearts"** (`i18n: settings.appearance.vibeHeartsTitle`, `apps/desktop/src/app/settings/appearance-settings.tsx:815-831`) with the description **"Floating hearts when you say thanks, ily, good bot, or send a heart. Separate from Message Reactions above."** (`i18n: settings.appearance.vibeHeartsDesc`).
- **What it does:** Turns the TikTok-style burst of floating pink pixel hearts on or off — the animation that plays when a user message reads as affection.
- **How it works:** `$vibeHeartsEnabled` (`apps/desktop/src/store/vibe-hearts-enabled.ts:18`) = `storedString('hermes.desktop.vibeHearts.v1') !== 'off'`, i.e. **on by default** so existing installs keep the pre-toggle always-on behaviour; `.listen()` persists `'on'`/`'off'`. The consumer is `burstVibeHearts(count?)` (`apps/desktop/src/components/chat/vibe-hearts.tsx:62`), fired by the core `reaction` event: it returns immediately when the atom is false, otherwise it routes the burst — pet popped out → `forwardPetReaction('vibe')` into the overlay window plus `flashPetActivity({ celebrate: true })`; pet in-window → play here on the pet plus celebrate; no pet → play from the composer. The visual is a `ParticleField` skinned with a 14x12 `crispEdges` pixel-heart SVG in `#ff9ec4`; composer preset `COMPOSER_HEART_CONFIG = { count: 12, size: [6,13], rise: [6.75,15.75], duration: [320,700] }`, pet preset `PET_HEART_CONFIG = { count: 10, spawnWindowMs: 450, size: [6,12], rise: [98,118], duration: [480,880], swayAmp: [5,14], bank: [6,14] }`.
- **Inputs / options:** `SegmentedControl` **"Off"** (`common.off`) / **"On"** (`common.on`) → `triggerHaptic('selection')`, `setVibeHeartsEnabled(id === 'on')`.
- **Outputs / side effects:** `localStorage['hermes.desktop.vibeHearts.v1']`; no network, no config write.
- **Config / env:** n/a.
- **Edge cases / guards:** Deliberately **distinct from Message Reactions** — the description says so, because both are emoji-shaped affection surfaces. Absent key or any value other than `"off"` counts as on. `playVibeHearts` is exported so the popped-out pet overlay window can play the same burst off the mirrored signal.
- **Rebuild notes:** Gate the emitter at the single entry point (`burstVibeHearts`) rather than at each render site, and mirror the signal to any detached overlay window. A better version would let the user choose the glyph/colour and would respect `prefers-reduced-motion` automatically.

### Inline Embeds  `id: gapfill-desktop-settings-1.appearance-embeds`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, row **"Inline Embeds"** (`i18n: settings.appearance.embedsTitle`; catalog `apps/desktop/src/i18n/en.ts:602`, rendered `apps/desktop/src/app/settings/appearance-settings.tsx:867-895`, DOM id `setting-field-appearance.embeds`) with the description **"Rich previews load from third-party sites (YouTube, X, …). Ask shows a placeholder until you allow each one; Always loads them automatically; Off keeps plain links."** (`i18n: settings.appearance.embedsDesc`). Search catalog entry with the same label/description and keywords `external content`, `privacy` (`use-settings-search.ts:181-189`).
- **What it does:** Chooses the privacy policy for third-party rich previews in the transcript — ask each time, always load, or never load — and clears any per-service "always allow" grants.
- **How it works:** Two persisted atoms in `apps/desktop/src/store/embed-consent.ts`: `$embedMode` = `persistentAtom<EmbedMode>('hermes.desktop.embed-mode', 'ask', modeCodec)` where the codec coerces anything that is not `'always'`/`'off'` back to `'ask'`; and `$embedAllowed` = `persistentAtom<string[]>('hermes.desktop.embed-allowed', [], Codecs.stringArray)` holding provider slugs (`youtube`, `twitter`, …). Writers: `setEmbedMode(mode)`, `allowProvider(provider)` (append-if-absent), `clearEmbedAllowed()`. Consumer `UrlEmbed` (`apps/desktop/src/components/assistant-ui/embeds/url-embed.tsx:47-51`): mode `off` renders a `PrettyLink` instead of an embed; otherwise `consented = mode === 'always' || loaded || allowed.includes(descriptor.provider)` decides between the lazy renderer (`SocialEmbedRenderer` for tweets/Instagram, `YouTubeEmbedRenderer`, `SpotifyEmbedRenderer`, else `FrameEmbedRenderer`) and the consent placeholder. The placeholder `EmbedFacade` (`embeds/embed-consent.tsx:15`) is sized to the embed's own footprint (`aspectRatio` or `height ?? 320`) so consenting causes **no layout shift**, and renders a `SplitButton` whose primary action is **"Load `<service>`"** (id `once`) and whose caret action is **"Always allow `<service>`"** (id `always`, calls `allowProvider`), above the resolved host name (`x.com` is substituted for `twitter.com` links). The whole gate is client-side and never touches the gateway or config.yaml (comment `embed-consent.ts:2-7`).
- **Inputs / options:** A three-way `SegmentedControl` — **"Ask"** (`settings.appearance.embedsAsk`, id `ask`), **"Always"** (`embedsAlways`, id `always`), **"Off"** (`embedsOff`, id `off`) → `triggerHaptic('selection')` then `setEmbedMode(id)`. Directly under it, rendered only while `embedAllowed.length > 0`, a text button **"Reset `<n>` allowed service"** / **"Reset `<n>` allowed services"** (`i18n: settings.appearance.embedsReset`, singular/plural on the count) → `clearEmbedAllowed()`. In the transcript itself: the split button's **"Load `<service>`"** and **"Always allow `<service>`"**.
- **Outputs / side effects:** `localStorage['hermes.desktop.embed-mode']` and `['hermes.desktop.embed-allowed']`; embeds start (or stop) issuing third-party requests that expose IP, referrer and cookies.
- **Config / env:** n/a — deliberately renderer-only, since the renderer is what makes the request.
- **Edge cases / guards:** Default is **"Ask"** (placeholder first). A per-embed "Load" grant lives in component state only (`loaded`), so it does not survive a reload; only "Always allow" is persisted. `RichBoundary` wraps every renderer with an `EmbedFail` fallback keyed on the descriptor id. Setting **Off** downgrades to a plain link, it does not hide the URL.
- **Rebuild notes:** Model embeds as consent-gated resources: a global mode, a persisted per-provider allow-list, a footprint-accurate placeholder, and a split control offering once-vs-always. A better version would show what the provider will learn (host, cookies) inside the placeholder and offer a proxy/no-cookie render path so "Always" is not the only convenient option.

### Tool Call Display (Product / Technical)  `id: gapfill-desktop-settings-1.appearance-tool-view`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance**, row **"Tool Call Display"** (`i18n: settings.appearance.toolViewTitle`) described as **"Product hides raw tool payloads; Technical shows full input/output."** (`i18n: settings.appearance.toolViewDesc`), rendered at `apps/desktop/src/app/settings/appearance-settings.tsx:833-847` with the option labels built at `:424-427`. The catalog also carries a longer description for each mode — **"Human-friendly tool activity with concise summaries."** (`i18n: settings.appearance.productDesc`, `apps/desktop/src/i18n/en.ts:610`) for **"Product"** (`settings.appearance.product`, option label rendered at `appearance-settings.tsx:425`) and **"Include raw tool args/results and low-level details."** (`i18n: settings.appearance.technicalDesc`, `en.ts:612`) for **"Technical"** (`settings.appearance.technical`, option label rendered at `appearance-settings.tsx:426`).
- **What it does:** Switches every tool-call card in the transcript between a summarised product view and a raw technical view.
- **How it works:** `$toolViewMode` (`apps/desktop/src/store/tool-view.ts:14`) is `'technical'` when `storedBoolean('hermes.desktop.toolView.technical', false)` is true, else `'product'` — i.e. **Product by default**; `$toolViewMode.subscribe` persists `mode === 'technical'` back to that key. The same module owns per-card disclosure memory: `$toolDisclosureStates` under `hermes.desktop.toolDisclosure.v1`, capped at `MAX_DISCLOSURE_STATES = 240` entries, with `$toolDisclosureOpen(id)` and `$anyToolDisclosureOpen(ids)` computed atoms (cached per id / per joined-id key) so toggling one disclosure only re-renders the runs whose answer changed.
- **Inputs / options:** `SegmentedControl` built from `toolOptions = [{ id: 'product', label: a.product }, { id: 'technical', label: a.technical }]` — visible labels **"Product"** and **"Technical"**; selecting fires `triggerHaptic('selection')` then `setToolViewMode(id)`. The two per-mode sentences (`productDesc`, `technicalDesc`) are **not** rendered by this row in v2026.8.31 — the row shows the single combined `toolViewDesc` instead — but they remain in every locale catalog (`en.ts:610`/`:612` plus `ar.ts`, `ja.ts`, `zh.ts`, `zh-hant.ts`) and are what a mode-detail UI would render.
- **Outputs / side effects:** `localStorage['hermes.desktop.toolView.technical']`; every tool card in every open transcript re-renders in the chosen mode.
- **Config / env:** n/a.
- **Edge cases / guards:** The disclosure map is trimmed to the newest 240 ids so a long-lived install cannot grow the key unboundedly. Reading `storedBoolean` under a blocked-storage browser context returns the default (`product`).
- **Rebuild notes:** One persisted enum plus a bounded per-card disclosure map, both device-local; expose the mode as a computed atom so cards subscribe rather than prop-drill. A better version would allow per-tool overrides ("always show diffs raw") and would keep the raw payload one keystroke away in Product mode instead of behind a global switch.

### Install from VS Code (theme importer copy)  `id: gapfill-desktop-settings-1.appearance-install-theme-copy`
- **Surface:** Desktop app
- **Where:** Catalog block `settings.appearance.install*` (`apps/desktop/src/i18n/en.ts:616-625`): title **"Install from VS Code"** (`installTitle`), description **"Paste a Marketplace extension id (e.g. dracula-theme.theme-dracula) to convert its color theme into a desktop palette."** (`installDesc`), input placeholder **"publisher.extension"** (`installPlaceholder`), button **"Install"** (`installButton`), busy label **"Installing…"** (`installing`), failure **"Could not install that theme."** (`installError`), success **"Installed `<name>`."** (`installed`), and the badge **"Imported"** (`importedBadge`). In v2026.8.31 the **live** UI for this capability is (a) the Appearance page's single search box — placeholder **"Search your themes or the VS Code Marketplace…"** (a literal, not an i18n key, `apps/desktop/src/app/settings/appearance-settings.tsx:476`) — whose Marketplace half renders under the heading **"From the VS Code Marketplace"** (`:186`), and (b) the Cmd-K page **"Install theme…"** (`apps/desktop/src/app/command-palette/marketplace-theme-page.tsx`, copy under `i18n: commandCenter.installTheme`, install failure rendered at `marketplace-theme-page.tsx:98`).
- **What it does:** Converts a VS Code Marketplace colour theme into a desktop palette and activates it, either by searching from Settings → Appearance or from the command palette.
- **How it works:** `installVscodeThemeFromMarketplace(id)` (`apps/desktop/src/themes/install.ts:76`) validates the id against `MARKETPLACE_ID_RE = /^[\w-]+\.[\w-]+$/`, calls the Electron bridge `window.hermesDesktop.themes.fetchMarketplace(id)` (main-side `electron/vscode-marketplace.ts`), then `buildThemeFromMarketplace(result)` → `parseVscodeTheme` + `convertVscodeColorTheme(raw, { label, source: extensionId })` + `vscodeThemeSlug`, and persists the result as a user theme. Searching uses `window.hermesDesktop.themes.searchMarketplace(query)` behind React-Query (`queryKey ['marketplace-themes-settings', debounced]` in Settings, `['marketplace-themes', debouncedSearch]` in the palette; `staleTime: 5 * 60 * 1000`; query debounced 300 ms via `useDebounced`). In both surfaces `select(item)` first checks `$marketplaceInstalls` — an already-imported extension is simply **re-activated**, never re-downloaded (comment `appearance-settings.tsx:145`) — otherwise `install(item)` runs with a single-flight `installingId` guard and, on success, `triggerHaptic('crisp')` then `setTheme(theme.name)` / `onPickTheme(theme.name)`.
- **Inputs / options:** In Settings the row is a text input (placeholder **"Search your themes or the VS Code Marketplace…"**) plus result cards showing display name, publisher and **"`<n>` installs"** (`commandCenter.installTheme.installs`), each ending in a spinner while installing, a green check when already installed, or a download glyph; buttons are disabled while another install runs (`disabled={Boolean(installingId) && !busy}`). Status rows use `commandCenter.installTheme`: **"Searching the Marketplace..."** (`loading`), **"Could not reach the Marketplace."** (`error`), **"No matching themes."** (`empty`); the Cmd-K page adds the per-row states **"Install"** (`install`), **"Installing..."** (`installing`), **"Installed"** (`installed`), the page titles **"Install theme…"** (`title`) / **"Install theme"** (`pageTitle`) and the placeholder **"Search the VS Code Marketplace..."** (`placeholder`). When no installed theme matches the query the grid prints the literal **"No installed themes match "`<query>`"."** (`appearance-settings.tsx:488`).
- **Outputs / side effects:** A new user theme persisted client-side (`themes/user-themes.ts`, tracked in `$marketplaceInstalls` keyed by extension id), the theme activated, and a network fetch to the Marketplace through the main process.
- **Config / env:** n/a. The theme choice is saved per profile — the Appearance page prints **"Saved for the `<profile>` profile — each profile keeps its own theme."** (`i18n: settings.appearance.themeProfileNote`) whenever more than one profile exists.
- **Edge cases / guards:** The `installTitle` / `installDesc` / `installPlaceholder` / `installButton` / `installError` / `installed` / `importedBadge` strings are **catalog-resident but unrendered** in this build — no `.tsx` reads `t.settings.appearance.installTitle` (the only `installTitle` consumer in the app is the unrelated `assistant-ui/mcp-setup-tool.tsx:397`) — so a reimplementation that restores a paste-an-id form has its copy ready. An install error falls back to `copy.error` when the thrown error has no message. Search is skipped entirely while the debounced query is empty (`enabled: debounced.length > 0`).
- **Rebuild notes:** Fetch the extension package in the main process (renderer CSP cannot reach the Marketplace), convert VS Code token colours into the app's palette shape in the renderer, key installs by `publisher.extension`, and re-activate rather than re-download. A better version would preview the palette before installing and would re-check upstream for theme updates.

### Remove theme (imported palettes)  `id: gapfill-desktop-settings-1.appearance-remove-theme`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance → Theme** grid. A trash button pinned to the top-right of each *imported* theme card, with both `aria-label` and `title` set to **"Remove theme"** (`i18n: settings.appearance.removeTheme`, `apps/desktop/src/app/settings/appearance-settings.tsx:519` and `:530`).
- **What it does:** Deletes a locally imported (VS Code / user) palette from this device.
- **How it works:** The card renders the button only when `isUserTheme(theme.name)` is true (`appearance-settings.tsx:495`) — built-in palettes have no delete affordance. Clicking runs `triggerHaptic('crisp')`, `removeUserTheme(theme.name)` (`apps/desktop/src/themes/user-themes.ts`), and — when the removed theme was the active one — calls `setTheme(theme.name)` again so the theme resolver **re-normalises off the now-missing skin back to the default** (comment `:525`).
- **Inputs / options:** One icon button per removable card (`Trash2`, `size-3.5`), revealed on hover or keyboard focus (`opacity-0 … focus-visible:opacity-100 group-hover:opacity-100`). No confirmation dialog.
- **Outputs / side effects:** The user theme is dropped from persisted storage and from `$marketplaceInstalls`; the grid re-renders one card shorter; an active removed theme falls back to the default palette.
- **Config / env:** n/a.
- **Edge cases / guards:** Only imported themes are removable; the built-ins cannot be deleted. Removal is immediate and irreversible from the UI — recovery means re-installing the extension id. The theme grid lives in a fixed `max-h-96 overflow-y-auto` scroll area so removing a card never reflows the page.
- **Rebuild notes:** Mark user-supplied themes distinctly (`isUserTheme`) and re-resolve the active theme after deletion so the app cannot end up pointing at a missing palette. A better version would soft-delete with an undo toast and would show which profile(s) currently use the theme before removing it.

### Pet — "Choose a pet" gallery picker  `id: gapfill-desktop-settings-1.pet-choose`
- **Surface:** Desktop app
- **Where:** **Settings → Appearance → Pet** (section heading **"Pet"**, `i18n: settings.appearance.pet.title`, `PawPrint` icon, rendered by `<PetSettings />` at the foot of the Appearance page, `apps/desktop/src/app/settings/appearance-settings.tsx:899-901`). The row title is **"Choose a pet"** (`i18n: settings.appearance.pet.chooseTitle`, `apps/desktop/src/app/settings/pet-settings.tsx:258`) with the description **"Picking one installs it (if needed) and makes it active."** (`i18n: settings.appearance.pet.chooseDesc`, `:255`). Section intro: **"Adopt an animated petdex mascot that floats over the app and reacts to what Hermes is doing — running while tools execute, celebrating on success, sulking on errors."** (`pet.intro`).
- **What it does:** Lists the petdex catalog plus your own pets, and adopting one installs it if needed and makes it the live floating mascot.
- **How it works:** `PetSettings()` (`pet-settings.tsx:49`) is a thin view over the shared `apps/desktop/src/store/pet-gallery.ts` store, so the gallery is fetched once and cached and adopt/toggle/remove patch local state instead of re-pulling (module comment `:42-48`). On mount (and whenever `$gatewayState === 'open'`) it calls `loadPetGallery(requestGateway)`, a **two-phase** load (`pet-gallery.ts:115-175`): phase 1 `pet.gallery { localOnly: true }` + `syncInfo()` paints the user's own/generated pets instantly; phase 2 merges the full remote petdex manifest via `pet.gallery` in the background, and a slow or failed manifest simply leaves the local-only list. `syncInfo` prefers `pet.info.meta` and falls back to `pet.info` when the backend lacks the newer RPC. Selecting a card calls `adoptPet(request, slug, copy.adoptFailed(slug))` → RPC `pet.select {slug}` and patches `{enabled: true, active: slug, pets[slug].installed = true}` optimistically. Thumbnails come from `loadPetThumb` → `pet.thumb {slug, url}` returning a data URI, memoised in a module-level `thumbCache`. The list is ranked by `rankedGalleryPets(gallery, query)` and capped at `RENDER_CAP = 60` because the catalog is thousands of entries (comment `:111`).
- **Inputs / options:**
  - Search input, placeholder **"Search pets…"** (`pet.searchPlaceholder`), `spellCheck={false}`.

  - One card per pet: thumbnail, display name, the badge **"Generated"** (`pet.generatedTag`) for locally generated pets, and a sub-line `slug` + **" · installed"** (`pet.installedTag`) when installed. Clicking adopts; the card is disabled while `busySlug === pet.slug` and shows a spinner.
  - Hover/focus actions on a card (icon buttons with `Tip` tooltips, `PetAction`): **"Rename `<name>`"** (`pet.rename`, `Pencil`, generated pets only), **"Export `<name>`"** (`pet.exportPet`, `Download`, generated pets only), and **"Delete `<name>`"** (`pet.delete`) for generated pets or **"Uninstall `<name>`"** (`pet.uninstall`) for petdex pets (`Trash2`, `danger`).
  - Rename dialog: title **"Rename pet"** (`pet.renameTitle`), input placeholder **"Name your pet"** (`pet.renamePlaceholder`), **"Save"** (`pet.renameSave`, disabled while the field is blank) and **"Cancel"** (`common.cancel`); **Enter** saves.
  - Status line under the grid: **"`<n>` pet."** / **"`<n>` pets."** (`pet.count`) or, when the ranked list exceeds the cap, **"Showing `<cap>` of `<total>` — type to narrow it down."** (`pet.countCapped`).
- **Outputs / side effects:** Gateway RPCs `pet.gallery`, `pet.info` / `pet.info.meta`, `pet.thumb`, `pet.select`, `pet.disable`, plus rename/export/remove calls; the floating mascot repaints within a couple of seconds because it polls `pet.info`.
- **Config / env:** Pets are per-profile on the gateway; `resetPetGallery()` clears the cache on a profile switch. The roam preference is device-local (see the Roam entry).
- **Edge cases / guards:** A backend that predates pets makes the RPC come back "missing method": status flips to `stale` and the section shows **"Pets need a quick restart — the running app started before this feature was added. Quit and reopen Hermes, then come back here."** (`pet.restartHint`). First load renders six skeleton cards rather than flashing the unreachable copy (comment `:143-145`). The grid lives in a fixed `h-72 overflow-y-auto` box so filtering never resizes the page, and the status line is always present (`min-h-4`) so it cannot shift layout. Failures surface as `pet.adoptFailed` / `pet.uninstallFailed` / `pet.renameFailed` / `pet.exportFailed`, each interpolating the slug.
- **Rebuild notes:** Split the catalog fetch into local-first + remote-merge, memoise thumbnails, cap the rendered rows and rank by query, and make every mutation optimistic with a named failure string. A better version would paginate the remote catalog server-side and preview the sprite animation on hover instead of a static thumb.

### Credential save guards (empty value, save failure)  `id: gapfill-desktop-settings-1.credential-save-guards`
- **Surface:** Desktop app
- **Where:** `useEnvCredentials(...).saveValue(key, value)` (`apps/desktop/src/app/settings/env-credentials.tsx:122-145`) — the direct-save API for a key form that owns its own input, used by the **Settings → API Keys / env credentials** surfaces. Returned messages: **"Enter a value first."** (`i18n: settings.credentials.enterValueFirst`, `:126`) and **"Could not save credential."** (`i18n: settings.credentials.couldNotSave`, `:141`).
- **What it does:** Saves a known credential value in one call and hands back a `{ok, message}` result so the caller can print an inline error instead of only toasting.
- **How it works:** `saveValue` trims the input; an empty result returns `{ message: credentials.enterValueFirst, ok: false }` **without any network call**. Otherwise it sets `saving`, awaits `setEnvVar(key, trimmed, profile)`, optimistically patches `{is_set: true, redacted_value: redactedValue(trimmed)}`, clears the local edit/reveal state for that key, raises the success toast `{ title: toolsets.savedTitle, message: toolsets.savedMessage(key) }`, and returns `{ ok: true }`. On a throw it still raises `notifyError(err, toolsets.failedSave(key))` **and** returns `{ message: err instanceof Error ? err.message : credentials.couldNotSave, ok: false }` — so the caller gets the concrete provider error when there is one and this generic sentence when there is not. `finally` always clears `saving`.
- **Inputs / options:** `key` (env var name) and `value` (raw string, trimmed by the function).
- **Outputs / side effects:** `setEnvVar` on the scoped profile; a success or failure toast; the returned result object.
- **Config / env:** Same profile scoping as the credential field (`useEnvCredentials(profile?)`, `undefined` = the app's active profile; an explicit `null` is deliberately never passed because the API helpers read `null` as "target the primary/default backend", comment `env-credentials.tsx:44-48`).
- **Edge cases / guards:** In v2026.8.31 `saveValue` is exported by the hook but has **no caller in the shipped tree** (grep finds only its definition and its type) — it is the onboarding-style key-form path, so these two strings are dormant-but-live API surface rather than dead copy. Note the asymmetry with `handleSave`, which returns nothing and only toasts.
- **Rebuild notes:** Give the credential store two save paths — a toast-only one for inline row editing and a result-returning one for forms that own their layout — and validate emptiness before touching the network. A better version would return a typed error (`invalid_key`, `unauthorized`, `network`) so callers can style the failure instead of matching on strings.

- **Inputs / options:** Up to four kind buttons plus two conditional hints below the description: **"Local is unavailable: the managed local connection already exists (there is only ever one)."** (`settings.connections.localAddHint`, shown while creating when `hasLocal`) and **"Tip: signing in under Hermes Cloud above discovers your agents automatically — use this form only to register a known instance URL by hand."** (`settings.connections.cloudAddHint`, shown while creating with `kind === 'cloud'`).
- **Outputs / side effects:** Changes which field rows the editor renders (URL + auth + headers for remote/cloud, host for ssh, nothing extra for local).
- **Config / env:** n/a.
- **Edge cases / guards:** `hasLocal` is computed from the registry (`:268`) and mirrors the main-process rule that there is at most one `local` entry ever; the same rule is enforced again in `findDuplicateConnection` and once more in main's `normalizeConnectionInput`, so a crafted payload cannot slip past the UI (comment `:254-255`).
- **Rebuild notes:** Make the kind immutable after creation (its identity fields differ per kind), show the kind's meaning as prose rather than expecting the label to carry it, and enforce singleton kinds in the UI *and* the writer. A better version would auto-detect the kind from a pasted address (an ssh URL, an https URL, a cloud agent id).

### Connection editor — Name field  `id: gapfill-desktop-settings-1.connection-editor-label`
- **Surface:** Desktop app
- **Where:** Connection editor row titled **"Name"** (`i18n: settings.connections.labelTitle`) with the description **"Required. Shown everywhere this instance appears; must be unique (e.g. "Homelab", "Work laptop")."** (`i18n: settings.connections.labelDesc`, `apps/desktop/src/app/settings/connections-registry.tsx:791`) and the input placeholder **"Homelab"** (`labelPlaceholder`).

- **How it works:** Plain controlled `Input` writing `editor.label`. The Save button is `disabled={saving || !editor.label.trim()}` (`:951`), which is how "Required" is enforced. Uniqueness is not enforced on the label itself but on the connection's identity: `findDuplicateConnection(editor, connections)` (`:144-184`) rejects a second `local`, a `remote`/`cloud` whose `normalizeGatewayUrl` (trim → drop trailing slashes → lowercase) matches an existing one, or an `ssh` whose `sshCompositeKey` (`user@host:port` with the default port `22` made explicit, so `box` and `box:22` collide) **and** trimmed `remoteProfile` match. - **Outputs / side effects:** `payload.label` on save.
- **Config / env:** n/a.
- **Edge cases / guards:** A whitespace-only name keeps Save disabled. The label is used as the toast title for per-row Test and fan-out results, which is why the copy insists on uniqueness even though nothing rejects a duplicate *name*.
- **Rebuild notes:** Gate Save on a trimmed non-empty name, and enforce duplicate rules on the identity tuple (kind + normalised address + profile) rather than the display name — in the UI and again in the writer. A better version would warn about duplicate *labels* too, since every toast and menu identifies a gateway by name.

### Connection editor — address fields (Gateway URL / SSH host / auth)  `id: gapfill-desktop-settings-1.connection-editor-address`
- **Surface:** Desktop app
- **Where:** Connection editor rows below the name (`apps/desktop/src/app/settings/connections-registry.tsx:795-943`): **"Gateway URL"** (`i18n: settings.connections.urlTitle`, placeholder literal **"http://homelab.lan:9119"**) for `remote`/`cloud`; **"SSH host"** (`sshHostTitle`, placeholder literal **"user@host:22"**) for `ssh`; and for `remote` an **"Authentication"** row (`i18n: settings.gateway.authTitle`) with the two buttons **"Session token"** (`settings.gateway.tokenTitle`) and the literal **"OAuth"**.
- **What it does:** Says where the gateway lives and how the app authenticates to it.
- **How it works:** URL and host inputs clear `dupeError` on change (the identity is what collided) and write `editor.url` / `editor.host`. The ssh field is a single composite string and **only that string is sent** on save — never separate `user`/`port` — because main's `normalizeSshConfig` gives explicit user/port fields precedence over the parsed host, so sending stored values alongside a retyped host would silently resurrect the old ones (comments `:78-82` and `:449-450`); `keyPath` rides along as `payload.keyPath = editor.keyPath || undefined`. In **token** mode the row **"Session token"** shows a `type="password"` input with the placeholder from `settings.gateway.pasteSessionToken` and the description `settings.gateway.tokenDesc`; a typed token is trimmed into `payload.token`. In **OAuth** mode the row instead offers a sign-in button — **"Sign in"** (`settings.gateway.signIn`) for a password provider or **"Sign in with `<provider>`"** (`settings.gateway.signInWith`) otherwise — which calls `window.hermesDesktop.oauthLoginConnectionConfig(editorUrl)` and, on success, replaces itself with a primary pill **"Signed in"** (`settings.gateway.signedIn`) plus a check. The provider name comes from a **debounced (400 ms) best-effort probe** of the typed URL via `window.hermesDesktop.probeConnectionConfig`, sequenced with `probeSeq` and cancelled on unmount, fed through `deriveRemoteAuthProviderShape(authProbe?.providers, t.boot.failure.identityProvider)`; a failed probe just leaves the generic label and never blocks signing in (comment `:279-281`). `editorUrl` is `coerceRemoteUrlScheme(editor.url)` for remote kinds. Changing the URL **or** flipping the auth mode resets `oauthConnected` to false, because the session is origin-scoped and a token-to-oauth edit must not show a stale "Signed in" pill (comment `:316-319`). Sign-in with an empty URL warns instead: `settings.gateway.enterUrlFirst`.
- **Inputs / options:** URL input; SSH host input; the `token`/`OAuth` mode buttons; the token password input; the sign-in button (disabled while `signingIn || !editorUrl`, spinner while in flight). Descriptions under the OAuth row vary by state: `authSignedInPassword` / `authSignedInOauth` when connected, `authNeedsPassword` / `authNeedsOauth(provider)` when not.
- **Outputs / side effects:** `payload.url`, `payload.authMode`, `payload.token`, `payload.host`, `payload.keyPath`; an OAuth browser round-trip whose credentials main keeps (native PKCE bearer tokens or legacy session cookies); sign-in toasts (documented in `gapfill-desktop-a-r0`).
- **Config / env:** n/a.
- **Edge cases / guards:** The probe fires only while the OAuth row is on screen and only for a non-empty URL. `cloud` entries get a URL but no auth row (Cloud sign-in happens above the section). The SSH `remoteProfile` is hydrated on edit so the duplicate key matches main's, but is deliberately **not** exposed in the editor (comment `:59-61`).
- **Rebuild notes:** Treat the ssh authority as one composite string end-to-end, debounce and sequence the auth probe, and invalidate "signed in" whenever the origin or the auth mode changes. A better version would validate reachability inline as the URL is typed (the Test button already exists per row) and would show which credential is currently stored for the row.

### Connection editor — Extra gateway headers  `id: gapfill-desktop-settings-1.connection-editor-headers`
- **Surface:** Desktop app
- **Where:** Connection editor, `remote` and `cloud` kinds only: the block titled **"Extra gateway headers"** (`i18n: settings.connections.headersTitle`, `apps/desktop/src/app/settings/connections-registry.tsx:878`) described as **"Sent with every HTTP and WebSocket request to this gateway — for access proxies such as Cloudflare Access (CF-Access-Client-Id / CF-Access-Client-Secret). Values are stored encrypted. Headers Hermes manages (Authorization, Cookie, Host…) are ignored."** (`i18n: settings.connections.headersDesc`).
- **What it does:** Lets a gateway sitting behind an access proxy receive extra static headers on every request the app makes to it.
- **How it works:** Editor state holds `headers: {name, stored, value}[]` (`:67`). Rows hydrated from an existing connection come from `conn.headerNames` with `stored: true` and an empty value — the app never round-trips the secret to the renderer. On save (`:436-447`) the rows are trimmed, blank names dropped, and turned into an authoritative map: a typed value → the new secret; an empty value on a **stored** row → `null`, meaning "keep the saved secret"; a row the user removed is simply **absent from the map, which clears it server-side**. The map is attached whenever there is at least one entry or the user emptied the list entirely (`headerEntries.length > 0 || editor.headers.length === 0`), so "delete the last header" is expressible.
- **Inputs / options:** Per row: a name input (placeholder literal **"CF-Access-Client-Id"**), a `type="password"` value input whose placeholder is **"Value"** (`settings.connections.headerValuePlaceholder`) for a new row or **"Saved — leave blank to keep"** (`headerValueSaved`) for a stored one, and a ghost **"Remove"** button (`headerRemove`). Below the list an outline **"Add header"** button (`headerAdd`) appends `{name: '', stored: false, value: ''}`.
- **Outputs / side effects:** `payload.headers` on save; main stores the values encrypted alongside the connection.
- **Config / env:** n/a.
- **Edge cases / guards:** Headers Hermes manages itself (`Authorization`, `Cookie`, `Host`, …) are ignored by the backend even if typed. Rows are keyed by index, so reordering is not offered. A stored row whose value box is left blank keeps its secret — that is the entire point of the `stored` flag.
- **Rebuild notes:** Model the header map as authoritative-on-save with a three-way value semantic (new secret / keep / absent-means-delete) and never send stored secrets back to the renderer. A better version would name the ignored headers inline when one is typed, and would support per-header enable/disable without deleting the value.

### Connection editor — Save / Cancel and save failure  `id: gapfill-desktop-settings-1.connection-editor-save`
- **Surface:** Desktop app
- **Where:** Footer of the connection editor (`apps/desktop/src/app/settings/connections-registry.tsx:947-954`): a ghost **"Cancel"** (`i18n: settings.connections.cancel`) and a primary **"Save connection"** (`save`) that becomes **"Saving…"** (`saving`) while in flight. Failures toast **"Could not save the connection"** (`i18n: settings.connections.saveFailed`, `connections-registry.tsx:475`; the same string backs a failed **Make primary** at `:513` and a failed launch-mode write at `:534`).
- **What it does:** Writes the edited connection into the registry, or abandons the edit.
- **How it works:** `save(allowPlainTextToken = false)` (`:388-481`) runs the duplicate check first (inline error, no IPC), then builds a `DesktopRegistryConnectionInput` — `{kind, label}` always, `id` when editing, plus the kind-specific fields — and calls `bridge.save(payload)`, publishing `result.registry` and closing the editor. One failure is special-cased **before** the toast: when the machine has no keyring (`registry.secureTokenStorage === false`) and the user is saving a `remote` connection in `token` mode with a non-empty token, the catch opens the plain-text opt-in `ConfirmDialog` instead of dead-ending the save (comment `:460-462`) — title `settings.gateway.plainTextConfirmTitle`, description `plainTextConfirmDesc`, confirm label `plainTextConfirmAction`, and confirming re-runs `save(true)` which sets `payload.allowPlainTextToken = true`. `Cancel` calls `openEditor(null)` (clearing the duplicate error) and is disabled while saving.
- **Inputs / options:** **"Cancel"** (`disabled={saving}`), **"Save connection"** (`disabled={saving || !editor.label.trim()}`), and the two buttons of the plain-text confirm dialog.
- **Outputs / side effects:** `connections.json` rewritten through main; the shared registry store republished; the editor closes; `plainTextConfirm` reset.
- **Config / env:** n/a. `secureTokenStorage` is a property of the registry payload, reflecting whether the OS keyring is usable.
- **Edge cases / guards:** The duplicate check runs in the renderer **and** in main (`normalizeConnectionInput`), so the UI check is convenience, not security (comment `:394-396`). Re-entering `save(true)` skips the plain-text branch, so a genuine second failure toasts instead of looping the dialog.
- **Rebuild notes:** Validate duplicates before the IPC hop, translate the one recoverable failure (no keyring) into a consent dialog rather than an error, and republish the whole registry from the writer's response instead of patching locally. A better version would keep the editor open with field-level errors on save failure instead of relying on a toast.

### Remove this connection?  `id: gapfill-desktop-settings-1.connection-remove-confirm`
- **Surface:** Desktop app
- **Where:** A destructive `ConfirmDialog` opened by a row's **"Remove"** button: title **"Remove this connection?"** (`i18n: settings.connections.removeConfirmTitle`, `apps/desktop/src/app/settings/connections-registry.tsx:1015`), description **""`<label>`" will be removed from this app. The instance itself is not touched — you can add it again any time."** (`removeConfirmDesc`), confirm label **"Remove"** (`removeConnection`). Failure toast: **"Could not remove the connection"** (`i18n: settings.connections.removeFailed`, `connections-registry.tsx:494`, `:499`).
- **What it does:** Confirms deleting a gateway from this app's registry, making clear that only the local bookkeeping is affected.
- **How it works:** The row button sets `removeTarget`; the dialog is `open={Boolean(removeTarget)}` and `destructive`. `onConfirm` runs `remove()` (`:483-499`): guard on `bridge && removeTarget`, set `busyId` to the target id (so the row shows a spinner), `await bridge.remove(removeTarget.id)`, publish the returned registry; a throw becomes `notifyError(err, s.removeFailed)`. `finally` clears both `busyId` and `removeTarget` — so the dialog closes whether or not the delete succeeded. `onClose` alone clears the target.
- **Inputs / options:** **"Remove"** (destructive confirm) and the dialog's cancel/dismiss.
- **Outputs / side effects:** `connections.json` loses the entry; the republished registry drops the row; the remote instance keeps running untouched.
- **Config / env:** n/a.
- **Edge cases / guards:** The app-managed `local` row never shows a Remove button, so it cannot reach this dialog. Removing the row that is currently **Primary** or **Current** is allowed — main re-resolves the registry (see `desktop-main.registry-save`) — which is why the launch-mode toggle stays visible even for a local-only registry (comment `:992-995`).
- **Rebuild notes:** Say what is *not* destroyed in the confirmation body; clear the busy id in `finally` so a failed delete cannot freeze the row. A better version would offer Undo for a few seconds instead of a modal, since the entry is cheap to restore.

### Update all instances (fan-out button)  `id: gapfill-desktop-settings-1.connections-update-all`
- **Surface:** Desktop app
- **Where:** Beside **"Add connection"** under the gateway list: an outline button **"Update all instances"** (`i18n: settings.connections.updateAll`, `RefreshCw` icon) that becomes **"Updating all instances…"** (`i18n: settings.connections.updateAllRunning`, `apps/desktop/src/app/settings/connections-registry.tsx:980`) with a spinner while running. Rendered only when `bridge?.updateAll` exists **and** more than one connection is registered (`:968`).
- **What it does:** Runs `hermes update` on every eligible registered instance at once and reports each one separately. It does **not** update the desktop client itself — that is the About page / Updates overlay path.
- **How it works:** `updateAll()` (`:569-593`) sets `updatingAll`, awaits `bridge.updateAll()` and loops the returned `results` rows, deliberately raising **one toast per connection so one dead box does not hide the others** (comment `:567-568`): `row.ok` → `notify({title: row.label, message: row.detail || s.updateAllDone})` where `updateAllDone` is **"Updates dispatched"**; `row.skipped && row.reason === 'cloud-managed'` → `notify({title: row.label, message: s.updateSkippedCloud})` = **"Managed by Hermes Cloud"**; anything else → `notifyError(new Error(row.error || row.detail || row.reason || row.label), s.updateAllFailed)` with the title **"Update fan-out failed"** (`i18n: settings.connections.updateAllFailed`, `connections-registry.tsx:585`), which is also the fallback title when the whole call throws (`:589`). `finally` clears `updatingAll`. The main-process fan-out (per-kind dispatch, SSH transaction, `excludeIds`) is `desktop-main.update-all`; the app-wide "update everything" orchestration that also drives this bridge is documented in `gapfill-desktop-main-r0`.
- **Inputs / options:** One button; `triggerHaptic('selection')` on click; `disabled={updatingAll}`.
- **Outputs / side effects:** An update command dispatched to each eligible instance; N toasts.
- **Config / env:** n/a.
- **Edge cases / guards:** Hidden entirely for a single-connection registry and for builds whose bridge lacks `updateAll` (older Electron main). Cloud-managed instances are reported as skipped rather than failed. The button does not wait for the updates to *finish* — "Updates dispatched" is the honest wording.
- **Rebuild notes:** Fan out server-side, return one result row per target with `{ok, skipped, reason, detail, error}`, and surface each row separately so partial success is visible. A better version would render a live per-instance progress list instead of a burst of toasts, and would let the user pick which instances to include.

### Startup launch mode (last-used vs Primary gateway)  `id: gapfill-desktop-settings-1.connections-launch-mode`
- **Surface:** Desktop app
- **Where:** A bordered block at the very bottom of **Settings → Gateways → Registered gateways**: `ToggleRow` labelled **"At startup, return to Sessions on the last-used gateway"** (`i18n: settings.connections.launchModeTitle`, `apps/desktop/src/app/settings/connections-registry.tsx:1002`) with the description **"When off, Sessions opens on the Primary gateway."** (`i18n: settings.connections.launchModeDesc`, `:1000`).
- **What it does:** Chooses which gateway the app lands on at launch — whichever you used last, or the one marked Primary.
- **How it works:** The switch is `checked={registry.launchMode === 'last-used'}` and `onChange` calls `setLaunchMode(enabled ? 'last-used' : 'primary')` (`:521-539`), which sets `launchModeBusy`, calls `bridge.setLaunchMode(mode)`, publishes the returned registry, and on failure toasts `s.saveFailed` (**"Could not save the connection"**). The value lives in `connections.json` as `launchMode: 'last-used' | 'primary'` alongside `primary` and `lastUsed` (registry v2 shape, `desktop-main.registry-file`); `connections.setLastUsed` is what keeps `lastUsed` current. The block renders whenever `!loading && registry` — explicitly **not** gated on `connections.length > 1`, because a registry that drifted down to local-only is exactly where a user needs to see and change this, and hiding it there left hand-editing `connections.json` as the only recourse (comment `:992-995`, issue #90174).
- **Inputs / options:** One `Switch` (`aria-label` **"At startup, return to Sessions on the last-used gateway"**), `disabled={launchModeBusy || !bridge?.setLaunchMode}`.
- **Outputs / side effects:** `connections.json` `launchMode` rewritten; the republished registry; the next launch resolves its start gateway accordingly.
- **Config / env:** n/a.
- **Edge cases / guards:** Disabled (but visible) on an Electron main too old to expose `setLaunchMode`. Toggling does not change the current session's gateway — only the next start.
- **Rebuild notes:** Store the launch policy next to the registry it governs, keep the control visible even in the degenerate one-connection case, and disable rather than hide when the bridge cannot honour it. A better version would offer a third mode ("always ask at launch") and would show which gateway the setting resolves to right now.

# Gap-fill — Desktop app: profile remote-override store, session status/unread, sidebar grouping, projects & worktrees, orphan profile strings

This shard closes the coverage gaps found by the mechanical i18n checker in area `desktop-b-0`: the
renderer-side store behind per-profile remote overrides, the one session status-dot primitive and the
persisted unread watermark it paints, the sidebar's grouping / projects-view toggle (including catalog-only
label variants), the project IDEA.md template pills, the base-branch combobox and the worktree-removal
lane, `moveSessionToProject`, and the two orphaned (catalog-only, no call site in v2026.8.31) profile
string families — clone-from-default and the profile setup-command copy.
It deliberately leaves to `desktop-b` the panels and dialogs these pieces are mounted in (Profiles panel,
create/rename/delete profile dialogs, Cron panel and editor, Artifacts page, chat sidebar and its session
rows/menus, project dialog, worktree dialog), to `desktop-a` the titlebar/command-palette/HUD, to
`desktop-main` the Electron main process (`connection.json`, `applyConnectionConfig`, git worktree IPC),
and to `desktop-settings` the Settings overlay. Verbatim labels that belong to an existing sibling entry
were appended in place rather than duplicated here.

## 1. Per-profile remote override — the renderer store

### Per-profile remote-override store (`store/profile-remote-override`)  `id: gapfill-desktop-b-0-r0.remote-override-store`
- **Surface:** Desktop app
- **Where:** No page of its own. It is the state layer behind the profile rail's context-menu entry **“Connect to a remote host…”** (`i18n: profiles.remoteOverride.menuItem`, rendered at `apps/desktop/src/app/chat/sidebar/profile-switcher.tsx:1328`) — replaced by the badge **“Runs on {host}”** (`i18n: profiles.remoteOverride.badge`) once an override exists — and behind the dialog `ProfileRemoteOverrideDialog`. File `apps/desktop/src/store/profile-remote-override.ts`.
- **What it does:** Remembers which profiles are pointed at a remote Hermes, so the rail can badge them; opens the override dialog from anywhere (context menu or a toast action); and turns a “remote host refused our token” switch failure into an actionable notification instead of a dead profile.
- **How it works:** Three exported atoms/functions plus one notifier.
  - `$profileRemoteOverrides` (`profile-remote-override.ts:24`) — `atom<Record<string, {host, url}>>`, keyed by profile name.
  - `$remoteOverrideDialogProfile` (`:29`) — `atom<null | string>`, the profile whose dialog is open. It is an atom rather than component state precisely so that *both* the rail's context menu and the auth-failure toast action can open the same single mounted dialog.
  - `openRemoteOverrideDialog(profile)` (`:31`) / `closeRemoteOverrideDialog()` (`:35`).
  - `remoteHostLabel(url)` (`:40`) — `new URL(url).hostname`, appending `:port` only when the port is present and is neither `80` nor `443`; returns `''` on a parse failure.
  - `refreshProfileRemoteOverrides(names)` (`:61`) — calls `window.hermesDesktop.getConnectionConfig(name)` for every name **in parallel** (`Promise.all`), keeps a profile only when `config.mode === 'remote' || config.mode === 'cloud'` **and** `config.remoteUrl` is set, and swallows per-profile errors so one bridge hiccup leaves that profile unbadged instead of failing the whole refresh. Then `$profileRemoteOverrides.set(next)` (a full replace, so a removed override disappears).
  - `notifyRemoteOverrideAuthFailure(profile, error)` (`:107`) — returns `false` (and lets the caller keep its generic handling) unless the profile has a known override **and** the error message matches `AUTH_FAILURE_RE` = `/\b(401|403|unauthorized|forbidden)\b|invalid[_ ]?token|token .*(expired|invalid|rejected)|authenticat\w+ (failed|required|expired)/i` (`:97`). Connectivity failures (timeout, refused, DNS) deliberately do **not** match, so a host that is merely down never misreads as a revoked token. On a match it raises an error notification and returns `true`.
  - The module deliberately does **not** import `store/profile` (which imports *this* module for the auth-failure toast); the dependency stays one-way (comment at `:14`).
- **Inputs / options:** `refreshProfileRemoteOverrides(names: string[])`; `openRemoteOverrideDialog(profile: string)`; `closeRemoteOverrideDialog()`; `remoteHostLabel(url: string)`; `notifyRemoteOverrideAuthFailure(profile: string, error: unknown)`. The only user-facing control it owns is the notification's action button, labelled **“Enter new token…”** (`i18n: profiles.remoteOverride.updateToken`, `profile-remote-override.ts:126`), which calls `openRemoteOverrideDialog(profile)`.
- **Outputs / side effects:** Writes `$profileRemoteOverrides` (drives the rail badge). Raises an error notification with title **“Remote host rejected the saved token”** (`i18n: profiles.remoteOverride.authFailedTitle`, `:123`) and message **“{host} refused the token saved for {profile}. It may have been changed on the remote side.”** (`i18n: profiles.remoteOverride.authFailedMessage`, `:124`), carrying the **“Enter new token…”** action. No disk writes of its own — the actual override lives in Electron's `connection.json` under `profiles.<name>` and is written only through `applyConnectionConfig`.
- **Config / env:** Reads `connection.json` (`profiles.<name>` → `profileRemoteOverride`) through the typed `window.hermesDesktop.getConnectionConfig(profile)` bridge. No config keys or env vars.
- **Edge cases / guards:** Blank/whitespace names are skipped. A profile whose config read throws stays unbadged rather than erroring. `remoteHostLabel` returning `''` makes callers fall back to the raw URL. Localisation uses `translateNow(...)` (not the React `useI18n` hook) because the notification is raised outside the render tree.
- **Rebuild notes:** Minimum: one map of profile → remote host, one “open the dialog for this profile” atom, and one error classifier that distinguishes *auth* failures from *reachability* failures. A better version would additionally probe the remote host's health on a switch (so “host down” and “token revoked” toast differently), and would offer to re-run the token exchange non-interactively when the remote supports OAuth.

## 2. Session status dot and the persisted unread watermark

### Session status dot (`SessionStatusDot`)  `id: gapfill-desktop-b-0-r0.session-status-dot`
- **Surface:** Desktop app
- **Where:** The small coloured dot in the lead slot of every sidebar session row, every pane/session tab, and the Ctrl+Tab session switcher. Component `apps/desktop/src/app/chat/session-status-dot.tsx`; also re-exported to plugins from `@hermes/plugin-sdk`.
- **What it does:** Renders one dot per session whose colour and fill say what that session is doing, with an accessible name and a hover title for every non-idle state.
- **How it works:** A pure lookup table `DOT_VARIANTS: Record<SessionDotState, DotVariant>` (`session-status-dot.tsx:29`); no priority logic lives here because `$sessionDotStateById` (`store/session-dot-state.ts`) has already reduced the overlapping signals to exactly one state. `DOT_BASE = 'size-1.5 rounded-full'` (`:21`). The design axis is “three colours × filled/hollow, nothing moving”: motion on a 6px circle only says *something is happening*, which the row's running arc already says better, at the cost of a repaint per frame on every row (comment at `:23`). The seven variants:
  - `needs-input` — `bg-amber-500`, `role="status"`, aria-label **“Needs your input”** (`i18n: sidebar.row.needsInput`), title **“Waiting for your answer”** (`i18n: sidebar.row.waitingForAnswer`, `:36`). Amber is the one “act now” colour and the only state the user is *required* to resolve (a clarify/approval is blocking the turn).
  - `working` — `bg-(--ui-accent)`, `role="status"`, aria-label **“Session running”** (`i18n: sidebar.row.sessionRunning`), no title (the row's arc carries the motion).
  - `stalled` — `border border-(--ui-accent)` (hollow accent), `role="status"`, aria-label and title both **“Session running”**. Same colour because it *is* working; hollow because nothing has arrived within the watchdog window.
  - `background` — `border border-(--ui-text-tertiary)` (hollow muted), `role="status"`, aria-label **and** title **“Background task running”** (`i18n: sidebar.row.backgroundRunning`, `:57` and `:60`). A `terminal(background=true)` process outlived the turn; an outline reads as “still open” without claiming the model is working, where a filled grey dot read as finished — the opposite of what it means.
  - `unread` — `bg-(--ui-success)` (emerald), `role="status"`, aria-label **and** title **“Finished — unread”** (`i18n: sidebar.row.finishedUnread`, `:67` and `:70`). The colour is theme-derived (a success green rotated toward the accent) so eight finished dots cannot sit in the sidebar fighting a palette they do not belong to; under a green accent it stays emerald.
  - `draft` — `border border-(--ui-text-quaternary)` (hollow grey, the faintest ink the app has), **no** `role`, aria-label and title both **“Draft — nothing sent yet”** (`i18n: sidebar.row.draftSession`, `:77` and `:79`). Shares the outline with `background` because both mean “open, not producing”, and sits a shade dimmer because a draft has yet to do anything at all.
  - `idle` — `size-1 rounded-full bg-(--ui-text-quaternary)`; rendered `aria-hidden`, with no label/title, and tinted with the session's project colour when there is one.
  `sessionDotClassName(state)` (`:93`) exports just the className for surfaces that describe a status rather than render a session (the sidebar's status-filter menu). The component subscribes to `$sessionColorById` for reactivity and resolves the tint with `sessionColorFor(session)`; the state comes from `useStoreSelector($sessionDotStateById, …)` — a **selector**, not a plain `useStore`, so a dot repaints only when *its own* state flips even though the map is rebuilt whenever any session changes (`:136`).
- **Inputs / options:** Props (`SessionStatusDotProps`, `:95`): `storedSessionId: null | string` (the STORED session id — the key every live-state atom is keyed by on both surfaces; `null` on a brand-new chat, which *is* the draft state by definition, so the state falls back to `'draft'`); `session?: null | SessionInfo` (row used for colour resolution, so the idle dot can inherit the project colour even for a session older than the paginated recents page); `branchStem?: string` (a TUI-style tree stem, `└─ ` / `├─ `, for a branched session); `className?: string` (applied to the OUTER wrapper — stem + dot — e.g. the hover-fade on the reorder handle). No click handlers: the dot is decoration + accessible status, never a control.
- **Outputs / side effects:** Pure render. An idle dot is still rendered when it has no colour to paint, so every row's title keeps the same left edge and a session finishing cannot shift the list under the pointer (comment at `:150`).
- **Config / env:** Colours come from the theme tokens `--ui-accent`, `--ui-success`, `--ui-text-tertiary`, `--ui-text-quaternary`, plus Tailwind's `amber-500`. No config keys.
- **Edge cases / guards:** `SessionDotState` is `'background' | 'draft' | 'idle' | 'needs-input' | 'stalled' | 'unread' | 'working'` (`session-dot-state.ts:70`). For filtering/ordering these fold into five buckets via `sessionStatusBucket()` — `stalled` and `background` both fold into `working` (`session-dot-state.ts:86`) — ranked `needs-input`=0, `working`=1, `unread`=2, `draft`=3, `idle`=4 (`STATUS_RANK`, `:90`). `showsRunningArc(state)` is true only for `stalled`/`working`; `hasLiveTurn(state)` adds `needs-input`. The idle variant is the only one rendered `aria-hidden`, so screen readers are not told about every quiet session.
- **Rebuild notes:** Minimum: reduce all overlapping session signals to ONE state in a single store, then map state → (className, aria-label, title) in one table that every surface renders. A better version would let the dot expose *why* it is in that state on hover (which tool is blocking, which background PID is alive) and would animate only the single row the user is pointing at.

### Mark as unread / Mark as read (persisted read-state watermark)  `id: gapfill-desktop-b-0-r0.session-unread-toggle`
- **Surface:** Desktop app
- **Where:** Session row actions menu → the single read-state item, labelled **“Mark as unread”** (`i18n: sidebar.row.markUnread`) or **“Mark as read”** (`i18n: sidebar.row.markRead`) depending on the row's current state (`apps/desktop/src/app/chat/sidebar/session-actions-menu.tsx:315`; the handler at `:201`). Wired from the sidebar by `toggleUnread(storedId)` (`apps/desktop/src/app/chat/sidebar/index.tsx:405`, prop threading at `:325`). Store: `apps/desktop/src/store/session-unread-remote.ts`.
- **What it does:** Flips a session's persisted unread flag so its emerald dot survives an app restart, and clears it again when you open the session.
- **How it works:** The dot is fed by two sources (`store/session-dot-state.ts`): the transient runtime marker `$unreadFinishedSessionIds` (“a turn finished in the background while this window was not looking”) and the backend's derived `row.unread` watermark (`last_read_at` vs `last_active`). This module owns the **write** side of the persisted one. `markSessionUnread(storedId, unread)` (`session-unread-remote.ts:40`): resolve the row (no-op for a runtime-only session with no persisted row); stamp `$unreadWriteGuard` with `{at: Date.now(), value: unread}`; optimistically patch `$sessions`; `await setSessionUnreadRemote(storedId, unread, row.profile)` → `PATCH /api/sessions/{id}` → `SessionDB.set_session_read`; on failure delete the guard entry and **visibly roll the row back** to `!unread`, then rethrow. The guard exists because a session-list page already in flight can land after the ack carrying the OLD value; a guarded row outranks that stale page for `UNREAD_WRITE_GUARD_MS = 10_000` ms (`:29`, `:31`). `watchUnreadWriteGuard()` (`:78`) listens on `$sessions` and releases each guard entry once a list page confirms the value that was written; it is called once at boot next to `watchSessionPins()`. `clearUnreadOnOpen(storedId)` (`:66`) is the auto-mark-read on open — best-effort, a failed PATCH is simply healed by the next honest refresh. The menu item's icon is `mail-read` when the row is unread and `mail` when it is read (the codicon font has `mail` and `mail-read` but no `mail-unread` glyph, verified against the font CSS — comment at `session-actions-menu.tsx:312`). Marking read *also* clears the transient family dot immediately via `markSessionRead(sessionId)` + `ackStoredSessionId(sessionId)` so a list refresh cannot repaint it.
- **Inputs / options:** One menu item (label toggles between **“Mark as unread”** and **“Mark as read”**), disabled when there is no `sessionId` or when neither an `onToggleUnread` handler nor a lit transient dot exists (`session-actions-menu.tsx:311`). Store API: `markSessionUnread(storedId, unread)`, `clearUnreadOnOpen(storedId)`, `watchUnreadWriteGuard()`, plus the atom `$unreadWriteGuard` and the constant `UNREAD_WRITE_GUARD_MS`.
- **Outputs / side effects:** `PATCH /api/sessions/{id}` writes the backend read watermark; `$sessions` is updated optimistically and rolled back on failure. A failed write raises an error toast whose fallback message is **“Could not update unread state”** (`i18n: sidebar.row.unreadFailed`, `sidebar/index.tsx:405`). Success is silent — the dot itself is the feedback. Selecting the item fires `triggerHaptic('selection')`.
- **Config / env:** n/a — no config keys or env vars; the watermark is backend state on the session row.
- **Edge cases / guards:** A brand-new chat with no persisted row is a silent no-op (nothing to flag). The rollback is deliberately *visible* (“optimistic, then honest”). Import cycle with `./session` is inert: both modules touch each other's exports only inside function bodies, never at module-evaluation time (comment at `session-unread-remote.ts:19`).
- **Rebuild notes:** Minimum: a boolean per session, a PATCH, and an optimistic update with rollback. The write guard is the non-obvious part — without it a concurrent list fetch silently reverts the user's click. A better version would make the watermark a timestamp rather than a boolean (so “unread since” is answerable) and would sync read-state across devices through the same change-event stream the sidebar already listens to.

## 3. Sidebar grouping / projects-view toggle

### Sidebar header toggle — projects list ⇄ session list  `id: gapfill-desktop-b-0-r0.sidebar-group-toggle`
- **Surface:** Desktop app
- **Where:** The icon button in the chat sidebar's section header (`list-unordered` codicon), rendered inside a `Tip` at `apps/desktop/src/app/chat/sidebar/index.tsx:1753`. Live label and aria-label are both **“Show projects”** (`i18n: sidebar.showProjects`).
- **What it does:** Leaves the currently-entered project and returns the sidebar to the projects overview; in the grouped/flat variants of this control it switches sessions between a workspace-grouped tree and one flat list.
- **How it works:** When the sidebar is scoped into a project (`inProject && enteredProject`) the header renders a `StartWorkButton` (when the project has a path), the `ProjectMenu` kebab (suppressed for the Home bucket, which has no record to rename, theme or delete), and this button, whose `onClick` does `event.stopPropagation()` then `exitProjectScope()` (`sidebar/index.tsx:1756`). Grouping itself is a persisted layout-store value (`setSidebarGrouping`, exposed in the sidebar filter menu as **“Grouping”** → **“Project”**), so the toggle is a shortcut into a state the filter menu also owns.
- **Inputs / options:** One button. `aria-label` **“Show projects”** and tooltip **“Show projects”** (`i18n: sidebar.showProjects`), class `HEADER_NAV_BTN`, `size="icon-xs"`, `variant="ghost"`, icon `list-unordered` at `0.75rem`. The catalog ships the full label set for both directions of the control, all five locales, so the reverse leg and the grouped/ungrouped tooltips are translatable: **“Show sessions”** (`i18n: sidebar.showSessions`, the sibling of `sidebar.showProjects` that returns the sidebar from the projects/workspace list to the flat session list), **“Show sessions as a single list”** (`i18n: sidebar.groupAriaGrouped`, the aria-label while grouped), **“Group sessions by workspace”** (`i18n: sidebar.groupAriaUngrouped`, the aria-label while flat), **“Ungroup sessions”** (`i18n: sidebar.groupTitleGrouped`, the tooltip/title while grouped) and **“Group by workspace”** (`i18n: sidebar.groupTitleUngrouped`, the tooltip/title while flat).
- **Outputs / side effects:** Calls `exitProjectScope()` — the sidebar drops out of the entered project and re-renders the project list; nothing is written to disk. The grouped/ungrouped variants write the persisted sidebar layout store.
- **Config / env:** Persisted in the desktop layout store alongside the other sidebar view settings (grouping, ordering, row meta, filters). No dotted config key.
- **Edge cases / guards:** Only the `sidebar.showProjects` label has a live call site in v2026.8.31 (verified by grepping `apps/desktop/src` for each key); `sidebar.showSessions`, `sidebar.groupAriaGrouped`, `sidebar.groupAriaUngrouped`, `sidebar.groupTitleGrouped` and `sidebar.groupTitleUngrouped` are present in all five locale catalogs (`en`, `ar`, `ja`, `zh`, `zh-hant`) with no remaining call site — the grouping control they described was folded into the filter menu's **“Grouping”** submenu and this header button. The button is not rendered at all outside an entered project; when showing all profiles the header renders the new-project/new-session action instead.
- **Rebuild notes:** Minimum: one header button that pops the sidebar out of a project scope, plus a grouping flag in a persisted view store. A better version would keep the label pair symmetric (one control that reads “Show projects” / “Show sessions” in place) instead of leaving half the vocabulary stranded in the catalog.

## 4. Projects — IDEA.md templates, base branch picker, worktree removal, move-to-project

### Project idea templates (“Shuffle templates” pills)  `id: gapfill-desktop-b-0-r0.project-idea-templates`
- **Surface:** Desktop app
- **Where:** Sidebar → Projects → the create-project dialog, under the **“Idea”** field (`i18n: sidebar.projects.ideaLabel`), whose textarea placeholder is **“What's this project about? (saved to IDEA.md)”** (`i18n: sidebar.projects.ideaPlaceholder`, `apps/desktop/src/app/chat/sidebar/project-dialog.tsx:239`). Pills render at `project-dialog.tsx:252`; the dice button at `:264`–`:266`. Content file `apps/desktop/src/lib/project-idea-templates.ts`.
- **What it does:** Offers a random handful of one-click starter briefs; clicking a pill fills the Idea textarea with that template's text, which is then written to the project's `IDEA.md`.
- **How it works:** `PROJECT_IDEA_TEMPLATES` (`project-idea-templates.ts:12`) is a flat array of `{emoji, label, idea}`. `randomIdeaTemplates(count = 6)` (`:106`) copies the pool, Fisher–Yates shuffles it in place, and returns the first `min(count, pool.length)` entries. `ProjectDialog` calls it once when the dialog opens (`project-dialog.tsx:55`) and again on every dice click (`:269`), so the visible set is a fresh random slice each time. Each pill is a `<button type="button">` rendering `template.emoji` (`aria-hidden`) followed by `template.label`, whose `onClick` is `setIdea(template.idea)` — it **replaces** whatever is in the textarea. On submit, `createProject({folders, idea: idea.trim() || undefined, name, use: true})` (`:127`) persists the brief.
- **Inputs / options:** The 18 templates, verbatim labels in file order: **“Game jam”** 🎮, **“Novel”** 📚, **“Discord bot”** 🤖, **“Data viz”** 📊, **“Generative art”**, **“Recipe box”**, **“Research log”**, **“Budget tracker”**, **“Habit tracker”**, **“Trip planner”**, **“Music toy”**, **“Puzzle maker”**, **“Digital garden”**, **“API wrapper”**, **“Workout plan”**, **“Flashcards”**, **“Screenplay”**, **“Learn-by-building”**. Plus the dice/refresh button whose tooltip **and** `aria-label` are both **“Shuffle templates”** (`i18n: sidebar.projects.ideaShuffle`), icon `refresh` at `0.75rem`, `size="icon-xs"`, `variant="ghost"`, disabled while `submitting`. Beside them sits the AI `GenerateButton` labelled **“Generate idea”** / **“Generating…”** (`i18n: sidebar.projects.ideaGenerate` / `sidebar.projects.ideaGenerating`), which calls `generateProjectIdea(name)`.
- **Outputs / side effects:** Sets the dialog's `idea` state only; the write happens on submit, when the brief is saved as the project's `IDEA.md`.
- **Config / env:** n/a — pure content, no config keys or env vars.
- **Edge cases / guards:** Clicking a pill overwrites unsaved text in the textarea with no confirmation. All pills and the dice are disabled while the dialog is submitting. `generateIdea()` guards re-entry with `generatingIdea` and only applies a non-empty result (`project-dialog.tsx:131`). Template content is source-only — it is **not** localised, so the pills read in English in every locale.
- **Rebuild notes:** Minimum: a static array of `{emoji, label, idea}`, a shuffle, and a click that fills a textarea. A better version would localise the pool, let a user pin/author their own templates, and seed the AI generator from the picked template instead of discarding it.

### Base branch picker (“branch off …”)  `id: gapfill-desktop-b-0-r0.base-branch-picker`
- **Surface:** Desktop app
- **Where:** Sidebar → Projects → the New-worktree dialog, below the branch-name input. Component `apps/desktop/src/app/chat/sidebar/projects/base-branch-picker.tsx`; mounted at `worktree-dialog.tsx:325` with `key={repoPath}` so it remounts (and reloads) whenever the target repo changes.
- **What it does:** Picks which existing branch the new worktree's branch is cut from, as a searchable combobox that defaults to the repo's default branch.
- **How it works:** On mount (and on popover open) `load()` (`base-branch-picker.tsx:38`) calls `listBaseBranches(repoPath)` and immediately selects a default: the entry with `isDefault` (the remote default, `origin/HEAD`), else `list[0]?.name ?? ''` — the value is always a concrete branch, never `undefined` (`:49`). It loads on mount rather than lazily because otherwise the trigger button would read **“branch off ”** with nothing after it (comment at `:66`). The list is sorted by pinning the current session's branch to the top and keeping git's most-recently-committed order for the rest (`:76`); the current branch comes from `$repoStatus` and is `null` when the checkout is detached (`:36`). The trigger's copy is assembled from `p.branchOff()`, an i18n **function returning `{before, after}`** so the branch name can be wrapped in its own underlined span and still work in a language with a different word order (comment at `:90`); in English `before` is `"branch off "` and `after` is `""`. While loading, the value slot renders `'...'`.
- **Inputs / options:** Props: `disabled?`, `repoPath`, `onValueChange(value)`, `value`. The trigger is a full-width `variant="text"` `size="inline"` button with a `git-branch` codicon, the `before` text, the selected branch (underlined on hover), a `chevron-down` codicon and the `after` text; it is disabled when `disabled || loading`. The popover holds a `Command` combobox with a case-insensitive `includes` filter, a `CommandInput` placeholder **“Search branches…”** (`i18n: sidebar.projects.baseBranchPlaceholder`, `:124`), a `CommandList` capped at `max-h-64`, a `CommandEmpty` reading **“No branches found”** (`i18n: sidebar.projects.baseBranchNone`, `:126`), and one `CommandItem` per branch showing a `repo` codicon for a remote branch or `git-branch` for a local one, plus a **★** marker on the default branch. Selecting an item calls `onValueChange(branch.name)` and closes the popover.
- **Outputs / side effects:** Reports the chosen base upward; the worktree dialog passes it as `startWorkInRepo(repoPath, {base, branch, name})`. A failed `listBaseBranches` silently sets an empty list (`:59`) — no toast.
- **Config / env:** n/a — the branch list comes from the git worktree IPC/bridge, not from config.
- **Edge cases / guards:** With no `repoPath` the loader returns immediately. A repo change remounts the component (via `key`), which is what stops branches of the previous project leaking into the new list; the worktree dialog additionally clears `branches`/`selectedBase` when the project picker changes (`worktree-dialog.tsx:257`). A silent load failure leaves the picker empty rather than blocking the dialog.
- **Rebuild notes:** Minimum: list branches, preselect the default, filterable popover, report the name. A better version would show ahead/behind counts and the last-commit date per branch, and would fall back to `HEAD` (with an explicit note) instead of an empty value when the repo has no branches at all.

### Remove worktree (project lane)  `id: gapfill-desktop-b-0-r0.worktree-remove`
- **Surface:** Desktop app
- **Where:** Sidebar → Projects → an entered project's worktree lane: the lane's kebab / workspace-header menu item **“Remove worktree”** (`i18n: sidebar.projects.removeWorktree`). Logic in `apps/desktop/src/app/chat/sidebar/projects/entered-content.tsx:141`; the two confirm dialogs at `:177`–`:222`; the menu items in `projects/workspace-header.tsx`.
- **What it does:** Removes a git worktree — either really (`git worktree remove`, deleting the directory while keeping the branch) or only from the sidebar, leaving it on disk — and escalates to a force prompt when git refuses because the worktree is dirty.
- **How it works:** `removeViaGit(group, force = false)` (`entered-content.tsx:141`) calls `removeWorktreePath(repo.path, group.path, {force})` then `dismissWorktree(group.id)`. On failure it inspects the message: if `!force` and the message matches `/force|modified|untracked|dirty|locked|contains/i` it opens the **force** prompt instead of dead-ending on a toast (comment at `:150`); anything else raises `notifyError(err, s.projects.removeWorktreeFailed)`. Both prompts are produced by one `worktreeDialog(target, setTarget, description, destructiveLabel, onDestructive)` helper (`:177`) so they share the shape — a destructive action, a secondary “just hide it” action, and cancel — and differ only in copy and handler. Both carry `dismissOnConfirm` because `removeViaGit` finishes on its own (it either dismisses the lane, escalates, or toasts) and there is nothing for the dialog to wait on (comment at `:186`). Lanes filtered out of `ordered` (`:130`) are the dismissed ones, unless the worktree is still discovered on disk.
- **Inputs / options:** Dialog title is assembled as **“Remove worktree”** + ` "` + the lane label + `"?`. First prompt: description **“Remove it from git (deletes the worktree directory; the branch stays), or just hide the lane from the sidebar and leave the worktree on disk.”** (`i18n: sidebar.projects.removeWorktreeConfirm`), destructive button **“Remove worktree”** (`i18n: sidebar.projects.removeWorktree`). Force prompt: description **“This worktree has uncommitted changes. Force-remove it (discards those changes), or just hide the lane and keep it on disk.”** (`i18n: sidebar.projects.removeWorktreeDirty`), destructive button **“Force remove”** (`i18n: sidebar.projects.forceRemove`). Both offer the secondary action **“Hide from sidebar”** (`i18n: sidebar.projects.removeFromSidebar`) which calls `dismissWorktree(id)`, plus the shared cancel. The lane menus also carry **“Reveal in folder”** (`i18n: sidebar.projects.reveal`, `workspace-header.tsx:93`) and **“Copy path”** (`i18n: sidebar.projects.copyPath`), both disabled when the lane has no path.
- **Outputs / side effects:** Runs a real `git worktree remove` (optionally `--force`) through the desktop git bridge, deleting the worktree directory; the branch itself survives. Dismissal writes the dismissed-worktree list that filters the lane out of the sidebar. A non-force failure that is not the dirty case toasts **“Could not remove worktree (uncommitted changes?)”** (`i18n: sidebar.projects.removeWorktreeFailed`, `entered-content.tsx:155`).
- **Config / env:** n/a
- **Edge cases / guards:** The main checkout lane and the aggregated kanban bucket get **no** remove action (`onRemove` is `undefined` for `group.isMain || group.isKanban`) — the kanban bucket aggregates many task worktrees, so “remove worktree” has no single target (comment at `entered-content.tsx:163`). Removal is a no-op when either `repo.path` or `group.path` is missing. A lane hidden from the sidebar reappears if the worktree is rediscovered on disk and `discoveredWorktreePaths` still contains its path.
- **Rebuild notes:** Minimum: `git worktree remove [--force]`, a confirm with a “just hide it” escape hatch, and a dirty-worktree escalation instead of a bare error. A better version would show the uncommitted diff stat inside the force prompt and offer to stash or branch the changes before discarding them.

### Move a session to another project  `id: gapfill-desktop-b-0-r0.move-session-to-project`
- **Surface:** Desktop app
- **Where:** Session row actions menu → the **“Move to project”** submenu (`i18n: sidebar.projects.moveToProject`), items rendered by `MoveToProjectItems` at `apps/desktop/src/app/chat/sidebar/session-actions-menu.tsx:302`; store function `moveSessionToProject` at `apps/desktop/src/store/projects.ts:615`.
- **What it does:** Re-homes an existing chat into another project's root folder — the fix for a session that was created in the wrong directory.
- **How it works:** The submenu computes eligible targets from `$projectTree`: every node except the session's current project (resolved from its `cwd` through `projectIdForCwd`), except the folderless Home bucket (`isNoProject`), and except nodes with no `projectRootCwd` — there is nothing to move into (comment at `session-actions-menu.tsx:299`). `moveSessionToProject(sessionId, projectId, profile?)` (`projects.ts:615`) resolves the destination `cwd` with `projectRootCwd(...)` and, when there is none, **throws** `new Error(translateNow('sidebar.projects.moveNoFolder'))`. Otherwise it calls the gateway RPC `session.workspace.move` with `{cwd, session_key: sessionId, ...(profile ? {profile} : {})}`; the backend replaces the session's cwd **and** git identity (so the tree's grouping follows) and re-anchors any live agent bound to the row. The renderer then mirrors the move into the `$sessions` cache using `res.cwd || cwd`, so both the flat list and the grouped tree reflect it before the next authoritative refresh.
- **Inputs / options:** One submenu item per eligible project, labelled with the project's own `label`. When `targets.length === 0` the submenu instead renders a single **disabled** item reading **“No other projects”** (`i18n: sidebar.projects.moveNoProjects`, `session-actions-menu.tsx:162`). Store signature: `moveSessionToProject(sessionId: string, projectId: string, profile?: null | string): Promise<void>`.
- **Outputs / side effects:** Gateway RPC `session.workspace.move` rewrites the stored session's cwd/git identity; `$sessions` is updated locally. Success toasts **“Moved to {name}”** (`i18n: sidebar.projects.movedTo`) for 2 000 ms; failure raises `notifyError(err, p.moveFailed)` with the fallback **“Could not move session”** (`i18n: sidebar.projects.moveFailed`, `session-actions-menu.tsx:174`). Selecting an item fires `triggerHaptic('selection')`.
- **Config / env:** n/a
- **Edge cases / guards:** A target project record with no folder path produces the thrown error **“That project has no folder to move into”** (`i18n: sidebar.projects.moveNoFolder`, `projects.ts:623`) — which surfaces through the same `moveFailed` toast path. The submenu subscribes to `$projectTree`/`$sessions` **inside** its own component so a closed submenu does not re-render every row's menu on each session update (comment at `session-actions-menu.tsx:126`). Sessions with a blank `cwd` have no current project, so every project with a folder is offered.
- **Rebuild notes:** Minimum: resolve the destination folder, one RPC that rewrites cwd + git identity server-side, mirror it locally, toast. A better version would move (or offer to move) the session's on-disk artifacts too, and would warn when the destination folder is not the same git repo.

### “Copy setup” — profile setup/wrapper command  `id: gapfill-desktop-b-0-r0.profiles-copy-setup`
- **Surface:** Desktop app
- **Where:** Profiles panel → per-profile action, catalogued as **“Copy setup”** (`i18n: profiles.copySetup`) with the busy label **“Copying...”** (`i18n: profiles.copying`). Catalog entries at `apps/desktop/src/i18n/en.ts` in the `profiles` block (`copySetup`, `copying`, `setupCopied:1961`, `failedCopy:1965`).
- **What it does:** Copies to the clipboard the shell command that makes this profile usable from a terminal (the `hermes` wrapper / `HERMES_PROFILE` invocation written into `~/.local/bin`), then reports success or failure as a toast.
- **What it does today:** Nothing — this string family is **catalog-only in v2026.8.31**. `copySetup`, `copying`, `setupCopied` and `failedCopy` are present in all five locale catalogs, but grepping `apps/desktop/src` for `copySetup`, `setupCopied` or `failedCopy` returns matches only inside `src/i18n/`. - **How it works:** As catalogued, the flow is: click the action → label swaps to **“Copying...”** while the command is assembled → `navigator.clipboard.writeText(...)` → success toast **“Setup command copied”** or, on a rejected clipboard write, an error toast **“Failed to copy setup command”**.

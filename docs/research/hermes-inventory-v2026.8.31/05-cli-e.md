## 1. `hermes skills` — Skills Hub

### Skills command group  `id: cli-e.skills`
- **Surface:** CLI
- **Where:** `hermes skills [-h] {trust,untrust,browse,search,install,inspect,list,check,update,audit,uninstall,reset,list-modified,diff,opt-out,opt-in,repair-official,publish,snapshot,tap,config} ...`. Help line in the root command list: `Search, install, configure, and manage skills`. Long description (verbatim): `Search, install, inspect, audit, configure, and manage skills from skills.sh, well-known agent skill endpoints, GitHub, ClawHub, and other registries.`
- **What it does:** Umbrella command for the Skills Hub: discovers skills across nine registries, installs them into `~/.hermes/skills/`, keeps them updated, security-scans them, and enables/disables them per profile and per platform.
- **How it works:** Parser is built in `hermes_cli/subcommands/skills.py:12` (`build_skills_parser`) and attached to the root subparsers with `set_defaults(func=cmd_skills)` (`hermes_cli/subcommands/skills.py:348`). `cmd_skills` (`hermes_cli/main.py:13021`) routes three ways: `config` → `hermes_cli/skills_config.py:159` (`skills_command`) after `_require_tty("skills config")`; `trust`/`untrust` → `_cmd_skills_trust` (`hermes_cli/main.py:13037`); everything else → `hermes_cli/skills_hub.py:1820` (`skills_command`), which dispatches to the shared `do_*` functions. The same `do_*` functions back the `/skills` chat slash command (`hermes_cli/skills_hub.py:1895` `handle_skills_slash`).
- **Inputs / options:** `-h, --help`; exactly one of the 21 sub-commands listed above. Sub-command help strings, verbatim from the group help screen: `trust` = `Trust a project so its repo-local skills (./.hermes/skills, ./.agents/skills) load`; `untrust` = `Revoke project-skill trust for a repo`; `browse` = `Browse all available skills (paginated)`; `search` = `Search skill registries`; `install` = `Install a skill`; `inspect` = `Preview a skill without installing`; `list` = `List installed skills`; `check` = `Check installed hub skills for updates`; `update` = `Update installed hub skills`; `audit` = `Re-scan installed hub skills`; `uninstall` = `Remove a hub-installed skill`; `reset` = `Reset a bundled skill — clears 'user-modified' tracking so updates work again`; `list-modified` = `List bundled skills you've edited (which `hermes update` keeps)`; `diff` = `Show how your copy of a bundled skill differs from the stock version`; `opt-out` = `Stop bundled skills from being seeded into this profile`; `opt-in` = `Re-enable bundled-skill seeding (undo opt-out)`; `repair-official` = `Backfill or restore official optional skills from repo source`; `publish` = `Publish a skill to a registry`; `snapshot` = `Export/import skill configurations`; `tap` = `Manage skill sources`; `config` = `Interactive skill configuration — enable/disable individual skills`.
- **Outputs / side effects:** With no sub-command, `skills_command` prints the fallback usage line `Usage: hermes skills [browse|search|install|inspect|list|list-modified|diff|check|update|audit|uninstall|reset|opt-out|opt-in|publish|snapshot|tap]` followed by `Run 'hermes skills <command> --help' for details.` (`hermes_cli/skills_hub.py:1884-1886`).
- **Config / env:** `skills.external_dirs` (default `[]`), `skills.project_discovery` (`true`), `skills.trusted_project_dirs` (`[]`), `skills.template_vars` (`true`), `skills.inline_shell` (`false`), `skills.inline_shell_timeout` (`10`), `skills.guard_agent_created` (`false`), `skills.tier1_advisory` (`true`), `skills.write_approval` (`false`), `skills.ledger` (`true`); plus the un-defaulted `skills.disabled` and `skills.platform_disabled.<platform>` lists written by `hermes skills config`. `GITHUB_TOKEN` raises the GitHub API limit from 60/hr to 5,000/hr. `HERMES_HOME` selects the profile root.
- **Edge cases / guards:** `hermes skills config` requires a TTY (`_require_tty`). Every hub install passes through quarantine + `tools/skills_guard.py` scanning before landing in `~/.hermes/skills`.
- **Rebuild notes:** Model the hub as (a) a source-router of pluggable `SkillSource` adapters, (b) a lockfile of installed skills with content hashes, (c) a quarantine+scan+confirm install pipeline, (d) a bundled-skill sync manifest that detects user edits. A better version would sign bundles and record a reproducible resolution (source id + commit sha) per install, instead of re-resolving a bare name at update time.

### Trust a project's repo-local skills  `id: cli-e.skills-trust`
- **Surface:** CLI
- **Where:** `hermes skills trust [-h] [path]`
- **What it does:** Adds a project root to `skills.trusted_project_dirs` so skills stored in that repo's `./.hermes/skills` or `./.agents/skills` load in sessions started inside it.
- **How it works:** `_cmd_skills_trust` (`hermes_cli/main.py:13037`). With no `path` it calls `agent.skill_utils.find_project_root()` (nearest ancestor containing `.git`); with a path it does `Path(raw_path).expanduser().resolve()` and rejects non-directories with `Not a directory: {root}`. Loads config via `hermes_cli/config.load_config`, normalises `skills.trusted_project_dirs` to a list of strings, appends the resolved root if not already present, and `save_config`s. It then counts loadable project skills by iterating `_candidate_project_skills_dirs(root)` and `iter_skill_index_files(d, "SKILL.md")`.
- **Inputs / options:** `-h, --help`; positional `path` (optional) = `Project root to trust (default: enclosing git checkout of cwd)`.
- **Outputs / side effects:** Writes `skills.trusted_project_dirs` in `~/.hermes/config.yaml`. Prints `Trusted: {root}` (or `Already trusted: {root}`), then either `{count} project skill(s) will load in sessions started inside this repo (they take precedence over same-named profile skills).` or `No project skills found yet — add them under {subdirs}.` where `subdirs` is `PROJECT_SKILLS_SUBDIRS` joined with ` or `.
- **Config / env:** `skills.trusted_project_dirs`, `skills.project_discovery`.
- **Edge cases / guards:** Outside a git checkout with no explicit path it prints `Not inside a git checkout. Run from a project directory or pass the project root path explicitly.` and returns. Paths are resolved before comparison, so symlinked duplicates collapse.
- **Rebuild notes:** Store absolute resolved paths; compare resolved. A better version would trust a repo *and* pin the commit/hash of the skills, re-prompting when repo-local skills change.

### Untrust a project  `id: cli-e.skills-untrust`
- **Surface:** CLI
- **Where:** `hermes skills untrust [-h] [path]`
- **What it does:** Removes a project root from `skills.trusted_project_dirs`, so that repo's local skills stop loading.
- **How it works:** Same handler `_cmd_skills_trust` with `action == "untrust"` (`hermes_cli/main.py:13077`): filters the trusted list by resolved-path inequality and saves.
- **Inputs / options:** `-h, --help`; positional `path` (optional) = `Project root to untrust (default: enclosing git checkout of cwd)`.
- **Outputs / side effects:** Config write. Prints `Untrusted: {root}` then `Project skills from this repo will no longer load.`; if the path was not in the list, prints `{root} was not trusted.` and makes no write.
- **Config / env:** `skills.trusted_project_dirs`.
- **Edge cases / guards:** Same "not inside a git checkout" guard as `trust`.
- **Rebuild notes:** Idempotent removal keyed on resolved path.

### Browse all skills (paginated)  `id: cli-e.skills-browse`
- **Surface:** CLI
- **Where:** `hermes skills browse [-h] [--page PAGE] [--size SIZE] [--source {all,official,skills-sh,well-known,github,clawhub,lobehub,browse-sh,nvidia,openai,anthropic,huggingface,voltagent,gstack,minimax}]`
- **What it does:** Lists every skill the hub can see, merged across registries, sorted official-first then by trust, paginated in a Rich table.
- **How it works:** `do_browse` (`hermes_cli/skills_hub.py:372`). Clamps `page_size` to 1..100. Builds sources via `tools.skills_hub.create_source_router(GitHubAuth())` and calls `parallel_search_sources(sources, query="", per_source_limits=_PER_SOURCE_LIMIT, source_filter=source, overall_timeout=30, on_source_done=...)`. `_PER_SOURCE_LIMIT` = `{"hermes-index": 1000000, "official": 200, "skills-sh": 200, "well-known": 50, "github": 200, "clawhub": 500, "lobehub": 500, "browse-sh": 500}` (`skills_hub.py:401-406`); when the centralized `hermes-index` is available the router serves everything from it and skips the external APIs. Provider filters (`nvidia`/`openai`/…) are applied post-hoc via `_filter_results_by_provider` because GitHub-tap skills are all stored under `source="github"`. Dedupe is by `identifier`, keeping the higher `_TRUST_RANK` (`{"builtin": 3, "trusted": 2, "community": 1}`). Sort key = `(-trust_rank, source != "official", name.lower())`.
- **Inputs / options:** `-h, --help`; `--page PAGE` = `Page number (default: 1)` (int); `--size SIZE` = `Results per page (default: 20)` (int, clamped 1–100); `--source` with 15 choices = `all`, `official`, `skills-sh`, `well-known`, `github`, `clawhub`, `lobehub`, `browse-sh`, `nvidia`, `openai`, `anthropic`, `huggingface`, `voltagent`, `gstack`, `minimax` (default `all`), help `Filter by source or provider (e.g. nvidia, openai) (default: all)`.
- **Outputs / side effects:** Network reads only (with a disk index cache under `~/.hermes/skills/.hub/index-cache`). Live spinner `Fetching skills from registries...` updated with `done: <source> (<count>)` per source. Header `Skills Hub — Browse — <source|all sources>  (<N> skills loaded[, <K> source(s) still loading], page P/T)`. On page 1 when official results exist: `★ <n> official optional skill(s) from Nous Research`. Table columns: `#`, `Name`, `Description`, `Source`, `Trust`, `Identifier` (trust cell shows `★ official` for official results). Navigation hints `--page <n> ← prev` / `--page <n> → next`. With `--source all`: `Sources: <id>: <count>, …`. If sources timed out: `⚡ Slow sources skipped: <ids> — run again for cached results`. Footer tip: `Tip: 'hermes skills inspect <identifier>' to preview, 'hermes skills install <identifier>' to install, 'hermes skills search <query>' to search deeper`. Empty result: `No skills found in the Skills Hub.`; empty provider filter: `No skills found for provider '<source>'.`
- **Config / env:** `GITHUB_TOKEN` (rate limit). Index cache dir `HUB_DIR/index-cache` (`tools/skills_hub.py:97`).
- **Edge cases / guards:** 30 s overall timeout across sources; page clamped into `1..total_pages`; description truncated to 44 chars with `...`; `overflow="fold"` on the Identifier column so long browse-sh slugs (which end in a `-XXXXXX` hash that is part of the identifier) stay copy-pasteable.
- **Rebuild notes:** Fan out to sources in threads with a global deadline and a per-source cap; dedupe on identifier by trust; sort official-first. A better version would stream rows as sources resolve and cache the merged index with an ETag so browse is instant offline.

### Search skill registries  `id: cli-e.skills-search`
- **Surface:** CLI
- **Where:** `hermes skills search [-h] [--source {…15 choices…}] [--limit LIMIT] [--json] query`
- **What it does:** Full-text searches all (or one) registry for skills matching a query and prints a table, or JSON for scripting.
- **How it works:** `do_search` (`hermes_cli/skills_hub.py:303`) → `tools.skills_hub.unified_search(query, sources, source_filter=source, limit=limit)`. With `--json` it skips the Rich status spinner entirely (so stdout stays parseable) and prints `json.dumps(payload, indent=2)` where each record is `{name, identifier, source, trust_level, description}`.
- **Inputs / options:** `-h, --help`; positional `query` = `Search query`; `--source` = same 15 choices as `browse`, default `all`, help `Filter by source or provider (e.g. nvidia, openai)`; `--limit LIMIT` = `Max results` (int, argparse default 25 — note the function signature default is 10, `skills_hub.py:303`); `--json` = `Output JSON instead of a table (full identifiers, scripting-friendly)`.
- **Outputs / side effects:** Table titled `Skills Hub — <N> result(s)` with columns `Name`, `Description` (truncated to 60 chars + `...`), `Source`, `Trust`, `Identifier`. Preceded by `Searching for: <query>` and the status `Searching registries...`. Footer: `Use: hermes skills inspect <identifier> to preview, hermes skills install <identifier> to install (--json for scripting)`. No results: `No skills found matching your query.`
- **Config / env:** `GITHUB_TOKEN`.
- **Edge cases / guards:** `_display_source` re-labels GitHub-tap rows with their `extra.provider` (e.g. `NVIDIA`) instead of the generic `github`. Trust colouring map: `builtin`→bright_cyan, `trusted`→green, `community`→yellow; `official` source displays the literal label `official`.
- **Rebuild notes:** Return the *full* identifier in machine output; never ellipsis-truncate it in the table.

### Install a skill  `id: cli-e.skills-install`
- **Surface:** CLI
- **Where:** `hermes skills install [-h] [--category CATEGORY] [--name NAME] [--force] [--yes] identifier`
- **What it does:** Fetches a skill bundle from whichever registry owns the identifier, quarantines it, security-scans it, asks you to confirm, then installs it under `~/.hermes/skills/[<category>/]<name>/`.
- **How it works:** `do_install` (`hermes_cli/skills_hub.py:543`). Pipeline: `ensure_hub_dirs()` → source router → optional `source_id` pin (`_source_matches`) → if the identifier has no `/`, `_resolve_short_name` searches all sources for an exact name match (official catalog wins ties) → `_resolve_source_meta_and_bundle` takes metadata **and** bundle from the same adapter → URL-source name resolution (see below) → optional interactive category prompt for URL sources → official sources auto-derive the category from the identifier segments between `official` and the slug → "already installed" check against `HubLockFile` → `quarantine_bundle(bundle)` (into `~/.hermes/skills/.hub/quarantine/`) → `scan_skill_cached(q_path, source=…, source_url=source_url_for_bundle(bundle), cache_dir=HUB_DIR/"scan-cache")` → `should_allow_install(result, force)` → advisory Tier-1 SkillEvaluator scan → upstream-metadata panel → confirm prompt → `install_from_quarantine(q_path, name, category, bundle, result)` → blueprint detection → prompt-cache invalidation.
- **Inputs / options:** `-h, --help`; positional `identifier` = `Skill identifier (e.g. openai/skills/skill-creator) or a direct HTTP(S) URL to a SKILL.md file`; `--category CATEGORY` = `Category folder to install into` (default `""`); `--name NAME` = `Override the skill name (useful when installing from a URL whose SKILL.md has no `name:` frontmatter)` (default `""`); `--force` = `Install despite blocked scan verdict` (also required to reinstall over an existing install); `--yes, -y` = `Skip confirmation prompt (needed in TUI mode)`. Interactive prompts: `Name: ` (when a URL skill has no frontmatter name, valid pattern `^[a-z][a-z0-9_-]*$`, rejecting `skill`/`readme`/`index`/`unnamed-skill`), `Category: ` (pattern `^[a-z][a-z0-9_/-]*$`, blank = flat install), and `Confirm [y/N]: `.
- **Outputs / side effects:** Creates `~/.hermes/skills/[<category>/]<name>/`, writes the hub lockfile `~/.hermes/skills/.hub/lock.json`, appends to `~/.hermes/skills/.hub/audit.log` (actions `BLOCKED` on invalid path / blocked verdict), writes the scan cache. Console output in order: `Fetching: <identifier>`; `Quarantined to <relative path>`; `Running security scan...`; the scan report; `Scan provenance: fresh|cached; scanner <version>; hash <bundle_hash>`; `Source: <source_url>; scanned <ts>; rules: <rules|none>`; optional `SkillEvaluator Tier 1 (advisory)` panel; optional `Upstream Metadata` panel; the confirmation panel (title `Official Skill` with body `This is an official optional skill maintained by Nous Research.` … `Files will be at: <HERMES_HOME>/skills/<cat>/<name>/`, or title `Disclaimer` with body `You are installing a third-party skill at your own risk.` / `External skills can contain instructions that influence agent behavior, shell commands, and scripts. Even after automated scanning, you should review the installed files before use.`); `Install '<name>'?`; then `Installed: <path relative to skills dir>` and `Files: <comma-separated file list>`. If the skill declares a `metadata.hermes.blueprint`, prints `Blueprint: '<name>' is an automation (schedule <schedule>).` + `Added to your suggestions — run /suggestions to schedule or dismiss it.` (or the "wasn't added" variant + `You can still schedule it any time by asking the agent or via hermes cron add.`). Finally clears the skills system-prompt cache via `agent.prompt_builder.clear_skills_system_prompt_cache(clear_snapshot=True)`.
- **Config / env:** `skills.tier1_advisory` (gates the advisory scan), `GITHUB_TOKEN`. Paths: `SKILLS_DIR=~/.hermes/skills`, `HUB_DIR=SKILLS_DIR/.hub`, `LOCK_FILE=HUB_DIR/lock.json`, `QUARANTINE_DIR=HUB_DIR/quarantine`, `AUDIT_LOG=HUB_DIR/audit.log`, `TAPS_FILE=HUB_DIR/taps.json`, `INDEX_CACHE_DIR=HUB_DIR/index-cache` (`tools/skills_hub.py:63-99`).
- **Edge cases / guards:** Ambiguous short name → prints `Multiple skills named '<name>' found:` with a Source/Trust/Identifier table and `Use the full identifier to install a specific one.`; no exact match but partial hits → `No exact match for '<name>'. Did you mean one of these?` + up to 5 suggestions; nothing found → `Error: No skill named '<name>' found in any source.`. Fetch failure prints `Error: Could not fetch '<identifier>' from any source.` and, if any source hit the API cap, the hint `GitHub API rate limit exhausted (unauthenticated: 60 requests/hour).` + `Set GITHUB_TOKEN in your .env or install the gh CLI and run gh auth login to raise the limit to 5,000/hr.`. Already-installed without `--force` → `Warning: '<name>' is already installed at <path>` + `Use --force to reinstall.`. Invalid `--name` → `Invalid --name: <value>. Must be a lowercase identifier (letters, digits, hyphens, underscores; starts with a letter).`. Non-interactive URL install with no name → `Cannot install from URL: <url>` with retry instructions for both `/skills install … --name` and `hermes skills install … --name`. Blocked scan verdict → `Installation blocked: <reason>`, quarantine `rmtree`d, audit entry written. Path-escape in the bundle → `Installation blocked: <ValueError>` with audit reason `invalid_path`. Declining the confirm prompt (or EOF/Ctrl-C) → `Installation cancelled.` and quarantine removed.
- **Rebuild notes:** Quarantine → scan → policy gate → explicit confirm → atomic move is the minimum. Record `source`, `identifier`, `install_path`, `content_hash` and `trust_level` in the lockfile so update can pin provenance. A better version would verify a publisher signature and diff the bundle against the previously installed hash before overwriting.

- **Surface:** CLI
- **Where:** `hermes skills inspect [-h] identifier`
- **What it does:** Shows a skill's metadata and the first 50 lines of its `SKILL.md` without writing anything to disk.

The programmatic twin `inspect_skill(identifier)` (`skills_hub.py:954`) returns `{name, description, source, identifier, tags, skill_md_preview}` for the TUI gateway.
- **Inputs / options:** `-h, --help`; positional `identifier` = `Skill identifier`.
- **Outputs / side effects:** Read-only. Second panel titled `SKILL.md Preview` with subtitle `hermes skills install <id> to install`; truncated previews append `... (<n> more lines)`.
- **Config / env:** `GITHUB_TOKEN`.

### List installed skills  `id: cli-e.skills-list`
- **Surface:** CLI
- **Where:** `hermes skills list [-h] [--source {all,hub,builtin,local}] [--enabled-only]`
- **What it does:** Tabulates every skill currently on disk for the active profile, annotating where it came from and whether it is enabled.
- **How it works:** `do_list` (`hermes_cli/skills_hub.py:992`). Reads `HubLockFile().list_installed()` for hub skills, `tools.skills_sync._read_manifest()` for bundled/builtin names, `tools.skills_tool._find_all_skills(skip_disabled=True)` for what's on disk, and `agent.skill_utils.get_disabled_skill_names()` for the disabled set. Classification: in the lockfile → `hub` (source/trust from lockfile), in the bundled manifest → `builtin`, otherwise → `local`.
- **Inputs / options:** `-h, --help`; `--source {all,hub,builtin,local}` (default `all`); `--enabled-only` = `Hide disabled skills. Use with -p <profile> to see exactly which skills will load for that profile.`
- **Outputs / side effects:** Read-only. Table titled `Installed Skills` (or `Installed Skills (enabled only)`), columns `Name`, `Category`, `Source`, `Trust`, `Status` (`enabled` green / `disabled` dim red). Summary line `<h> hub-installed, <b> builtin, <l> local — <e> enabled, <d> disabled` (with `--enabled-only`: `— <e> enabled shown`).
- **Config / env:** `skills.disabled`, `skills.platform_disabled`. The `-p <profile>` global flag swaps `HERMES_HOME` at process start, so this command reads that profile's config with no extra flag.
- **Edge cases / guards:** Skills sorted by `(category, name)`. `trust` label for lockfile source `official` renders as `official`.
- **Rebuild notes:** Keep three provenance buckets (managed/bundled/hand-written) and show enabled state resolved against the active profile.

### Update hub skills  `id: cli-e.skills-update`
- **Surface:** CLI
- **Where:** `hermes skills update [-h] [--force] [name]`
- **What it does:** Re-installs every hub skill that has an upstream update, skipping any whose local files you have edited.
- **How it works:** `do_update` (`hermes_cli/skills_hub.py:1114`). Filters `check_for_skill_updates` to `status == "update_available"`. For each, unless `--force`, it recomputes `tools.skills_guard.content_hash(skill_path)` and compares to the lockfile's `content_hash`; a mismatch means local edits and the skill is skipped. Otherwise it calls `do_install(identifier, category=<derived from install_path>, force=True, source_id=<lockfile source>)` — the `source_id` pin exists so a bare identifier such as `reddit` cannot be fuzzy-resolved into a same-named skill from a different registry, which would silently rewrite the skill's provenance.
- **Inputs / options:** `-h, --help`; positional `name` (optional) = `Specific skill to update (default: all outdated skills)`; `--force` = `Overwrite skills you have edited locally (they are skipped by default)`.
- **Outputs / side effects:** Overwrites skill directories (`do_install(force=True)` rmtree-replaces), rewrites lockfile entries, appends audit entries. Prints `Updating: <name>` per skill, `Skipping: <name> — you have local edits (update would overwrite them).` for protected ones, `Updated <n> skill(s).`, and when anything was skipped `<n> skill(s) kept your local edits: <names>.` + `Overwrite with: hermes skills update <name> --force`. No updates → `No updates available.`
- **Config / env:** `GITHUB_TOKEN`.
- **Edge cases / guards:** `OSError` while hashing the on-disk copy falls back to treating it as unmodified. Destructive replacement is never a rerun default.
- **Rebuild notes:** Always pin the update to the recorded source adapter; treat a content-hash mismatch as "user owns this file now".

### Re-scan installed skills  `id: cli-e.skills-audit`
- **Surface:** CLI
- **Where:** `hermes skills audit [-h] [--deep] [name]`
- **What it does:** Re-runs the security scanner over already-installed hub skills, optionally adding an AST-level Python diagnostic.
- **How it works:** `do_audit` (`hermes_cli/skills_hub.py:1183`). ### Bundles command group  `id: cli-e.bundles`
- **Surface:** CLI

- **How it works:** Parser registered at `hermes_cli/main.py:13718-13729`: the top-level parser is created in `main.py`, then `hermes_cli/bundles.py:167` `register_cli(bundles_parser)` attaches the five sub-parsers (each sets `_bundles_handler`) and calls `scan_bundles()` so a fresh scan happens whenever any bundles sub-command runs. - **Edge cases / guards:** A bundle file that is unreadable, invalid YAML, not a mapping, nameless, or has an empty/missing `skills` list is logged at WARNING and skipped — a broken bundle never breaks slash-command discovery. - **Rebuild notes:** A bundle is `{name, skills[], description?, instruction?}` in YAML; slugify the name for the slash command; invalidate a mtime-keyed cache on write. A better version would validate that each referenced skill actually exists at save time and warn about dangling references.

### Install a plugin  `id: cli-e.plugins-install`
- **Surface:** CLI
- **Where:** `hermes plugins install [-h] [--force] [--ref COMMIT_SHA] [--enable | --no-enable] identifier`
- **What it does:** Clones a plugin from Git (or resolves a bare name through the community index), security-scans it, installs it into `~/.hermes/plugins/<name>/`, collects any required env vars, and optionally enables it.
- **How it works:** `cmd_install` (`hermes_cli/plugins_cmd.py:952`) → `_install_plugin_core` (`plugins_cmd.py:715`). Identifier resolution `_resolve_git_url` (`plugins_cmd.py:226`) accepts: full `https://…/owner/repo.git`; `git@host:owner/repo.git`; `ssh://…`; `file://…`; GitHub browser URLs whose third path segment is one of `actions`, `blob`, `commit`, `commits`, `issues`, `pull`, `pulls`, `releases`, `tree`, `wiki` (a `tree` URL contributes the sub-directory); `owner/repo` shorthand; `owner/repo/path/to/plugin`; `<url>.git/path/to/plugin`; and `<url>#path/to/plugin` for any scheme. Bare names (no slash, no scheme) go through `_resolve_index_name` (`plugins_cmd.py:906`). Clone is `git clone --depth 1` (plus `--no-checkout` when a revision is pinned) with a 60-second timeout, `stdin=DEVNULL` and a non-interactive git env; the cloned `origin` is then scrubbed of credentials (`_scrub_cloned_origin`). Manifests: `plugin.yaml`/`plugin.yml` (native) or `plugin.json` (portable Agent Plugins v1, read via `hermes_cli/agent_plugins.read_agent_plugin_manifest`). `manifest_version` is checked against `_SUPPORTED_MANIFEST_VERSION = 1`. The clone is scanned by `tools/plugin_guard.scan_plugin` **before** anything moves into place, then swapped in with `os.replace` with rollback of both the directory and the metadata file on failure.
- **Inputs / options:** `-h, --help`; positional `identifier` = `Git URL, owner/repo shorthand (e.g. anpicasso/hermes-plugin-chrome-profiles), or a bare plugin name resolved through the community index (see `hermes plugins search`)`; `--force, -f` = `Remove existing plugin and reinstall`; `--ref COMMIT_SHA` = `Install exactly one immutable 40-character Git commit SHA`; mutually exclusive `--enable` = `Auto-enable the plugin after install (skip confirmation prompt)` and `--no-enable` = `Install disabled (skip confirmation prompt); enable later with `hermes plugins enable <name>``. Interactive prompts: `  Install anyway? Only continue if you trust the source. [y/N]: ` (caution verdict), one prompt per missing `requires_env` entry (`  <NAME>: `, masked when the spec has `secret: true`), `  Enable '<name>' now? [y/N]: `, and `  Grant these capabilities? [y/N] `.
- **Outputs / side effects:** Creates `~/.hermes/plugins/<name>/`; writes `~/.hermes/plugins/.install-metadata.json`; copies every `*.example` file to its real name when the target does not exist (printing `  Created <real> from <example>`); may write secrets to `<HERMES_HOME>/.env` via `save_env_value` and set them in `os.environ`; may write `plugins.enabled`/`plugins.disabled` and `plugins.entries.<id>.granted_capabilities`. Console: `Cloning <url>...` (or `Cloning <url> (subdir: <p>)...`); on `http://`/`file://` the warning `Warning: Using insecure/local URL scheme. Consider using https:// or git@ for production installs.`; the declared-dependency block `<plugin> declares Python dependencies (not installed automatically):` with `  - <dep>` lines and `Install them yourself if needed: pip install '<dep>' …`; the plugin's `after-install.md` rendered as Markdown in a green panel, or the default panel titled `✓ Installed` containing `Plugin installed: <identifier>` and `Location: <dir>`; then either `✓ Plugin <name> enabled.` or `Plugin installed but not enabled. Run `hermes plugins enable <name>` to activate.`; the capability-consent screen; finally `Restart the gateway for the plugin to take effect:` + `  hermes gateway restart`.
- **Config / env:** `plugins.scan_on_install`, `plugins.index_url`, `plugins.enabled`, `plugins.disabled`, `plugins.entries.*`. Env vars declared by the plugin's `requires_env` are written to `<HERMES_HOME>/.env`.
- **Edge cases / guards:** `git` missing → `git is not installed or not in PATH.`; clone timeout → `Git clone timed out after 60 seconds.`; clone failure → `Git clone failed:\n<scrubbed stderr>`. Path-traversal in the derived plugin name → `Invalid plugin name '<n>': …` (rejects `/`, `\`, `..`, names resolving to or outside the plugins dir). Sub-directory traversal is rejected by `_resolve_subdir_within`. Existing plugin without `--force` → `Plugin '<n>' already exists. Use force reinstall or run `hermes plugins update <n>`.` A pinned plugin cannot be moved implicitly: `Plugin '<n>' is pinned. Reinstall it with an explicit --ref <40-character commit SHA> to change its source or revision.` Re-installing the same source keeps its pin even if the directory was deleted by hand. `manifest_version` above 1 → `Plugin '<n>' requires manifest_version <v>, but this installer only supports up to 1. Run <update command> to update Hermes.` Scan verdicts: `safe` → proceed, `caution` → needs `--force` or interactive acceptance, `dangerous` → always blocked with `Blocked: Security scan blocked plugin install: <reason>` plus the report and `Review the findings above. Install only plugins from sources you trust. (Scanning can be configured via plugins.scan_on_install in config.yaml.)`; exit 1. A missing `plugin.yaml`/`plugin.json`/`__init__.py` produces `Warning: <n> doesn't contain plugin.yaml, plugin.json, or __init__.py. It may not be a valid Hermes plugin.` Non-interactive sessions never grant capabilities (fail closed) and never auto-enable. `--ref` must match `^[0-9a-fA-F]{40}$`.
- **Rebuild notes:** Clone to a temp dir inside the target directory (so the final move is same-filesystem and atomic), scan before moving, then `os.replace` with a rollback path that restores both the tree and the metadata. A better version would run plugins out-of-process with a real capability sandbox rather than consent-only.

### Enable a plugin  `id: cli-e.plugins-enable`
- **Surface:** CLI
- **Where:** `hermes plugins enable [-h] [--allow-tool-override | --no-allow-tool-override] name`
- **What it does:** Adds a plugin to `plugins.enabled`, clears every form of it from `plugins.disabled`, and runs the capability-consent screen.
- **How it works:** `cmd_enable` (`hermes_cli/plugins_cmd.py:1405`). Resolves `name` to the canonical key via `_resolve_plugin_key_and_source` (accepts the manifest name, directory name, or full `category/name` key). On enable it discards the key, its bare leaf, **and** the manifest name from the disabled list, because the loader's disable check matches on both forms (#40190). Bundled plugins are trusted and skip the tool-override prompt entirely. For everything else, a manifest that declares `capabilities:` routes through `_run_capability_consent` (which also covers `tools.override`); the legacy standalone tool-override prompt runs only when the manifest declares nothing or the operator passed an explicit flag.
- **Inputs / options:** `-h, --help`; positional `name` = `Plugin name to enable`; mutually exclusive `--allow-tool-override` = `Grant this plugin permission to replace built-in tools (e.g. shell_exec, write_file). Skips the confirmation prompt.` and `--no-allow-tool-override` = `Enable without granting built-in tool override (skip prompt).` Interactive prompts: `  Grant these capabilities? ### Install a plugin pack  `id: cli-e.plugins-pack-install`
- **Surface:** CLI
- **Where:** `hermes plugins pack install [-h] [--force] source` (group `hermes plugins pack [-h] {install,export,show} ...`, description verbatim: `Install, export, or inspect plugin packs — a single YAML file pinning a set of plugins to exact commit SHAs, with optional non-secret config seeds. - **What it does:** Reads a `hermes-pack.yaml`, shows a mandatory review screen of every plugin, pinned SHA and config seed, asks once for consent, then installs each plugin as an ordinary pinned install.
- **How it works:** `cmd_pack_install` (`hermes_cli/plugin_packs.py:674`) → `load_pack` → `resolve_pack_plugins` → `render_pack_review` → confirm → `install_pack_plugins` (`plugin_packs.py:448`). Pack schema (`parse_pack`, `plugin_packs.py:180`): top-level or nested-under-`pack:` `name` (required), `description`, `author`, `version`; a non-empty `plugins:` list where each entry needs `name` (community index) **or** `repo`/`source` (`owner/repo`, `github:` prefix stripped), a `ref`/`version` that must match `^[0-9a-fA-F]{40}$`, and an optional `subdir`; an optional `config:` mapping of plugin id → non-secret settings; an optional `skills:` list. Config seeds are validated by `validate_config_seed` (`plugin_packs.py:148`) which rejects the reserved entry keys `granted_capabilities` and `capabilities_consent` and secret-looking keys (`_SECRET_KEY_RE`, `plugin_packs.py:56`). Pack payloads are capped at 1 MiB with a 15 s fetch timeout.
- **Inputs / options:** `-h, --help`; positional `source` = `Path to a hermes-pack.yaml file, or an https:// URL`; `--force, -f` = `Reinstall plugins that already exist`. Interactive prompt: `Install <n> plugin(s) from pack '<name>'? [y/N] `, followed by the per-plugin capability consent prompts.
- **Outputs / side effects:** Installs N plugins (each with the full install pipeline and pinned ref), seeds `plugins.entries.<id>.*` from the pack's `config:` block. Review screen: header `<name> v<version> — by <author>`, the description, a table with columns `Plugin`, `Source`, `Pinned ref` (12-char prefix), `Capabilities (declared)` (or `(shown at install)`); then `Config seeds (plugins.entries.<id>, non-secret):` with `  <id>.<key> = <value!r>` lines; then, when the pack lists skills, `Pack lists skills (NOT auto-installed yet): <ids>` + `Install them manually, e.g. `hermes skills install <id>`.`; then `Installing a pack runs third-party code × <n> plugins. Each plugin's declared capabilities still require individual consent after install — a pack never bulk-grants.` Result line `Pack '<name>': <ok> installed, <failed> failed.` with `  ✗ <display>: <error>` per failure, then `Restart the gateway for the plugins to take effect:` + `  hermes gateway restart`.
- **Config / env:** `plugins.entries.<id>.*` (config seeds), `plugins.index_url` (for `name:` entries).
- **Edge cases / guards:** Any parse problem raises `PackError` printed as `Error: <msg>` + exit 1 — including non-YAML, non-mapping, missing `name`, empty `plugins` list, an entry with neither `name` nor `repo`, an invalid `subdir`, and (most importantly) `Pack plugin entry <label> has ref <r>: refs must be exact 40-character commit SHAs (tags and branch names are rejected — pin the commit for reproducible installs).` Non-interactive session → `Error: Pack install requires an interactive terminal to review and confirm the pack contents (no --yes in v1).` + exit 1. Declining → `Aborted — nothing installed.` + exit 1. Any failed plugin makes the command exit 1.
- **Rebuild notes:** Require exact SHAs so a pack is reproducible; keep capability consent per plugin so a pack can never bulk-grant. A better version would verify each pinned SHA's signature and support `--yes` behind an explicit trust store.

## 4. `hermes curator` — agent-skill lifecycle curator

### Curator command group  `id: cli-e.curator`
- **Surface:** CLI
- **Where:** `hermes curator [-h] {status,usage,run,pause,resume,pin,unpin,list-unmanaged,adopt,restore,list-archived,archive,prune,backup,rollback,ledger,purge} ...`. Description (verbatim): `The curator is an auxiliary-model background task that periodically reviews agent-created skills, prunes stale ones, consolidates overlaps, and archives obsolete skills. Bundled and hub-installed skills are never touched. Archives are recoverable; auto-deletion never happens.`
- **What it does:** Controls the background task that ages out agent-authored skills — showing status, forcing a run, pinning/adopting skills, archiving/restoring/pruning/purging them, and rolling back mutations from an audit ledger or a whole-tree snapshot.
- **How it works:** Parser `hermes_cli/curator.py:866` `register_cli(parent)` attaches every sub-command with its own `func`; the group parser's default `func` prints help and returns 0 (`curator.py:871`). Logic lives in `agent/curator.py` (scheduler, state, LLM review), `agent/curator_backup.py` (tar snapshots), `tools/skill_usage.py` (per-skill telemetry, states, archive) and `tools/skill_ledger.py` (per-mutation audit ledger). State files, all under `HERMES_HOME`: `skills/.curator_state` (`agent/curator.py:86`), `skills/.archive/` (`tools/skill_usage.py:124`), `skills/.curator_backups/<utc-iso>/` with a `manifest.json` (`agent/curator_backup.py:72`, excludes `.curator_backups` and `.hub` from snapshots), `skills/.curator_ledger.jsonl` (`tools/skill_ledger.py:105`) and content-addressed blobs in `.curator_backups/blobs/` (`tools/skill_ledger.py:108`). Skill states are `active`, `stale`, `archived`; provenance is `agent`, `bundled` or `hub`; only `created_by: agent` skills are curator-managed.
- **Inputs / options:** `-h, --help`; one of the 17 sub-commands. Their help strings, verbatim: `status` = `Show curator status and skill stats`; `usage` = `Show usage telemetry for ALL skills (built-in, hub, agent) with provenance`; `run` = `Trigger a curator review now`; `pause` = `Pause the curator until resumed`; `resume` = `Resume a paused curator`; `pin` = `Pin a skill so the curator never auto-transitions it`; `unpin` = `Unpin a skill`; `list-unmanaged` = `List curation-eligible skills with no provenance marker`; `adopt` = `Hand unmanaged skills to the curator (provenance is a user declaration)`; `restore` = `Restore an archived skill`; `list-archived` = `List archived skills`; `archive` = `Manually archive a skill (move to .archive/, excluded from prompt)`; `prune` = `Bulk-archive curator-managed skills idle for >= N days (default 90)`; `backup` = `Take a manual tar.gz snapshot of ~/.hermes/skills/ (curator also does this automatically before every real run)`; `rollback` = `Restore ~/.hermes/skills/ from a curator snapshot, or a single mutation by ledger entry id (see `hermes curator ledger`)`; `ledger` = `List the per-mutation skill audit ledger (all actors: curator/agent/user)`; `purge` = `Delete archived skills older than curator.archive_ttl_days (explicit only — never automatic; recorded in the ledger)`.
- **Outputs / side effects:** No sub-command → the group help screen, exit 0.
- **Config / env:** `curator.enabled` (default `true`), `curator.interval_hours` (`168`), `curator.min_idle_hours` (`2`), `curator.stale_after_days` (`30`), `curator.archive_after_days` (`90`), `curator.consolidate` (`false`), `curator.prune_builtins` (`true`), `curator.archive_ttl_days` (`0` = purge disabled), `curator.backup.enabled` (`true`), `curator.backup.keep` (`5`), `skills.ledger` (`true`).
- **Edge cases / guards:** Bundled and hub-installed skills are never auto-transitioned. Auto-deletion never happens — only the explicit `purge` deletes, and even that is ledgered with recoverable blobs.
- **Rebuild notes:** Three storage layers — a state file for the scheduler, per-skill usage telemetry with a state machine (active→stale→archived), and an append-only ledger with content-addressed before/after blobs — make every curator action reversible. A better version would let the user express curation policy per category rather than one global idle threshold.

- **Surface:** CLI

### Rollback (snapshot or single mutation)  `id: cli-e.curator-rollback`
- **Surface:** CLI
- **Where:** `hermes curator rollback [-h] [--list] [--id BACKUP_ID] [-y] [entry_id]`
- **What it does:** Either restores the whole `~/.hermes/skills/` tree from a snapshot, or undoes exactly one ledger mutation by restoring the files it touched.
- **How it works:** `_cmd_rollback` (`hermes_cli/curator.py:677`). With a positional `entry_id` it reads `skill_ledger.get_entry(entry_id)`, shows the entry, confirms, and calls `skill_ledger.rollback_entry(entry_id)` — which takes a pre-rollback safety ledger entry first and fails closed if that capture fails. Without it, it resolves a snapshot via `curator_backup._resolve_backup(backup_id)` (newest by default), reads its `manifest.json`, confirms, and calls `curator_backup.rollback(backup_id=…)`, which first snapshots the current tree into `.curator_backups/pre-rollback-<ts>/` so the rollback itself is undoable.
- **Inputs / options:** `-h, --help`; positional `entry_id` (optional) = `Ledger entry id for single-mutation rollback (from `hermes curator ledger`). Prompts: `Restore this mutation's before-state? [y/N] ` (ledger mode) and `Proceed? [y/N] ` (snapshot mode).
- **Outputs / side effects:** Rewrites skill files; creates a safety snapshot/ledger entry first. Ledger mode prints `Rollback target: ledger entry <id>` then `  action:`, `  skill:`, `  actor:`, `  when:`, `  files:  <n>`. Snapshot mode prints `Rollback target: <snapshot name>` then `  reason:`, `  created_at:`, `  skill files:` and either `  cron jobs:   <n> (will be restored for skill-link fields only)` or `  cron jobs:   not in snapshot (<reason>)`, followed by the warning `This will replace the current ~/.hermes/skills/ tree (a safety snapshot of the current state is taken first so this is undoable). - **Config / env:** `curator.backup.*`, `skills.ledger`.
- **Edge cases / guards:** Unknown ledger id → `curator: no ledger entry '<id>'. See `hermes curator ledger` for entry ids, or use `--id <snapshot>` for whole-tree snapshot rollback.` + exit 1. Cron restoration is scoped to the `skills`/`skill` link fields only; all other cron fields are left alone.
- **Rebuild notes:** Snapshot before every rollback so undo is always available; content-addressed per-file blobs make single-mutation rollback cheap compared to full tarballs.

A better version would cache the manifest on disk with an ETag rather than a 300 s in-process TTL, and would ship a local fallback pet so the feature works fully offline.

### Install a pet  `id: cli-e.pets-install`
- **Surface:** CLI
- **Where:** `hermes pets install [-h] [--force] [--select] slug`
- **What it does:** Downloads the named pet's spritesheet (and `pet.json`) from petdex into `<HERMES_HOME>/pets/<slug>/`, and makes it the active pet if none is active yet.
- **How it works:** `_cmd_install` (`hermes_cli/pets.py:71`) → `store.install_pet(slug, force=…)` (`agent/pet/store.py:151`). Idempotent: an already-complete install short-circuits unless `--force`. The spritesheet host must satisfy `_is_petdex_host` or the install refuses with `refusing non-petdex spritesheet host for '<slug>'`. The file extension is `.png` when the URL path (query stripped) ends in `.png`, else `.webp`; it is written to `pets/<slug>/spritesheet<ext>` with a 60 s timeout (`_DOWNLOAD_TIMEOUT`). `pet.json` is fetched only when `petJsonUrl` is also a petdex host; on failure or an empty body a minimal `{"id": slug, "displayName": …, "description": ""}` is synthesised. `spritesheetPath` is then forced to the local filename and the JSON written with `indent=2`. - **Inputs / options:** `-h, --help`; positional `slug` (required) = `Pet slug (e.g. boba)`; `--force` = `Re-download even if present`; `--select` = `Make it the active pet`.
- **Outputs / side effects:** Creates `<HERMES_HOME>/pets/<slug>/spritesheet.{webp,png}` + `pet.json`; may rewrite `display.pet.slug`/`display.pet.enabled` in `config.yaml`. - **Config / env:** writes `display.pet.slug`, `display.pet.enabled`.
- **Edge cases / guards:** Failure prints `✗ install failed: <exc>` to stderr and exits 1 — sources are `PetStoreError` (invalid slug, unknown slug, non-petdex host, download failure, `install of '<slug>' did not produce a spritesheet`) and `ManifestError`. Slugs are sanitised before touching the filesystem.
- **Rebuild notes:** Download → verify → write manifest → verify again. A stronger version would checksum the asset against a manifest digest and keep the previous spritesheet until the new one validates.

### Animate the pet in the terminal  `id: cli-e.pets-show`
- **Surface:** CLI
- **Where:** `hermes pets show [-h] [--state STATE] [--cycle] [--once] [--mode MODE] [--scale SCALE] [slug]`
- **What it does:** Plays the pet's sprite animation right-aligned in the terminal until Ctrl-C, using the richest graphics protocol the terminal supports.
- **How it works:** `_cmd_show` (`hermes_cli/pets.py:142`). Resolves the pet via `store.resolve_active_pet(slug or display.pet.slug)` — configured slug first, else the first installed pet alphabetically. Mode comes from `--mode`, else `display.pet.render_mode`; scale from `--scale` (non-zero), else `display.pet.scale`, else `DEFAULT_SCALE = 0.33`. Terminal width in cells is `resolve_cols(scale, display.pet.unicode_cols)`: an explicit positive `unicode_cols` wins, otherwise `cols_for_scale(scale) = max(UNICODE_MIN_COLS=16, round(24 * scale))` where `24 = FRAME_W//8` (`agent/pet/constants.py:52-75`). `build_renderer` (`agent/pet/render.py:683`) → `resolve_mode` (`render.py:109`) → `detect_terminal_graphics` (`render.py:48`): the detector is env-based only (never issues a DA1 query that could hang a pipe); `TERM_PROGRAM=vscode` is forced to `unicode` (VS Code/Cursor leak `ITERM_SESSION_ID`/`KITTY_WINDOW_ID` from the launching emulator); `KITTY_WINDOW_ID` or `kitty`/`ghostty` in `TERM` → `kitty`; unknown → `unicode`. Not attached to a TTY → mode `off`. Frame timing: `frame_delay = max(0.05, (LOOP_MS/1000)/frame_count)` with `LOOP_MS = 1100`. Half-block mode indents each row by `term_cols - cols - 1` and redraws in place with `ESC[<n>F`; graphics modes clear with `ESC[2J ESC[3J ESC[H`, print `"<display name> [<state>]"`, pad the cursor by `term_cols - (frame_w*scale)//8 - 1` and emit the image at the cursor. The cursor is hidden (`ESC[?25l`) for the duration and restored in `finally`.
- **Inputs / options:** `-h, --help`; positional `slug` (optional, default `""`) = `Pet slug (default: active)`; `--state STATE` (default `""`) = `Single state: idle/run/review/failed/wave/jump`; `--cycle` = `Cycle through all states`; `--once` = `Play once instead of looping`; `--mode MODE` (default `None`) = `Override render mode (kitty/iterm/sixel/unicode/auto)` — accepted values are the `RENDER_MODES` tuple `("auto", "kitty", "iterm", "sixel", "unicode", "off")` (`render.py:41`), anything else falls back to `unicode` inside `PetRenderer`; `--scale SCALE` (float, default `0`) = `Override scale (0 = config)`. Keyboard: **Ctrl-C** stops the loop cleanly.
- **Outputs / side effects:** Terminal-only. Header line `<display name> — mode=<mode>  (Ctrl+C to stop)`. States: with `--state` exactly that one; with `--cycle` every row of `STATE_ROWS` that is also a `PetState` value; otherwise just `idle`. `STATE_ROWS` defaults to the 9-row Codex taxonomy `["idle","running-right","running-left","waving","jumping","failed","waiting","running","review"]`; the legacy 8-row taxonomy is `["idle","wave","run","failed","review","jump","extra1","extra2"]` and is picked automatically for sheets with fewer rows (`state_rows_for_grid`, `constants.py:147`). `PetState` enum values: `idle`, `wave`, `run`, `failed`, `review`, `jump`, `waiting`.
- **Config / env:** `display.pet.slug`, `display.pet.render_mode`, `display.pet.scale`, `display.pet.unicode_cols`; env `TERM`, `TERM_PROGRAM`, `KITTY_WINDOW_ID` feed graphics detection.
- **Edge cases / guards:** No resolvable pet → `✗ no pet to show — run: hermes pets install boba` (stderr, exit 1). Renderer unavailable (no TTY / graphics disabled) → `✗ cannot render here (no TTY / graphics disabled). Effective mode: <mode>.` (exit 1). Scale is clamped to `[0.1, 3.0]` by `clamp_scale`; the half-block renderer additionally clamps to `UNICODE_MIN_COLS = 16` because a 192×208 sprite sampled at 1 horizontal + 2 vertical taps per cell becomes unreadable below that. Sprite decoding needs Pillow.
- **Rebuild notes:** Sprite atlas (192×208 cells, 6 frames stepped per state) + per-protocol encoder + an in-place redraw loop. A better version would sync the animation state to live agent activity instead of a fixed cycle, and negotiate the protocol with a real DA1 query behind a timeout.

## 6. `hermes journey` (aliases `learning`, `memory-graph`) — learning timeline

### Journey timeline (default action)  `id: cli-e.journey`
- **Surface:** CLI
- **Where:** `hermes journey [-h] [--reveal 0..1] [--play] [--fps FPS] [--width WIDTH] [--height HEIGHT] [--no-color] [--json] {list,delete,edit} ...`. - **What it does:** Renders, in the terminal, everything Hermes has *learned* — profile skills that were agent-created or actually used, plus every memory card from `MEMORY.md`/`USER.md` — as a date-bucketed bar chart with a legend, a date axis, a "charted signals" label list, a cumulative trajectory sparkline and a summary footer.

Layout: width/height default to `shutil.get_terminal_size((90, 30))` floored at 40 cols / 10 rows; content width is `cols - 2` (rows are `pad_left(2)`); the chart field gets `max(6, rows - 10 - len(summary))` rows.
- **Inputs / options:** `-h, --help`; `--reveal 0..1` (float, default `1.0`) = `Render the timeline built up to this point (0=oldest, 1=now).`; `--play` = `Animate the build-up over time (Ctrl-C to stop).`; `--fps FPS` (int, default `12`) = `Animation frames per second for --play (default 12).`; `--width WIDTH` (int, default `None`) = `Override render width in columns.`; `--height HEIGHT` (int, default `None`) = `Override render height in rows.`; `--no-color` = `Disable color output.`; `--json` = `Print the raw graph payload as JSON and exit.`; `--force-color` = hidden flag (`argparse.SUPPRESS`, `journey.py:385`) that forces truecolor ANSI even into a captured stream, used when the interactive CLI re-renders the output through prompt_toolkit. Sub-commands: `list`, `delete`, `edit`. Keyboard during `--play`: **Ctrl-C** stops.
- **Outputs / side effects:** Read-only. The frame is: title `✦ Journey ` + `· learned skills & memories over time` (title colour `#E8C463`); a legend line `● skills (<n>)   ◆ memories (<n>)`; an optional category line of up to 4 `● <category> (<count>)` entries plus `· +<hidden>`; a blank line; the chart grid; a date axis with `axis["start"]` left and `axis["end"]` right (`oldest`/`now` when timestamps are not spread); the playhead footer `◷ <date or —>   <visible>/<total> revealed · <pct>%`; then, when present, a blank line, `  charted signals` and up to 6 rows of `<key> <glyph> <label>  <meta truncated to 32 chars with …>`; finally the summary lines `<n> learned skills · <n> memories · <n> skill links` and optionally `<n> memory↔skill links · busiest day <label> · <n> learned`. `--json` prints the whole payload (`nodes`, `edges`, `clusters`, `memory`, `stats`) through Rich's `print_json`. `--play` renders 42 frames from `reveal = i/41` to 1.0 in a Rich `Live` region at `refresh_per_second=fps` with `delay = 1/max(1, min(60, fps))`.
- **Config / env:** no dedicated config keys; the palette follows the active skin (`hermes_cli.skin_engine.get_active_skin`). Reads `<HERMES_HOME>/skills/`, `<HERMES_HOME>/skills/.usage.json`, `<HERMES_HOME>/memories/MEMORY.md`, `<HERMES_HOME>/memories/USER.md` and the repo's bundled `skills/`.
- **Edge cases / guards:** Empty graph → `No learning yet — use Hermes a while and your learned skills and memories will start mapping out here.` and exit 0. `--reveal` is clamped to `[0, 1]`. - **Rebuild notes:** Build a node list `{id, label, kind, timestamp, category, useCount, state, createdBy, pinned}`, bucket by date, draw proportional bars, derive colours from one primary hex, and gate label contrast at 4.5:1. A better version would stream new nodes incrementally instead of rebuilding the whole graph per frame, and would make edges browsable rather than only counted.

- **Rebuild notes:** One parser, three names. Better: echo the invoked name in usage strings so copy-pasted help is directly runnable.

### List journey node ids  `id: cli-e.journey-list`
- **Surface:** CLI
- **Where:** `hermes journey list [-h] [--no-color]` (also `hermes learning list`, `hermes memory-graph list`)
- **What it does:** Prints every graph node with its stable id, kind glyph, label and date — the lookup table you need before `journey delete` or `journey edit`.
- **How it works:** `_cmd_list` (`hermes_cli/journey.py:296`) builds the same payload and sorts nodes by `timestamp` ascending (missing timestamps sort as `0`). Ids are stable by construction: a skill node's id is the skill name; a memory node's id is `memory:<source>:<global index>` where `source` is `memory` (`MEMORY.md`) or `profile` (`USER.md`) and the index is the position in the combined card list — all `MEMORY.md` cards first, then `USER.md` (`agent/learning_mutations.py:3-9`). Dates go through `format_date` (`learning_graph_render.py:72`) → `"<day> <Mon> <Year>"` in UTC, or `unknown`.
- **Inputs / options:** `-h, --help`; `--no-color` (no help text in the dump); hidden `--force-color` (`argparse.SUPPRESS`, `journey.py:393`).
- **Outputs / side effects:** Read-only. One line per node: `<id>  <glyph> <label>  <date>` where `<glyph>` is `◆` for `kind == "memory"` and `●` otherwise; the id and date are rendered in `grey54`. Empty graph → `No learning yet.`. Always exits 0.
- **Config / env:** none.
- **Edge cases / guards:** Memory ids are **positional** — deleting or adding a memory renumbers everything after it, so an id captured from an earlier listing can go stale; the mutation layer detects this and answers `memory node id is stale — refresh the graph`.
- **Rebuild notes:** Sort + print. Better: give memory cards a content hash id so ids survive edits to neighbouring cards.

### Delete a journey node  `id: cli-e.journey-delete`
- **Surface:** CLI
- **Where:** `hermes journey delete [-h] [-y] node` (also under the `learning` / `memory-graph` aliases)
- **What it does:** Archives a learned skill (recoverable) or permanently removes one memory card from `MEMORY.md`/`USER.md`, after a confirmation prompt.
- **How it works:** `_cmd_delete` (`hermes_cli/journey.py:311`) first calls `agent.learning_mutations.node_detail(node)` to resolve and label the target, prompts unless `-y`, then `delete_node(node)` (`learning_mutations.py:124`). Skills: `_delete_skill` refuses when `tools.skill_usage.get_record(name)["pinned"]` is truthy, otherwise `skill_usage.archive_skill(name)` moves the skill into the curator archive and `_clear_skill_cache()` invalidates the skills system-prompt cache (`agent.prompt_builder.clear_skills_system_prompt_cache(clear_snapshot=True)`). Memories: `_delete_memory` parses `memory:<source>:<index>`, maps the global index to the file-local one (`_memory_local_index`, subtracting the `MEMORY.md` card count for `profile` cards), reads the chunk list with `tools.memory_tool.MemoryStore._read_file` — the same parser the memory tool uses, so indices stay aligned — deletes the entry, and writes the file back atomically through `MemoryStore._write_file` (temp file + rename, `§`-joined, blank chunks dropped).
- **Inputs / options:** `-h, --help`; positional `node` (required) = `Node id (skill name or memory:<source>:<index>; see \`journey list\`).`; `-y, --yes` = `Skip the confirmation prompt.`. Prompt: `  Delete '<label>'? [y/N] ` — only `y`/`yes` (case-insensitive) proceed.
- **Outputs / side effects:** Skills: the skill directory moves to the archive and the ledger records it; prints `  archived '<name>' — restore with: hermes curator restore <name>`. Memories: `MEMORY.md` or `USER.md` is rewritten; prints `  deleted memory from <filename>`. Exit 0 on success, 1 on failure/abort.
- **Config / env:** `<HERMES_HOME>/memories/MEMORY.md`, `<HERMES_HOME>/memories/USER.md`, `<HERMES_HOME>/skills/`.
- **Edge cases / guards:** Unknown id → the resolver's message (`skill '<id>' not found`, `SKILL.md missing for '<id>'`, `bad memory node id: <repr>`, `memory index <n> out of range`, `<file> not found`, `memory node id is stale — refresh the graph`) and exit 1. Pinned skill → `'<name>' is pinned — unpin it first (hermes curator unpin <name>)` and exit 1. EOF/Ctrl-C at the prompt → `\n  aborted` and exit 1; answering anything else → `  aborted` and exit 1. Skill deletion is *archival* (undoable with `hermes curator restore`); memory deletion is a real file rewrite and is **not** undoable from here.
- **Rebuild notes:** Resolve id → confirm → archive-or-rewrite, sharing one atomic writer with the memory tool. A better version would snapshot the memory file before rewriting so memory deletion is as recoverable as skill archiving.

### Edit a journey node in $EDITOR  `id: cli-e.journey-edit`
- **Surface:** CLI
- **Where:** `hermes journey edit [-h] node` (also under the `learning` / `memory-graph` aliases)
- **What it does:** Opens the skill's full `SKILL.md` (or the raw memory chunk) in your editor and writes back whatever you save.
- **How it works:** `_cmd_edit` (`hermes_cli/journey.py:331`) resolves the node with `node_detail(node)` — which returns `{ok, kind, id, label, content}` where `content` is the whole `SKILL.md` for skills or the raw `§`-chunk for memories — picks the temp-file suffix (`.md` for skills, `.txt` for memories), and calls `_open_in_editor` (`journey.py:348`): write to a `tempfile.NamedTemporaryFile(delete=False)`, `subprocess.call([*editor.split(), path])`, read it back, then unlink in `finally`. The editor is `$EDITOR`, else `$VISUAL`, else `vi`. Unchanged content (after `.strip()` comparison) short-circuits. Skills go through `tools.skill_manager_tool._edit_skill` (and invalidate the skills prompt cache); memories replace the chunk in place and rewrite the file atomically via `MemoryStore._write_file`.
- **Inputs / options:** `-h, --help`; positional `node` (required) = `Node id (skill name or memory:<source>:<index>; see \`journey list\`).`. No `--yes`/dry-run — saving in the editor *is* the confirmation.
- **Outputs / side effects:** Rewrites `<skill dir>/SKILL.md` or one chunk of `MEMORY.md`/`USER.md`. Prints `  no changes`, `  updated '<name>'` (skill), `  updated memory in <filename>` (memory), or the failure message. Exit 0 on success or no-change, 1 on failure.
- **Config / env:** env `EDITOR`, `VISUAL`; files under `<HERMES_HOME>/skills/` and `<HERMES_HOME>/memories/`.
- **Edge cases / guards:** Saving an empty memory is refused with `empty memory — use delete to remove it` (exit 1) — you cannot delete via edit. An editor that cannot be spawned prints `  editor failed: <OSError>` and is treated as "no changes". A stale memory index raises the same staleness message as delete. The temp file is always removed, even when the editor exits non-zero.
- **Rebuild notes:** Detail → temp file → `$EDITOR` → diff-check → typed writer. Better: validate skill frontmatter before writing back and refuse a save that breaks the `SKILL.md` schema.

## 7. `hermes memory` — memory provider plugins + built-in memory reset

### Memory command group  `id: cli-e.memory`
- **Surface:** CLI
- **Where:** `hermes memory [-h] {setup,status,off,reset} ...`. Root command-list help line: `Configure external memory provider`. Long description (verbatim): `Set up and manage external memory provider plugins.\n\nAvailable providers: honcho, openviking, mem0, hindsight,\nholographic, retaindb, byterover.\n\nOnly one external provider can be active at a time.\nBuilt-in memory (MEMORY.md/USER.md) is always active.`
- **What it does:** Picks and configures which external memory-provider plugin is active (at most one), reports the current memory posture, turns the external provider off, and erases the built-in memory files.
- **How it works:** Parser `build_memory_parser` (`hermes_cli/subcommands/memory.py:12`), handler `cmd_memory` (`hermes_cli/main.py:12853`). `off` and `reset` are handled inline in `cmd_memory`; everything else (including a bare `hermes memory`) is delegated to `hermes_cli.memory_setup.memory_command` (`memory_setup.py:573`), whose router maps `setup` → `cmd_setup_provider`/`cmd_setup` and *everything else, including no sub-command*, → `cmd_status`. Providers are discovered by `plugins.memory.discover_memory_providers()` (`plugins/memory/__init__.py:261`), which scans bundled provider directories, then user-installed directories, then pip entry points (bundled wins on a name clash), reading each `plugin.yaml` for its description and calling the loaded provider's `is_available()`. `"memory"` is in `_BUILTIN_SUBCOMMANDS`.
- **Inputs / options:** `-h, --help`; sub-commands with verbatim help: `setup` = `Interactive provider selection and configuration`; `status` = `Show current memory provider config`; `off` = `Disable external provider (built-in only)`; `reset` = `Erase all built-in memory (MEMORY.md and USER.md)`.
- **Outputs / side effects:** Writes `memory.provider` (and provider-specific blocks) in `config.yaml`, secrets in `<HERMES_HOME>/.env`, provider-native config files, and can delete `<HERMES_HOME>/memories/*.md`.
- **Config / env:** `memory.provider` (default `""`), `memory.memory_enabled` (`true`), `memory.user_profile_enabled` (`true`), `memory.write_approval` (`false`), `memory.memory_char_limit` (`2200`), `memory.user_char_limit` (`1375`), `memory.nudge_interval` (`10`) — `hermes_cli/config_defaults.py:2057-2084`. Provider bundles shipped in `plugins/memory/`: `byterover`, `hindsight`, `holographic`, `honcho`, `mem0`, `openviking`, `retaindb`, `supermemory` (the help text names the seven the description was written for; `supermemory` also ships).
- **Edge cases / guards:** Only one external provider can be active; built-in `MEMORY.md`/`USER.md` memory is always present regardless of provider. Nothing in this group can enable/disable the `memory` **toolset** — that lives in `hermes tools`.
- **Rebuild notes:** A one-key activation switch (`memory.provider`) plus per-provider schema-driven setup, with secrets segregated into `.env`. A better version would let providers be layered (e.g. a fast local store in front of a cloud one) and would health-check the active provider on every session start.

### Interactive memory provider setup  `id: cli-e.memory-setup`
- **Surface:** CLI (curses picker + text prompts)
- **Where:** `hermes memory setup [-h] [provider]`
- **What it does:** Shows a curses radio list of every discovered memory-provider plugin plus a "Built-in only" row, installs the chosen provider's pip dependencies, walks its config schema (choices, text, secrets), and activates it.
- **How it works:** With a positional `provider` argument the picker is skipped by `cmd_setup_provider` (`hermes_cli/memory_setup.py:244`): it looks the name up in `_get_available_providers()`, clears the screen, installs dependencies, and — if the provider exposes `post_setup` — hands the whole flow to `provider.post_setup(str(get_hermes_home()), config)`; otherwise it just writes `memory.provider = <name>` and saves. Without an argument, `cmd_setup` (`memory_setup.py:282`) builds the picker rows as `(<name>, "— <setup hint>")` where the hint is derived from the provider's `get_config_schema()`: `API key / local` (both secret and non-secret fields), `requires API key` (secrets only), `no setup needed` (empty schema), else `local`; the last row is `("Built-in only", "— MEMORY.md / USER.md (default)")` and is the pre-selected default. Selection is `_curses_select` (`memory_setup.py:51`) → `hermes_cli.curses_ui.curses_radiolist`, cancel returns `_CANCELLED = -1`. Schema walk, per field: `when` (a dict of field→value) skips non-matching fields; `default_from` resolves a dynamic default by mapping another field's current value through `map`; `choices` renders another curses radio list pre-selected at the current value; `secret: true` prompts through `hermes_cli.secret_prompt.masked_secret_prompt` (showing `(current: ...<last4>, blank to keep)` when the env var is already set, and printing `  Get yours at <url>` when the field declares one) and writes to `.env` under `env_var`; plain fields prompt with the current-or-default value in brackets and also mirror to `.env` when they declare an `env_var`. Non-secret values are handed to `provider.save_config(provider_config, hermes_home)` (its native location); secrets go through `_write_env_vars` (`memory_setup.py:426`). Dependency install: `_install_dependencies(name)` (`memory_setup.py:106`) reads the pip deps declared in the provider's `plugin.yaml`, extended by `_provider_pip_dependencies` (`memory_setup.py:21`) which appends `hindsight-all` when Hindsight's `<HERMES_HOME>/hindsight/config.json` has `mode` in `{"local", "local_embedded"}`.
- **Inputs / options:** `-h, --help`; positional `provider` (optional, default `None`) = `Provider to configure directly (e.g. honcho), skipping the picker`. Picker title: `Memory provider setup`; keys `↑↓ navigate  ENTER/SPACE select  ESC cancel` (from `curses_radiolist`'s hint line, `hermes_cli/curses_ui.py:1035`). Text prompts render as `  <description> [<default>]: `.
- **Outputs / side effects:** Writes `memory.provider` in `config.yaml`; may write a provider-native config file and `<HERMES_HOME>/.env` entries; runs `pip`/`uv pip` installs. On the built-in row: `\n  ✓ Memory provider: built-in only` + `  Saved to config.yaml\n`. On a provider: `\n  Configuring <name>:\n` during the walk, then `\n  Memory provider: <name>`, `  Activation saved to config.yaml`, optionally `  Provider config saved` and `  API keys saved to .env`, then `\n  Start a new session to activate.\n`.
- **Config / env:** `memory.provider`, `memory.<provider>.*`; secrets written to `<HERMES_HOME>/.env` under each field's `env_var`.
- **Edge cases / guards:** No providers discovered → `\n  No memory provider plugins detected.` + `  Install a plugin to ~/.hermes/plugins/ and try again.\n`. Unknown positional provider → `\n  Memory provider '<name>' not found.` + `  Run 'hermes memory setup' to see available providers.\n`. ESC anywhere in the picker or a choice field → `\n  Cancelled. No changes saved.\n` and nothing is written. A failing `provider.save_config` prints `  Failed to write provider config: <e>` but activation is still saved. Between curses screens `_clear_interactive_transition()` emits `\033[2J\033[H` only when stdout is a TTY.
- **Rebuild notes:** Discover → hint-classify → radio pick → dependency install → schema walk (choices/secret/text with `when` + `default_from`) → split writes (config vs native vs .env). A better version would validate the credential with a live connection test before saving, as some providers' `post_setup` already do.

### Memory status  `id: cli-e.memory-status`
- **Surface:** CLI
- **Where:** `hermes memory status [-h]` — also what a bare `hermes memory` prints.
- **What it does:** Reports whether built-in memory injection, the user profile and the `memory` tool are on, which external provider is active, its config, whether its plugin is installed and available, which env vars are still missing, and every installed provider plugin.
- **How it works:** `cmd_status` (`hermes_cli/memory_setup.py:478`). Built-in flags come from `memory.memory_enabled` / `memory.user_profile_enabled` (both default `True`). The tool line is the *canonical* resolution: `hermes_cli.tools_config._get_platform_tools(config, "cli", include_default_mcp_servers=False)` must contain `"memory"` **and** `tools.memory_tool.check_memory_requirements()` must pass. The provider block reads `memory.<provider>` and, when the provider exposes `get_status_config(provider_config)`, displays that redacted view instead (a raised exception is shown as an extra `status_config_error` key). Availability is `provider.is_available()`; when unavailable, every schema field carrying an `env_var` is listed with `✓`/`✗` based on `os.environ`.
- **Inputs / options:** `-h, --help`. No arguments.
- **Outputs / side effects:** Read-only. Verbatim layout: `\nMemory status\n` + a 40-char `─` rule; `  Built-in (MEMORY.md / USER.md):`; `    Memory injection:   <enabled ✓|disabled ✗>`; `    User profile:       <enabled ✓|disabled ✗>`; `    Memory tool:        <enabled ✓|disabled ✗>`; `  Provider:  <name or '(none — built-in only)'>`. With a provider: `\n  <name> config:` then `    <key>: <value>` per entry; `\n  Plugin:    installed ✓` then `  Status:    available ✓` or `  Status:    not available ✗` + `  Missing:` + `    <✓|✗> <ENV_VAR>` (plus `  → <url>` when unset and a url is declared) + the two-line note `  Note: systemd/gateway services do not inherit ~/.hermes/.env —` / `        set any variables above in the service environment.`. - **Edge cases / guards:** The env-var probe reads `os.environ` **after** `.env` loading in this process, which is why the systemd note exists — a gateway service will not see `~/.hermes/.env`. `hermes memory` with an unrecognised sub-command also falls through to status.
- **Rebuild notes:** Read config → resolve the effective tool set → per-provider availability + missing-credential matrix. A better version would print the last successful provider round-trip time and the store size.

### Disable the external memory provider  `id: cli-e.memory-off`
- **Surface:** CLI
- **Where:** `hermes memory off [-h]`
- **What it does:** Clears `memory.provider` so only the built-in `MEMORY.md`/`USER.md` memory remains; the provider's plugin, credentials and stored data are untouched.
- **How it works:** Handled inline in `cmd_memory` (`hermes_cli/main.py:12855-12864`): `load_config()`, coerce `config["memory"]` to a dict if it isn't one, set `config["memory"]["provider"] = ""`, `save_config`.
- **Inputs / options:** `-h, --help`. No arguments, no confirmation.
- **Outputs / side effects:** One config write. Prints `\n  ✓ Memory provider: built-in only` then `  Saved to config.yaml\n`. Returns `None` (exit 0).
- **Config / env:** `memory.provider`.
- **Edge cases / guards:** Idempotent. Does **not** uninstall the plugin, delete provider-side data, or remove credentials from `.env`; re-activating with `hermes memory setup <name>` restores the previous configuration.
- **Rebuild notes:** One key blanked. Better: also stop any provider daemon it started (e.g. Hindsight's embedded mode) instead of leaving it running.

### Erase built-in memory  `id: cli-e.memory-reset`
- **Surface:** CLI
- **Where:** `hermes memory reset [-h] [--yes] [--target {all,memory,user}]`
- **What it does:** Permanently deletes `MEMORY.md` (agent notes) and/or `USER.md` (user profile) from the profile's `memories/` directory after a typed confirmation.
- **How it works:** Inline in `cmd_memory` (`hermes_cli/main.py:12865-12909`). It maps `--target` to the file list — `all` → both, `memory` → `("MEMORY.md", "agent notes")`, `user` → `("USER.md", "user profile")` — filters to files that actually exist, prints each with its byte size, asks for confirmation unless `--yes`, then `unlink()`s them one by one.
- **Inputs / options:** `-h, --help`; `--yes, -y` = `Skip confirmation prompt`; `--target {all,memory,user}` (default `all`) = `Which store to reset: 'all' (default), 'memory', or 'user'`. Prompt: `\n  Type 'yes' to confirm: ` — the answer must be exactly `yes` (lower-cased, stripped); anything else cancels.
- **Outputs / side effects:** Deletes files under `<HERMES_HOME>/memories/`. Prints `\n  This will permanently erase the following memory files:` then `    ◆ <file> (<desc>) — <size with thousands separators> bytes` per file; after deletion `  ✓ Deleted <file> (<desc>)` per file, then `\n  Memory reset complete. - **Edge cases / guards:** Nothing to delete → `\n  Nothing to reset — no memory files found in <display hermes home>/memories/\n` and it returns without prompting. EOF/Ctrl-C at the prompt → `\n  Cancelled.\n`; a wrong answer → `  Cancelled.\n`. **Not undoable** — there is no snapshot, and it deletes files rather than truncating them. It does not touch an external provider's store.
- **Rebuild notes:** Existence check → sized preview → typed confirmation → unlink. A better version would move the files into a timestamped `.trash/` folder so a reset is recoverable for a grace period.

## 9. `hermes computer-use` — the cua-driver backend

### Computer-use command group  `id: cli-e.computer-use`
- **Surface:** CLI
- **Where:** `hermes computer-use [-h] {install,status,doctor,permissions} ...`. Root command-list help line: `Manage the Computer Use (cua-driver) backend (macOS/Windows/Linux)`. Long description (verbatim): `Install or check the cua-driver binary used by the \`computer_use\` toolset. Supported on macOS, Windows, and Linux.\n\nUse \`hermes computer-use install\` to fetch and run the upstream cua-driver installer. This is equivalent to the post-setup hook that \`hermes tools\` runs when you first enable the Computer Use toolset, and is a stable target for re-running the install if it didn't fire (e.g. when toggling the toolset on a returning-user setup).\n\nUse \`hermes computer-use doctor\` to run cua-driver's \`health_report\` MCP tool and surface its check matrix (TCC, bundle identity, version, platform support, ...) in human-readable form.`
- **What it does:** Installs, upgrades, inspects and permission-grants the third-party `cua-driver` binary that the `computer_use` toolset drives the desktop through.
- **How it works:** Parser and handler are inline in `hermes_cli/main.py:13862-14082` (`cmd_computer_use` at `main.py:13963`). Every surface resolves the binary through one function, `tools.computer_use.cua_backend.resolve_cua_driver_cmd` (`cua_backend.py:1103`): an explicit override (or a non-empty `HERMES_CUA_DRIVER_CMD`) is authoritative and is *never* silently replaced; otherwise candidates are tried in order — bare `cua-driver` on PATH, then on Windows `%LOCALAPPDATA%\Programs\Cua\cua-driver\bin\cua-driver.exe`, `~/.local/bin/cua-driver.exe`, `~/.local/bin/cua-driver`; on POSIX `~/.local/bin/cua-driver`, `~/.cargo/bin/cua-driver`, `/opt/homebrew/bin/cua-driver`, `/usr/local/bin/cua-driver`. Bare `hermes computer-use` prints the group help. `"computer-use"` is in `_BUILTIN_SUBCOMMANDS` (`main.py:12408`).
- **Inputs / options:** `-h, --help`; sub-commands with verbatim help: `install` = `Install or repair the cua-driver binary (macOS/Windows/Linux)`; `status` = `Print whether cua-driver is installed and on PATH`; `doctor` = `Run cua-driver \`health_report\` and surface the check matrix`; `permissions` = `Check or grant macOS Accessibility + Screen Recording (macOS)`.
- **Outputs / side effects:** Downloads and installs a third-party binary; no Hermes config keys are written.
- **Config / env:** `HERMES_CUA_DRIVER_CMD` (pin a specific binary — authoritative even when broken). Child processes get a telemetry-policy env from `cua_driver_child_env()` and are then stripped of Hermes provider secrets by `tools.environments.local._sanitize_subprocess_env` — cua-driver is third-party and must never inherit API keys.
- **Edge cases / guards:** Runtime platforms are `darwin`, `win32`, `linux` (`_RUNTIME_PLATFORMS`, `tools/computer_use/permissions.py:34`); Linux is alpha. The Hermes runtime contract requires cua-driver **≥ 0.20.0** whose `manifest` advertises `mcp --socket/--grant`, `serve --socket/--permission-mode/--capability-manifest/--approve-capability-manifest/--embedded` and `stop --socket` (`_CUA_DRIVER_RUNTIME_CONTRACT_MIN` / `_CUA_DRIVER_RUNTIME_CONTRACT_ARGS`, `cua_backend.py:1127-1139`).
- **Rebuild notes:** Wrap a third-party driver with one resolver, one contract check and one health passthrough, and keep the health model upstream so new checks appear without code changes. A better version would vendor a signed driver build and verify its signature before first launch.

### Install or repair cua-driver  `id: cli-e.computer-use-install`
- **Surface:** CLI
- **Where:** `hermes computer-use install [-h] [--upgrade]`
- **What it does:** Fetches and runs the upstream cua-driver installer to install it fresh, repair a version that fails the Hermes runtime contract, or upgrade in place.
- **How it works:** `cmd_computer_use` (`hermes_cli/main.py:13965`) calls `hermes_cli.tools_config.install_cua_driver(upgrade=…)` (`tools_config.py:976`) and, on success, re-checks `_cua_driver_contract_status().get("ready")`. Two modes: `upgrade=False` keeps a compatible 0.20+ install, repairs an old/incomplete one, and installs when missing (this is the path the toolset-enable flow uses); `upgrade=True` always re-runs the installer, or calls the driver's own `update` verb when it supports it. Installer invocation (`_run_cua_driver_installer`, `tools_config.py:1617`): on macOS/Linux the script is **downloaded then executed** (`curl -fsSL -o <mkstemp 0600 file> https://raw.githubusercontent.com/trycua/cua/main/libs/cua-driver/scripts/install.sh` with a 120 s download timeout, then `/bin/bash <file>`) rather than piped through a shell — no `shell=True`, no command substitution, no fixed `/tmp` path to race; on Windows it runs `powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/trycua/cua/main/libs/cua-driver/scripts/install.ps1 | iex"`. A confirmed version can be pinned by exporting `CUA_DRIVER_RS_VERSION` so the installer fetches that exact release instead of its baked-in default (which Release Please bumps *before* the assets publish, so an unpinned run inside that window 404s). Timeouts: `_CUA_INSTALLER_TIMEOUT = 660` s for the explicit path, `_CUA_BACKGROUND_UPDATE_TIMEOUT = 120` s for quiet background upgrades, `_CUA_INSTALLER_DRAIN_GRACE = 15` s to drain output after a kill. Windows additionally handles `install.ps1`'s `FileShare::None` concurrency lock (stale-lock detection at `tools_config.py:1333`/`1414`) and can repair the driver's autostart registration (`_repair_cua_driver_autostart_windows`, `tools_config.py:1553`).
- **Inputs / options:** `-h, --help`; `--upgrade` = `Re-run the upstream installer even if cua-driver is already on PATH. The upstream install.sh always pulls the latest release, so this performs an in-place upgrade.`
- **Outputs / side effects:** Downloads and installs the cua-driver binary (typically into `~/.local/bin` on POSIX or `%LOCALAPPDATA%\Programs\Cua\...` on Windows), may register Windows autostart, may show a UAC/SmartScreen dialog. Returns exit 0 only when the install succeeded **and** the runtime contract is satisfied; otherwise 1.
- **Config / env:** `HERMES_CUA_DRIVER_CMD` (an override blocks installing over it); `CUA_DRIVER_RS_VERSION` is exported to the installer when a version is pinned.
- **Edge cases / guards:** Unsupported platform → `    Computer Use (cua-driver) is unsupported on this platform; skipping.` (silent when called with `upgrade=True` from `hermes update`) and False. A set-but-unresolvable `HERMES_CUA_DRIVER_CMD` → `    HERMES_CUA_DRIVER_CMD does not resolve to an executable: <value>` + `    Fix or unset the override before running computer-use install.` and False — Hermes will not install over or replace an explicitly pinned binary. `/Applications` not writable (macOS fresh install) → `    /Applications is not writable; skipping cua-driver install.` + `    Run from an admin account or install cua-driver manually.`. Missing fetch tool → `    curl not found — install manually:` (or `powershell`) + `      https://github.com/trycua/cua/blob/main/libs/cua-driver/README.md`. Download failure → `    cua-driver installer download failed: <detail>`.
- **Rebuild notes:** Download-then-exec (never pipe-to-shell), pin the version you confirmed, bound every step with a timeout, and gate success on a manifest contract check rather than "the binary exists". Better: verify a checksum/signature of the downloaded installer and the resulting binary.

### cua-driver status  `id: cli-e.computer-use-status`
- **Surface:** CLI
- **Where:** `hermes computer-use status [-h]`
- **What it does:** Says whether cua-driver is installed, where, at what version, whether it satisfies the Hermes runtime contract, and whether a newer release exists.
- **How it works:** `cmd_computer_use` (`hermes_cli/main.py:13976-14038`). It resolves the path with `resolve_cua_driver_cmd()` (deliberately the *runtime* resolver, because Desktop/TUI processes can have a PATH without `~/.local/bin`), reads `HERMES_CUA_DRIVER_CMD`, runs `<binary> --version` with a 5 s timeout and the sanitised child env, condenses it through `_cua_version_summary(raw, limit=120)`, then calls `_cua_driver_contract_status(path)` (`tools_config.py:811`, a 30 s-cached wrapper around `cua_backend.cua_driver_runtime_contract_status`, which runs `<binary> manifest`, requires a semantic `binary_version` ≥ 0.20.0, an `mcp_invocation.args` list, and every required sub-command argument) and `cua_backend.cua_driver_update_check()` (`<binary> check-update --json`).
- **Inputs / options:** `-h, --help`. No arguments.
- **Outputs / side effects:** Read-only (spawns the driver twice with short timeouts). Installed: `cua-driver: installed at <path>[ [custom binary from HERMES_CUA_DRIVER_CMD]] (<version>)` — the version parenthetical is dropped when `--version` fails. Contract failure adds `  ⚠ Repair required: <reason or 'runtime contract is incomplete'>` plus, when an override is set, `    Update the binary selected by HERMES_CUA_DRIVER_CMD, or unset the override and run: hermes computer-use install --upgrade`, else `    Run: hermes computer-use install` — exit **1**. Otherwise the update check prints `  ⬆ Update available: cua-driver <latest>.` + `    Run: hermes computer-use install --upgrade`, or `  ✓ Up to date.`, or (older driver without `check-update`, or offline/error) `  Refresh to latest: hermes computer-use install --upgrade` — exit **0**. Not installed: `cua-driver: not installed` + `  Run: hermes computer-use install` — exit **1**.
- **Config / env:** `HERMES_CUA_DRIVER_CMD`.
- **Edge cases / guards:** Contract reasons surfaced verbatim include `cua-driver is not installed`, `manifest check failed: <exc>`, `driver manifest is missing or invalid`, `driver manifest does not report a semantic version`, `Hermes computer use requires cua-driver 0.20.0 or newer`, `driver manifest does not provide an MCP launch command`, and `driver manifest is missing: <command arg, …>`. The `manifest` probe uses a 15 s timeout on Windows and 5 s elsewhere. The contract result is cached for 30 s keyed on `(path, mtime_ns, size)`.
- **Rebuild notes:** Resolve → `--version` → `manifest` contract → `check-update`, each bounded and each with a distinct actionable message. Better: cache the update check with a TTL so `status` stays instant offline.

### cua-driver doctor  `id: cli-e.computer-use-doctor`
- **Surface:** CLI
- **Where:** `hermes computer-use doctor [-h] [--include CHECK] [--skip CHECK] [--json]`
- **What it does:** Drives cua-driver's own `health_report` MCP tool over stdio JSON-RPC and renders its full check matrix — TCC permissions, bundle identity, version, platform support, screenshot probe and whatever else upstream adds.
- **How it works:** `tools.computer_use.doctor.run_doctor` (`doctor.py:837`), called from `main.py:14039` and `sys.exit()`ed with its return code. It first makes stdout/stderr UTF-8 (`reconfigure(encoding="utf-8", errors="replace")`) because the ✅❌⚠️⏭️ glyphs are unencodable in the Windows ANSI codepages. It resolves the binary with the shared runtime resolver — so the doctor diagnoses exactly what the `computer_use` toolset will invoke — then performs the stdio MCP handshake and calls `health_report`. A valid report must be a dict carrying `schema_version`, `overall` and a list `checks` (`_is_valid_health_report`, `doctor.py:89`). cua-driver 0.10.x marks `health_report` as `risk.class='unclassified'`, so `tools/call` returns `isError=true` with `structuredContent {"exit_code": 1}`; that is detected and a composite `schema_version=1` report is synthesised from working probes (`check_permissions`, `list_apps`, CLI `--version`) instead of printing a `• cua-driver ? on ? — ?` line. The child env is telemetry-policy + secret-sanitised (`_sanitized_cua_env`, `doctor.py:72`). The header additionally reports the binary's own `--version`, and flags a mismatch against `health_report.driver_version` (observed on Windows where health_report claimed 0.8.3 against a real 0.12.6).
- **Inputs / options:** `-h, --help`; `--include CHECK` (`action="append"`, default `[]`) = `Run only the listed checks. Repeat for multiple (e.g. --include tcc_accessibility --include bundle_identity). Unknown names are reported by cua-driver.`; `--skip CHECK` (`action="append"`, default `[]`) = `Skip the listed checks. Repeat for multiple. Wins over --include.`; `--json` = `Emit the raw structured payload as JSON (same shape as \`tools/call\`).`

### Run Hermes as an MCP server  `id: cli-e.mcp-serve`
- **Surface:** CLI
- **Where:** `hermes mcp serve [-h] [-v] [--accept-hooks]`
- **What it does:** Exposes Hermes' cross-platform conversations to another agent over MCP on stdio — listing conversations and channels, reading messages and attachments, sending messages, polling/waiting for events, and resolving approval requests.
- **How it works:** `mcp_command` → `mcp_serve.run_mcp_server(verbose=…)` (`mcp_serve.py:1029`). It configures logging on **stderr** (DEBUG with `-v`, else WARNING — stdout is the JSON-RPC channel), starts an `EventBridge`, builds the server with `create_mcp_server(event_bridge=bridge)` (`mcp_serve.py:623`) and runs `server.run_stdio_async()` inside `asyncio.run`, stopping the bridge in `finally` and on `KeyboardInterrupt`. The server is named `hermes` with instructions `Hermes Agent messaging bridge. Use these tools to interact with conversations across Telegram, Discord, Slack, WhatsApp, Signal, Matrix, and other connected platforms.`
- **Inputs / options:** `-h, --help`; `-v, --verbose` = `Enable verbose logging on stderr`; `--accept-hooks` = `Auto-approve unseen shell hooks without a TTY prompt (equivalent to HERMES_ACCEPT_HOOKS=1 / hooks_auto_accept: true).`
- **Outputs / side effects:** Speaks MCP JSON-RPC on stdin/stdout until killed. It registers exactly 10 tools: `conversations_list(platform=None, limit=50, search=None)` — list active conversations with their session keys, platform, chat type, display name and last activity; `conversation_get(session_key)` — details for one conversation; `messages_read(session_key, limit=50)` — recent messages in chronological order with role, content and timestamp (limit coerced to 1..200); `attachments_fetch(session_key, message_id)` — non-text blocks (images, media) of one message; `events_poll(after_cursor=0, session_key=None, limit=20)` — events since a cursor, returning `next_cursor`, event types `message`, `approval_requested`, `approval_resolved`; `events_wait(after_cursor=0, session_key=None, timeout_ms=30000)` — long-poll for the next matching event; `messages_send(target, message)` — send to `"platform:chat_id"` (e.g. `telegram:6308981865`, `discord:#general`, `slack:#engineering`) or a resolvable channel name; `channels_list(platform=None)` — sendable targets; `permissions_list_open()` — approval requests the bridge has seen **since it started** (live-session only); `permissions_respond(id, decision)` where `decision ∈ {allow-once, allow-always, deny}`. Every tool returns a JSON string.
- **Config / env:** reads the profile's session index and channel directory; `HERMES_ACCEPT_HOOKS` / `hooks_auto_accept` via `--accept-hooks`.
- **Edge cases / guards:** Missing `mcp` package → `Error: MCP server requires the 'mcp' package.\nInstall with: <python> -m pip install 'mcp'` on stderr and exit 1. `permissions_respond` rejects any other decision with `Invalid decision: <d>. Must be allow-once, allow-always, or deny`. `permissions_list_open` cannot see approvals raised before the bridge connected. Because stdout is the protocol, anything printed there would corrupt the session — hence stderr-only logging.
- **Rebuild notes:** Wrap the existing session store in ten read/write tools, keep a cursor-based event stream with both poll and long-poll, and put all logging on stderr. A better version would stream events as MCP notifications instead of requiring a poll loop.

With nothing configured: `No MCP servers configured.` then `Add one with:` + `  hermes mcp add <name> --url <endpoint>` + `  hermes mcp add <name> --command <cmd> --args <args...>`.
- **Config / env:** reads `mcp_servers`.
- **Edge cases / guards:** A server with neither `url` nor `command` shows `?` as its transport. Long names are not truncated, so the columns can misalign for names over 16 chars. Glob patterns in `tools.exclude` are counted like literals.
- **Rebuild notes:** Pure config read + fixed-width table. Better: add a `--json` mode and a last-connection-status column.

### Test an MCP server connection  `id: cli-e.mcp-test`
- **Surface:** CLI
- **Where:** `hermes mcp test [-h] name`
- **What it does:** Connects to one configured server, times the round-trip, and lists every tool it advertises — the diagnostic for "why is this server's tools missing".
- **How it works:** `cmd_mcp_test` (`hermes_cli/mcp_config.py:746`) prints the transport and a masked view of the auth, then calls `_probe_single_server(name, cfg)` around a `time.monotonic()` measurement. Masking: for each header whose key contains `key` or `auth` (case-insensitive) it resolves `${VAR}` / Cursor-style `${env:VAR}` references from the environment and prints `<first 4>***<last 4>` when the resolved value is longer than 8 characters, else `***`.
- **Inputs / options:** `-h, --help`; positional `name` (required) = `Server name to test`.
- **Outputs / side effects:** Opens and closes one connection; no writes. Prints `  Testing '<name>'...`, then `Transport: HTTP → <url>` or `Transport: stdio → <command>`, then `Auth: OAuth 2.1 PKCE`, or the masked header lines `    <header>: <masked>`, or `Auth: none`. On success: `✓ Connected (<ms>ms)`, `✓ Tools discovered: <n>`, then one `    <tool name padded to 36>  <description truncated to 55 + "...">` per tool.
- **Config / env:** reads `mcp_servers.<name>` and resolves `${VAR}` placeholders against `<HERMES_HOME>/.env` + the process environment.
- **Edge cases / guards:** Unknown name → `Server '<name>' not found in config.` plus `Available: <comma list>`. Connection failure → `Connection failed (<ms>ms): <exc>`, where the exception is unwrapped from anyio `BaseExceptionGroup`/`ExceptionGroup` wrappers by `_unwrap_exception_group` (`mcp_config.py:420`) so the message names the real cause. A server rejected by the security validator raises before any connection is attempted. `prompts/list` and `resources/list` are **not** probed here (that extra capability probe is gated behind the `details` out-param used by the dashboard, and honours `tools.prompts` / `tools.resources` plus the server's advertised capabilities).
- **Rebuild notes:** One probe function shared with add/configure, an elapsed-ms number, and masked-but-visible auth. Better: print the negotiated protocol version and the server's advertised capability set.

### Toggle an MCP server's tools  `id: cli-e.mcp-configure`
- **Surface:** CLI (curses checklist)
- **Where:** `hermes mcp configure [-h] name`, alias `hermes mcp config` (help prints `usage: hermes mcp configure …`)
- **What it does:** Re-probes an installed server and shows a checklist so you can turn individual tools on and off, writing the result back as an include or exclude filter.
- **How it works:** `cmd_mcp_configure` (`hermes_cli/mcp_config.py:987`) requires an interactive terminal, probes the server, and computes the current selection with the **same** matching semantics as runtime registration — `tools.mcp_tool.matches_name_filter`, i.e. exact names or `fnmatch` globs — so a glob exclude such as `*team_member*` is reflected in the checkboxes instead of appearing as "nothing excluded". Writing back has three branches: (a) everything selected and the entry was not in exclude mode → drop `tools` entirely (register all); (b) the entry was in **exclude mode** (a hand-written `tools.exclude` or a catalog manifest's `default_excluded`) → stay in exclude mode: keep every glob entry, drop literal entries for re-checked tools, append newly-unchecked tools that are not already matched, and write `tools.exclude` while removing any `include`; (c) otherwise write `tools.include` with the chosen names and remove `exclude`.
- **Inputs / options:** `-h, --help`; positional `name` (required) = `Server name to configure`. Checklist title `Select tools for '<name>'`, rows `<tool>  —  <description>`, keys `↑↓ navigate  SPACE toggle  ENTER confirm  ESC cancel`.
- **Outputs / side effects:** Rewrites `mcp_servers.<name>.tools`. Prints `  Connecting to '<name>' to discover tools...`, then `Currently <n>/<total> tools enabled for '<name>'.`, and on save `✓ Updated config: <n>/<total> tools enabled` + `Start a new session for changes to take effect.`.
- **Config / env:** `mcp_servers.<name>.tools.{include,exclude}`.
- **Edge cases / guards:** Non-TTY stdin → `Error: 'hermes mcp configure' requires an interactive terminal.` on stderr and **exit 1**. Unknown name → `Server '<name>' not found in config.` + `Available: <comma list>`. Probe failure → `Failed to connect: <exc>`. Server reports no tools → `Server reports no tools.`. Checklist unchanged → `No changes made.` and nothing is written. Re-checking a tool that a kept glob still excludes warns: `<n> re-enabled tool(s) still match glob exclude pattern(s) <globs> and stay excluded: <first 5>[ ...]. Remove the pattern from mcp_servers.<name>.tools.exclude in config.yaml to enable them.` — the click is neither silently ignored nor silently frozen into a literal list.
- **Rebuild notes:** Preserve the user's filter *mode* (include vs exclude) across edits, use one matcher for UI and runtime, and be explicit when a glob shadows a click. Better: allow editing the glob patterns themselves from the checklist.

### Force MCP OAuth re-authentication  `id: cli-e.mcp-login`
- **Surface:** CLI
- **Where:** `hermes mcp login [-h] name`
- **What it does:** Wipes a server's cached OAuth state and runs a fresh browser sign-in flow, verifying that a token actually landed.
- **How it works:** `cmd_mcp_login` (`hermes_cli/mcp_config.py:910`) → the shared `_reauth_oauth_server(name, cfg)` (`mcp_config.py:810`). It clears both disk and the in-process `MCPOAuthManager` cache via `get_manager().remove(name)`, then re-probes inside `tools.mcp_oauth.force_interactive_oauth()` — needed because `hermes mcp login` is explicitly user-initiated even when stdin is not a TTY (Hermes Desktop, agent-spawned terminals), and the default interactivity check is `sys.stdin.isatty()`. The probe timeout is `max(configured connect_timeout, 315.0)` seconds — the 300 s OAuth callback window plus headroom — matching the dashboard's re-auth path so CLI and GUI behave identically. Crucially, a clean probe is **not** treated as proof of authentication: some servers (notably Google Drive) serve `initialize` + `tools/list` anonymously, so `_oauth_tokens_present(name)` (`mcp_config.py:404`, `HermesTokenStorage(name).has_cached_tokens()`) must confirm a token exists on disk.
- **Inputs / options:** `-h, --help`; positional `name` (required) = `Server name to re-authenticate`.
- **Outputs / side effects:** Deletes and re-acquires OAuth tokens; opens a browser. Prints `Starting OAuth flow for '<name>'...`, then `✓ Authenticated — <n> tool(s) available` or `✓ Authenticated (server reported no tools)`.
- **Config / env:** `mcp_servers.<name>.{url,auth,oauth,connect_timeout}`; OAuth token storage on disk.
- **Edge cases / guards:** Unknown name → `Server '<name>' not found in config.` + `Available servers: <comma list>`. No URL → `Server '<name>' has no URL — not an OAuth-capable server`. Not `auth: oauth` → `Server '<name>' is not configured for OAuth (auth=<value>)` + `Use \`hermes mcp remove\` + \`hermes mcp add\` to reconfigure auth.`. Token-clear failure → `Could not clear existing OAuth state: <exc>` (non-fatal). Probe succeeded but no token → `Server responded, but no OAuth token was obtained — authentication did not complete.` followed by the guidance `Some providers (e.g. Google Drive, Atlassian) do not support automatic client registration. For those you must create an OAuth client yourself and add its credentials to config.yaml:` and a verbatim YAML snippet (`mcp_servers:` / `  <name>:` / `    url: <url>` / `    auth: oauth` / `    oauth:` / `      client_id: "<your-oauth-client-id>"` / `      client_secret: "<your-oauth-client-secret>"`), then `Then re-run \`hermes mcp login <name>\`.`. Any exception is humanised through `tools.mcp_oauth.humanize_oauth_registration_error` before printing `Authentication failed: <message>`. Use it when tokens are stuck, when you want a different account/scopes, or when a tool call returned `needs_reauth: true`.
- **Rebuild notes:** Clear both caches, force interactivity explicitly, give the human a 300 s+ window, and verify the token on disk rather than trusting a successful probe. Better: detect the RFC 7591 registration failure up front and print the manual-client instructions before opening a browser.

### Re-authenticate one or all OAuth servers  `id: cli-e.mcp-reauth`
- **Surface:** CLI
- **Where:** `hermes mcp reauth [-h] [--all] [name]`
- **What it does:** Same as `login` for one server, or walks **every** `auth: oauth` server in config one at a time.
- **How it works:** `cmd_mcp_reauth` (`hermes_cli/mcp_config.py:935`). With `--all` it selects every server whose `auth == "oauth"` **and** which has a `url`, then calls `_reauth_oauth_server` sequentially. Serial by design: a human can only complete one browser OAuth flow at a time, so a concurrent run would open N tabs and N-1 would time out.
- **Inputs / options:** `-h, --help`; positional `name` (optional) = `Server name to re-authenticate (omit with --all)`; `--all` = `Re-authenticate every OAuth server in config, one at a time`.
- **Outputs / side effects:** Same token wipe + re-acquire as `login`, per server. `--all` prints `Re-authenticating <n> OAuth server(s) one at a time...`, then per server a blank line and `  ── <name> ──` (cyan+bold), and finishes with `✓ Re-authenticated <succeeded>/<total> server(s)`.
- **Config / env:** `mcp_servers.*.{auth,url,connect_timeout}`.
- **Edge cases / guards:** `--all` with no OAuth servers → `No OAuth-based MCP servers found in config.`. Neither a name nor `--all` → `Specify a server name, or use --all to re-auth every OAuth server.` + `Usage: hermes mcp reauth <name>   |   hermes mcp reauth --all`. Unknown name → `Server '<name>' not found in config.` + `Available servers: <comma list>`. A failure on one server does not stop the others; the final count reports how many succeeded. Existing to fix the recurring stale-client ritual and the startup popup storm when several servers go stale at once.
- **Rebuild notes:** Reuse the single-server routine in a loop and never parallelise a flow that needs a human. Better: skip servers whose tokens are still valid unless `--force`.

### Interactive MCP catalog picker  `id: cli-e.mcp-picker`
- **Surface:** CLI (curses single-select, with a text fallback)
- **Where:** `hermes mcp picker [-h]` — and the default action of a bare `hermes mcp`.
- **What it does:** One screen listing every Nous-approved catalog MCP plus every custom server you added, with its status, and ENTER acts on the row: install, enable, or open a per-row action menu.
- **How it works:** `hermes_cli.mcp_picker.run_picker` (`mcp_picker.py:274`) loops until ESC/q so several entries can be managed in one session. Rows are built by `_build_rows` (`mcp_picker.py:69`): catalog entries from `list_catalog()` with status `available` (not installed), `enabled`, or `installed (disabled)`; then any `mcp_servers` entry that is *not* a catalog name, with status `custom — enabled` / `custom — disabled` and the URL or command as its description. Each row renders as `<name:18> <status:24> <description>`. Actions (`_handle_row`, `mcp_picker.py:160`): a not-installed catalog row installs immediately (`install_entry(entry, enable=True)`); an installed-but-disabled catalog row enables; an installed+enabled catalog row opens a 4-item menu; a custom row opens a 3-item menu.
- **Inputs / options:** `-h, --help`. Picker title: `MCP Catalog  —  ↑↓ navigate  ENTER act on entry  ESC/q quit`. Catalog-row action menu (verbatim): `Configure tools (probe server + re-pick)`, `Disable (keep config, stop loading on next session)`, `Uninstall (remove config and any cloned files)`, `Reinstall (re-clone, re-prompt for credentials)`, plus the `Cancel` row `curses_single_select` appends. Custom-row menu: `Configure tools (probe server + re-pick)`, `Enable` or `Disable` (whichever applies), `Remove from config`, plus `Cancel`. Confirmations: `Uninstall '<name>'?` (default no) and `Remove '<name>' from mcp_servers?` (default no).
- **Outputs / side effects:** Installs/enables/disables/removes `mcp_servers` entries and may clone or delete catalog install directories. Messages: `  ✓ '<name>' <enabled|disabled>. Start a new Hermes session for changes to take effect.`; `  ✓ Uninstalled '<name>'. - **Edge cases / guards:** Non-TTY stdin degrades gracefully to the same text dump `hermes mcp catalog` prints, instead of failing. An empty row list prints the text dump and returns. Uninstall deliberately preserves `.env` credentials.
- **Rebuild notes:** One unified row model over "curated catalog" + "user-added", with the action derived from status rather than a separate verb per case. Better: show each entry's tool count and last connection result on the row.

### Install a catalog MCP by name  `id: cli-e.mcp-install`
- **Surface:** CLI
- **Where:** `hermes mcp install [-h] identifier`
- **What it does:** One-command install of a curated catalog entry: clone/bootstrap if needed, prompt for credentials, write the `mcp_servers` block, probe the server and pick its tools, then print any post-install notes.
- **How it works:** `install_by_name(identifier)` (`hermes_cli/mcp_picker.py:301`) resolves the entry with `mcp_catalog.get_entry` and calls `install_entry(entry, enable=True)` (`mcp_catalog.py:887`), whose six steps are: (1) when `install.type == git`, clone and run the manifest's bootstrap commands (`_do_git_install`, `mcp_catalog.py:483`, using a non-interactive git env); (2) when `auth.type == api_key`, prompt for the declared env vars and save them to `<HERMES_HOME>/.env`; (3) when `auth.type == oauth`, either point at `hermes auth <provider>` (provider-mediated) or note that native OAuth 2.1 tokens will be acquired on first connection; (4) translate the manifest into an `mcp_servers.<name>` block via `_build_server_config` (substituting `${INSTALL_DIR}` in `transport.command`/`transport.args`) and save it through `mcp_config._save_mcp_server` — which runs the security validator; (5) probe and apply the tool selection, preserving any prior include selection or exclude list across a reinstall, and falling back to the manifest's `tools.default_enabled` (or all-on) when the probe fails; (6) print `post_install` notes. `auth.type == "none"` skips step 2/3 entirely.
- **Inputs / options:** `-h, --help`; positional `identifier` (required) = `Catalog entry name (or \`official/<name>\`)`.
- **Outputs / side effects:** Writes `mcp_servers.<name>` (enabled), possibly `.env` keys, possibly a clone directory. Prints `  Installing MCP '<name>'` (cyan+bold), the description and `  Source: <url>` in dim, then `  Configure credentials:` for api_key entries, or `  This MCP uses <provider> OAuth. Run \`hermes auth <provider>\` if you have not already authenticated.` / `  This MCP uses native OAuth 2.1; tokens will be acquired on first connection (browser flow).`; finally `  ✓ Installed '<name>' (enabled). Start a new Hermes session to load its tools.` and the manifest's post-install lines.
- **Config / env:** `mcp_servers.<name>.*`; `<HERMES_HOME>/.env` for the manifest's declared env vars.
- **Edge cases / guards:** Unknown identifier → `  ✗ '<identifier>' is not in the catalog. Run \`hermes mcp catalog\` to see available entries.` and **exit 1**. A `CatalogError` → `  ✗ install failed: <exc>` and **exit 1** — including `catalog entry '<name>' rejected: suspicious command/args configuration` when the security validator refuses the generated entry. Exit 0 on success (the command only calls `sys.exit` on a non-zero code). Reinstalling re-prompts for credentials and re-clones.
- **Rebuild notes:** Manifest → credentials → config → probe → tool filter, with prior user choices preserved across reinstalls and `${INSTALL_DIR}` as the only templating hook. A better version would verify the pinned SHA/version after cloning and record what it installed for later audit.

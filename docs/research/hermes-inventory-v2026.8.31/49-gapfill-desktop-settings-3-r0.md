# Gap-fill — Desktop Settings, area 3 (Tools & Keys, Providers, Archived Chats, Toolset/Execution-backend panels, MCP deep-link validator)

Scope: the Hermes Desktop (Electron/React) Settings surfaces that round-trip credentials and
backends — **Tools & Keys** (`KeysSettings` + the shared `useEnvCredentials` hook), **Providers**
(Accounts / API keys / Local endpoint), **Archived Chats** (`SessionsSettings`: archived list,
auto-archive, default project directory), the reusable **toolset config panel** and **Execution
backend** panel rendered inside Capabilities → Tools, and the pure `hermes://mcp/install`
deep-link *validator* module. Deliberately left to sibling shards: the Gateways/SSH page and the
connections registry (`gapfill-desktop-settings-2-r0.md`), the Model/Voice/Appearance config rows
and Settings frame (`desktop-settings.md`), the MCP install *dialog* and the Capabilities page
shell (`desktop-b.md`), credential row widgets and the env-var actions menu
(`gapfill-desktop-settings-1-r0.md`), and every backend REST handler (`docs-rest.md`, config shards).

### Settings → Tools & Keys page (`KeysSettings`)  `id: gapfill-desktop-settings-3-r0.keys-page`
- **Surface:** Desktop app
- **Where:** Settings overlay → left nav **"Tools & Keys"** (`i18n: settings.nav.apiKeys`, icon `KeyRound`) with the two sidebar sub-items **"Tools"** (`i18n: settings.nav.keysTools`) and **"Settings"** (`i18n: settings.nav.keysSettings`). Route `?tab=keys` plus the sub-view param `?kview=tools|settings` (`apps/desktop/src/app/settings/index.tsx:400`). Component `apps/desktop/src/app/settings/keys-settings.tsx:35`.
- **What it does:** Lists every non-provider, non-messaging credential/env var Hermes knows about as an expandable card so the user can set, reveal, replace or clear it — tool API keys under **Tools**, server/gateway settings under **Settings**.
- **How it works:** `KEYS_VIEWS = ['tools', 'settings']` (`keys-settings.tsx:15`). `VIEW_CATEGORIES` (`:28-31`) maps the sub-view onto backend env categories: `tools → ['tool']`, `settings → ['setting', 'messaging']`. The row set is `Object.entries(vars)` filtered by `!info.channel_managed && cats.includes(asText(info.category))` and sorted `a.localeCompare(b)` (`:56-58`) — platform credentials carry `channel_managed` and are configured on the Messaging page instead, so only gateway-wide `messaging` rows (e.g. `GATEWAY_PROXY`) show here (comment `:24-27`). Data comes from `useEnvCredentials(scopeProfile)` (`env-credentials.tsx:49`), i.e. `GET /api/env` scoped to the profile selected by the shared "Applies to" chip (`$settingsRequestProfile`, `keys-settings.tsx:41`). Each row is a `CredentialKeyCard` inside a `div` whose id is `credential-key-<KEY>` (`credentialElementId`, `:33`); `openKey` state keeps at most one card expanded and is reset whenever the scope profile or the sub-view changes (`:45-47`). Deep link `?tab=keys&key=<ENV_KEY>` is consumed by `useDeepLinkHighlight({elementId: credentialElementId, onResolve: setOpenKey, param: 'key', ready: key => renderableKeys.has(key)})` (`:73-78`) — it scrolls the card into view, flashes it and expands it, and only fires for keys this sub-view actually renders so a stale Tools/Settings pairing cannot spin forever.
- **Inputs / options:** Sub-nav **"Tools"** / **"Settings"**; the **"Applies to"** profile scope chip row (`SettingsProfileScope`, `:86`); per-row card controls (expand/collapse header, value input placeholder **"Paste key"**, Save, the `⋯` actions menu, right-click context menu) — documented in `gapfill-desktop-settings-1.credential-field` / `.env-actions-manage-keys`; the search box for this tab uses the placeholder **"Search API keys..."** (`i18n: settings.searchPlaceholder.keys`).
- **Outputs / side effects:** Reads `GET /api/env`; card actions write `PUT /api/env`, `DELETE /api/env`, `POST /api/env/reveal` (`apps/desktop/src/api/config.ts:114-145`), all capability/profile-scoped, which edit `~/.hermes/.env` (or the selected profile's env store). No state is written when only browsing.
- **Config / env:** Every env var the backend reports in categories `tool`, `setting`, `messaging` (non-`channel_managed`); the target profile comes from `$settingsRequestProfile`.
- **Edge cases / guards:** While `vars` is null the page renders `<SettingsSkeleton sections={[{ rows: 5 }]} />` (`:80-82`) — the catalog also carries the never-rendered loading label **"Loading API keys and credentials..."** (`i18n: settings.keys.loading`, declared `apps/desktop/src/i18n/en.ts:983` and `apps/desktop/src/i18n/types.ts:844`), a latent string with no render site in v2026.8.31. When the filtered list is empty the page shows a dashed-border, centered box reading **"Nothing configured in this category yet."** (`i18n: settings.keys.empty`, `keys-settings.tsx:110`, `en.ts:985`). A retired `localStorage` flag `desktop.settings.keys.show_advanced` is best-effort deleted on mount (`env-credentials.tsx:60-66`).
- **Rebuild notes:** Drive the page purely from a backend env-var catalog with `{category, advanced, channel_managed, description, url, is_set, redacted_value}`; split by category into sub-views, keep one expanded card, and support a `?key=` deep link that scrolls + flashes. A better version would validate a pasted key against the vendor before saving and show per-key last-used/quota telemetry.

### Credential catalog fetch (`useEnvCredentials` load lifecycle)  `id: gapfill-desktop-settings-3-r0.env-credentials-load`
- **Surface:** Desktop app
- **Where:** Shared hook behind Settings → **Tools & Keys** and Settings → **Providers** — `useEnvCredentials(profile?)` in `apps/desktop/src/app/settings/env-credentials.tsx:49`. The failure is a toast titled **"API keys failed to load"** (`i18n: settings.keys.failedLoad`, `env-credentials.tsx:81`, `en.ts:984`).
- **What it does:** Fetches the whole env-var catalog for one profile once per profile change and hands it, plus the save/clear/reveal handlers, to every credential surface so the two pages can never drift.
- **How it works:** An effect keyed on `profile` sets `vars` to `null` (which is what makes both pages render their skeleton), then awaits `getEnvVars(profile)` → `GET /api/env` with `profileScoped(profile)` (`apps/desktop/src/api/config.ts:114-119`). A `cancelled` flag drops a late response after the profile changed. On a thrown request it calls `notifyError(err, t.settings.keys.failedLoad)`, leaving `vars` at `null` so the page stays in its skeleton state rather than showing an empty catalog. The hook also owns `edits`, `revealed`, `saving` maps and returns `{ saveValue, vars, rowProps: { edits, revealed, saving, setEdits, onSave, onClear, onReveal } }` (`:181-193`).
- **Inputs / options:** One optional argument `profile` (a profile name, or `undefined` = the app-wide active profile; an explicit `null` is deliberately never passed because the API helpers read `null` as "target the primary backend", comment `:44-48`).
- **Outputs / side effects:** One `GET /api/env` per profile switch; an error toast on failure; the mutation handlers issue `PUT`/`DELETE /api/env` and `POST /api/env/reveal` and toast **"Credential saved"** / **"{key} updated."**, **"Credential removed"** / **"{key} removed."**, **"Failed to save {key}"**, **"Failed to remove {key}"**, **"Failed to reveal {key}"** (`i18n: settings.toolsets.savedTitle` / `savedMessage` / `removedTitle` / `removedMessage` / `failedSave` / `failedRemove` / `failedReveal`).
- **Config / env:** Reads/writes the profile's `.env` store through the backend; no local config keys.
- **Edge cases / guards:** Clearing a key first asks for confirmation with the destructive title **"Remove {key} from .env?"** (`i18n: settings.toolsets.removeConfirm`, `:148`). A failed load never partially populates the page. The retired `desktop.settings.keys.show_advanced` localStorage key is removed inside a `try/catch` so a storage-blocked browser context does not throw.
- **Rebuild notes:** One hook = one fetch + one mutation surface for every credential page; null-vs-empty must be distinguishable so "loading" and "nothing configured" render differently. A better version would revalidate on window focus and expose a per-key `last_error` from the provider.

### `hermes://mcp/install` deep-link validator (`parseMcpInstallDeepLink`)  `id: gapfill-desktop-settings-3-r0.mcp-deeplink-parser`
- **Surface:** Desktop app
- **Where:** Pure module `apps/desktop/src/lib/mcp-deeplink.ts` (no UI of its own), invoked by `requestMcpInstallFromDeepLink(params)` in `apps/desktop/src/store/mcp-deeplink-install.ts:17`. Rejections surface as an error toast titled **"MCP install link rejected"** (`i18n: settings.mcp.deepLinkErrorTitle`).
- **What it does:** Classifies the query params of an `hermes://mcp/install?name=NAME&config=B64` link into either a pending, reviewable install request or a specific rejection code — it never writes config itself.
- **How it works:** `MCP_DEEPLINK_NAME_RE = /^[A-Za-z0-9._-]{1,64}$/` (`:13`); `MCP_DEEPLINK_MAX_CONFIG_BYTES = 32 * 1024` (`:16`) with a pre-decode ceiling `MAX_ENCODED_LENGTH = ceil(32768 * 4 / 3) + 4` (`:20`). Order of checks in `parseMcpInstallDeepLink` (`:76-147`): name regex → `invalid_name`; empty `config` → `missing_config`; over-long encoded text → `payload_too_large`; `decodeBase64` (base64url `-`/`_` normalised to `+`/`/`, whitespace stripped, re-padded to a multiple of 4, `atob`) returning null → `bad_encoding`; decoded bytes > 32 KB → `payload_too_large`; `JSON.parse(new TextDecoder('utf-8', {fatal:true}).decode(bytes))` throwing → `bad_encoding`; non-object / array / null → `not_an_object`; a config carrying BOTH a string `url` and any `command` key → `invalid_shape` (deliberate: loader precedence would decide which runs, so a user could be shown "just a URL" while a command rides along, comment `:119-121`); an unparsable `url` or a scheme other than `http:`/`https:` → `invalid_url`; a string `url` → `{ok:true, transport:'http'}`; a non-empty trimmed string `command` → `{ok:true, transport:'stdio'}`; anything else → `invalid_shape`. `MCP_DEEPLINK_ERROR_KEYS` (`:42-50`) maps each code to an i18n leaf under `settings.mcp`, and the store resolves it with `translateNow('settings.mcp.' + key)` (`mcp-deeplink-install.ts:24`). On success the request is parked in the `$mcpInstallRequest` atom (`:14`) for the confirmation dialog.
- **Inputs / options:** Two query params — `name` (1–64 of `A-Za-z0-9._-`) and `config` (base64url **or** standard base64 of a single JSON server object). Seven error codes: `bad_encoding`, `invalid_name`, `invalid_shape`, `invalid_url`, `missing_config`, `not_an_object`, `payload_too_large`.
- **Outputs / side effects:** Either `$mcpInstallRequest.set({name, config, transport})` (which opens the review dialog — see `desktop-b.contrib-mcp-deeplink`) or exactly one error toast. Nothing is written to `mcp.json` here.
- **Config / env:** Eventually `mcp_servers.<name>`, but only after the dialog's explicit confirmation.
- **Edge cases / guards:** Everything here is treated as hostile input because any web page can open the scheme (module header `:8-10`). Verbatim rejection copy, by code: `invalid_name` → **"The link's server name is missing or invalid."** (`i18n: settings.mcp.deepLinkErrorName`, `en.ts:1072`); `bad_encoding` / `missing_config` / `not_an_object` all → **"The link's config is not valid base64-encoded JSON."** (`i18n: settings.mcp.deepLinkErrorConfig`, `en.ts:1073`); `invalid_shape` → **"The config must be a JSON object with a string `url` or `command` field."** (`settings.mcp.deepLinkErrorShape`); `invalid_url` → **"Only http:// and https:// server URLs are allowed."** (`settings.mcp.deepLinkErrorUrl`); `payload_too_large` → **"The config payload exceeds the 32KB limit."** (`settings.mcp.deepLinkErrorTooLarge`). Note the two catalog entries use a typographic apostrophe (`The link’s …`) in `en.ts`.
- **Rebuild notes:** Keep the classifier pure and total (a closed union of error codes), cap the payload before decoding, reject ambiguous dual-transport configs, and force a human confirmation step in a separate module. A better version would additionally pin an allowlist of publisher origins and show a diff against an existing same-named server.

### Providers → Accounts: connected-provider row and disconnect  `id: gapfill-desktop-settings-3-r0.providers-connected-row`
- **Surface:** Desktop app
- **Where:** Settings → Providers → Accounts → the **"Connected"** group; component `ConnectedProviderRow` (`providers-settings.tsx:221-293`), handlers `handleDisconnect` (`:415`) and `handleTerminalDisconnect` (`:386`).
- **What it does:** Shows a signed-in provider with a "Connected" badge and offers the right way to remove it — an API disconnect when Hermes owns the credential, or running the vendor CLI's own removal command in the embedded terminal when it does not.
- **How it works:** `canDisconnect = provider.disconnectable ?? provider.flow !== 'external'` (`:239`). `terminalDisconnect = !canDisconnect && Boolean(provider.disconnect_command) && canRunInTerminal()` where `canRunInTerminal()` is `Boolean(window.hermesDesktop?.terminal)` — the embedded terminal exists only in the Electron shell, not the web dashboard (`:36`). `showHint = !canDisconnect && !terminalDisconnect`. The API path confirms, then calls `disconnectOAuthProvider(id)` → `DELETE /api/providers/oauth/{id}` (`api/config.ts:208`) and refreshes the list. The terminal path confirms, closes the Settings overlay so the terminal pane is visible, calls `runInTerminal(command)` and toasts — Hermes deliberately never deletes credentials another tool owns behind a silent API call (comment `:382-385`).
- **Inputs / options:** The row button itself (re-runs `startManualProviderOAuth`); the trailing glyph (`Terminal` icon for `flow === 'external'`, otherwise `ChevronRight`); the **"Connected"** pill with a `Check` icon; the flow subtitle; the API disconnect icon-button whose `aria-label` and `title` are both **"Remove {provider}"** (`t.common.remove` + the provider title, `:267`,`:271`) and which shows a spinner while disconnecting; the terminal disconnect icon-button whose `aria-label` is **"Disconnect {provider}"** and whose tooltip/`title` is **"Disconnect (runs the removal command in the terminal)"** (`i18n: settings.providers.disconnectInTerminal`, `en.ts:1124`, `:283`); and, when neither button applies, the static hint **"{provider} is managed by its own CLI — remove it there."** (`settings.providers.removeExternalGeneric`) or **"{provider} is configured from an API key. Remove it from API Keys."** (`settings.providers.removeKeyManaged`).
- **Outputs / side effects:** API path → `DELETE /api/providers/oauth/{id}`, then a 3 s success toast titled **"Account removed"** (`i18n: settings.providers.removedTitle`, `en.ts:1131`, `:410`,`:435`) with the body **"{provider} was removed."** (`settings.providers.removedMessage`), then a provider-list refetch. Terminal path → the Settings overlay closes, the command is typed into the embedded terminal, and an info toast titled **"Account removed"** carries **"Running {provider} disconnect in the terminal…"** (`settings.providers.removeTerminalRunning`).
- **Config / env:** `provider.disconnect_command` from the backend provider catalog.
- **Edge cases / guards:** Both paths are gated by a destructive `confirm()` — API: title **"Remove {provider}?"** (`settings.providers.removeConfirm`), confirm label **"Disconnect"** (`settings.providers.disconnect`); terminal: title **"Disconnect {provider}? This runs "{command}" in the terminal to clear the credential."** (`settings.providers.removeTerminalConfirm`), same confirm label. A failed API disconnect toasts **"Could not remove {provider}"** (`settings.providers.failedRemove`). `handleTerminalDisconnect` returns immediately when the provider ships no command. The terminal button never appears in the web dashboard build.
- **Rebuild notes:** Model three removal states — Hermes-owned (API), CLI-owned (run the documented command visibly), key-owned (point at the keys page) — and never silently delete another tool's credential. A better version would verify after the command exits that the credential is actually gone.

### Providers → API keys tab (search + empty states)  `id: gapfill-desktop-settings-3-r0.providers-keys-tab`
- **Surface:** Desktop app
- **Where:** Settings → Providers → API keys (`?tab=providers&pview=keys`), render branch `providers-settings.tsx:457-504`.
- **What it does:** Groups every `category === 'provider'` env var by vendor into one expandable card per provider, with a free-text filter across provider name, description and env-var keys.
- **How it works:** `buildProviderKeyGroups(vars)` (`:65-116`) buckets provider env vars by, in precedence order, the backend's `provider_label` → `provider` → the desktop prefix guess `providerGroup(key)`; the `'Other'` bucket is skipped. Each bucket needs a *primary* key — the first non-advanced `isKeyVar` entry, else any `isKeyVar` entry — or the group is dropped (`:87-91`). `advanced` is every other entry, excluding redundant alias key vars unless they are already set (so no second "Paste key" input is rendered, comment `:100-102`), sorted by key name. Presentation (`description`, `docsUrl`, `priority`) comes from `providerMeta(name)` with a fallback to the env metadata. Groups sort by `priority` then name. The filter uses `normalize(keyQuery)` and matches `[group.name, group.description, group.primary[0], ...group.advanced keys]` case-insensitively (`:460-466`). One `openProvider` name is expanded at a time.
- **Inputs / options:** The **"Local / custom endpoint"** row at the top (see next entry); a `SearchField` whose `aria-label` and `placeholder` are both **"Search providers…"** (`i18n: settings.providers.searchKeys`, `:474`,`:477`); one `ProviderKeyRows` card per visible group (header click toggles expansion; inside are the primary key field and the advanced overrides).
- **Outputs / side effects:** Expanding/collapsing is local state; saving/clearing a key inside a card goes through `rowProps` → `PUT`/`DELETE /api/env`.
- **Config / env:** Every env var whose backend `category` is `provider`; grouping identity is the same one `hermes model` uses (`hermes_cli/provider_catalog.py`).
- **Edge cases / guards:** With no provider groups at all, `<NoProviderKeys>` renders a centered `min-h-32` block reading **"No provider API keys available."** (`i18n: settings.providers.noProviderKeys`, `en.ts:1134`, `:300`). With groups present but the filter matching none, a centered `min-h-24` block reads **"No providers match your search."** (`i18n: settings.providers.noKeysMatch`, `en.ts:1136`, `:495`). The search box itself is only rendered when `keyGroups.length > 0`.
- **Rebuild notes:** Group by the backend's own provider identity first and the client's prefix guess only as a fallback, and make one key per provider primary so the card never shows two paste boxes. A better version would test the key against the provider on save and badge the card green/red.

### Settings → Archived Chats page (`SessionsSettings`)  `id: gapfill-desktop-settings-3-r0.sessions-page`
- **Surface:** Desktop app

Re-run setup only if something is broken."** (`i18n: settings.toolsets.postSetupInstalledHint`, `en.ts:1210`, `:352`), a primary-tone pill **"Installed"** with a `Check` (`i18n: settings.toolsets.postSetupInstalled`), and a low-key text button **"Re-run setup"** (`i18n: settings.toolsets.postSetupRerun`) that also becomes **"Installing…"**. Both states render a `Terminal` icon when idle.
- **Outputs / side effects:** Spawns a server-side action; streams its log into a scrollable `max-h-48` monospace `<pre>` (selectable), showing **"Starting…"** (`i18n: settings.toolsets.postSetupStarting`) until the first line arrives; feeds the desktop activity rail; on completion toasts **"Setup complete"** / **"{step} installed."** (`i18n: settings.toolsets.postSetupCompleteTitle` / `postSetupCompleteMessage`) or **"Setup finished with errors"** / **"Check the {step} log."** (`postSetupErrorTitle` / `postSetupErrorMessage`), then calls `onComplete` → the panel's `refresh()`.
- **Config / env:** The provider's `post_setup` hook key; the install itself touches the host (npm/pip/global binaries).
- **Edge cases / guards:** A spawn failure or a thrown poll toasts **"Failed to run {step} setup"** (`i18n: settings.toolsets.postSetupFailed`). The poll ceiling is 150 × 1.2 s ≈ 3 minutes of tailing; the action keeps running server-side past that. The log block only renders once there are lines or the action is still running.
- **Rebuild notes:** Spawn server-side, poll a bounded loop, tail the log verbatim, and make the already-installed state visually distinct so clicking around does not look like reinstalling. A better version would stream the log over a socket and offer a cancel.

### Toolset panel → per-backend model catalog picker  `id: gapfill-desktop-settings-3-r0.toolset-model-catalog`
- **Surface:** Desktop app
- **Where:** Capabilities → Tools → **image_gen** or **video_gen** toolset → an expanded provider row. Component `ModelCatalogPicker` (`toolset-config-panel.tsx:381-508`), gated by `MODEL_CATALOG_TOOLSETS = new Set(['image_gen', 'video_gen'])` (`:52`) and mounted at `:899-905`.
- **What it does:** Lists the models a generation backend offers, with speed / strengths / price, and persists the chosen one.
- **How it works:** `getToolsetModels(toolset, providerName, profile)` → `GET /api/tools/toolsets/{name}/models?provider=…` (`api/toolsets.ts:44-54`). A rejection (older backend, or a provider with no catalog) sets `catalog = null` and the section hides itself entirely rather than erroring (comment `:414-416`). `pick(modelId)` calls `selectToolsetModel(toolset, modelId, providerName, profile)` → `PUT /api/tools/toolsets/{name}/model` (`api/toolsets.ts:57-66`) and mirrors `catalog.current` locally. Selection highlight is `catalog.current ?? catalog.default`.
- **Inputs / options:** A section header **"Model"** (`i18n: settings.toolsets.modelSectionTitle`) with the right-aligned count **"{n} model"** / **"{n} models"** (`i18n: settings.toolsets.modelCount`); one radio-style `button` per model showing `model.display || model.id` in monospace, an **"In use"** pill with a `Check` (`i18n: settings.toolsets.modelInUse`) on the selected one, a **"default"** pill (`i18n: settings.toolsets.modelDefault`) on the catalog default when it is not selected, a spinner while saving that model, and a caption row with `model.speed`, `model.strengths` and a monospace `model.price` when present. `aria-pressed` reflects selection.
- **Outputs / side effects:** Writes `image_gen.model` / `video_gen.model`; a success toast titled **"Model selected"** with **"{model} applies to new sessions."** (`i18n: settings.toolsets.modelSelectedTitle` / `modelSelectedMessage`).
- **Config / env:** `image_gen.model`, `video_gen.model`.
- **Edge cases / guards:** While fetching, an inline row shows a spinner and **"Loading model catalog..."** (`i18n: settings.toolsets.loadingModels`, `en.ts:1230`, `:454`). When the provider is not the active backend, every card is `opacity-60` and disabled, and a caption reads **"Select this backend first to change its model."** (`i18n: settings.toolsets.modelInactiveHint`, `en.ts:1235`, `:471`). An empty / `has_models:false` catalog renders nothing. A failed save toasts **"Failed to select {model}"** (`i18n: settings.toolsets.failedSelectModel`).
- **Rebuild notes:** Serve a per-provider model catalog with display/speed/strengths/price and a default, disable the picker for non-active backends, and hide the whole section when the backend has no catalog. A better version would show sample outputs and live per-model pricing.

### Settings → Execution backend panel (`TerminalBackendPanel`)  `id: gapfill-desktop-settings-3-r0.terminal-backend-panel`
- **Surface:** Desktop app
- **Where:** Capabilities → Tools → the **terminal** toolset detail, rendered above the generic toolset panel (`apps/desktop/src/app/skills/index.tsx:1174`). Component `apps/desktop/src/app/settings/terminal-backend-panel.tsx:48`. Section title **"Execution backend"** (`i18n: settings.toolsets.terminalBackend.sectionTitle`, `:116`).
- **What it does:** Lists every terminal execution backend with a live health probe and lets you switch which one runs the agent's commands.
- **How it works:** `refresh()` calls `getTerminalBackends()` → `GET /api/tools/terminal/backends` (`api/toolsets.ts:112-116`), returning `{active, backends:[{name, label, description, status, detail, active}]}` where `status ∈ {ready, needs_setup, unavailable}` comes from a real probe (Docker daemon reachable, SSH host configured, Modal/Daytona credentials present — comment `:40-46`). `handleSelect(backend)` returns early when the backend is already active or a selection is in flight, then calls `selectTerminalBackend(name)` → `PUT /api/tools/terminal/backend` (`api/toolsets.ts:119-124`) and mirrors `active` locally (probes are unchanged by a select, comment `:80-81`). Selecting a needs-setup backend is deliberately allowed — the row shows what is missing instead of blocking, matching the CLI configurator.
- **Inputs / options:** A `RefreshCw` icon button on the section header (disabled and spinning while loading) that re-probes; one full-width `button` per backend with `aria-pressed={backend.active}`, showing `backend.label`, a `StatusPill` — **"Ready"** with a `Check` in primary tone (`i18n: settings.toolsets.terminalBackend.ready`), otherwise a muted pill with an `AlertTriangle` reading **"Needs setup"** (`terminalBackend.needsSetup`) or **"Unavailable"** (`terminalBackend.unavailable`) — plus an **"In use"** pill with a `Check` (`terminalBackend.inUse`) on the active row, a spinner while selecting, `backend.description` as a caption, and for a non-ready backend an amber `AlertTriangle` line with `backend.detail`. Every row is disabled while any selection is in flight.
- **Outputs / side effects:** `PUT /api/tools/terminal/backend` writes `terminal.backend`; a success toast titled **"Backend selected"** (`i18n: settings.toolsets.terminalBackend.selectedTitle`) with **"Terminal commands now run via {backend}. Applies to new sessions."** (`terminalBackend.selectedMessage`); `onConfiguredChange?.()` refreshes the parent's derived pills.
- **Config / env:** `terminal.backend` (the same enum the Config editor exposes); the probes read Docker/SSH/Modal/Daytona/Vercel settings and credentials.
- **Edge cases / guards:** While the first probe runs (`loading && !data`) an inline spinner row reads **"Checking execution backends…"** (`i18n: settings.toolsets.terminalBackend.loading`, `en.ts:1241`, `:104`). A failed probe toasts **"Could not load terminal backends"** (`terminalBackend.failedLoad`) and, with no prior data, the panel renders `null`. When the *active* backend is not ready, its amber detail line is suffixed with **"You can select this backend now — commands will fail until setup is complete."** (`terminalBackend.needsSetupHint`, `:152`). A failed select toasts **"Failed to select {backend}"** (`terminalBackend.failedSelect`).
- **Rebuild notes:** Probe each backend server-side, return `{status, detail}` per row, allow selecting a not-ready backend while saying exactly what is missing, and apply the change to new sessions only. A better version would offer a one-click remediation per detail (start Docker, install the CLI, open the SSH settings).

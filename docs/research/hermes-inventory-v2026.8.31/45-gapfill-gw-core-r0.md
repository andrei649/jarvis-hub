# Gap-fill: Gateway core — kanban wake-notification message composer

Round-0 gap-fill for the `gw-core` area. It documents the three user-visible text blocks that the
gateway kanban notifier assembles into the **synthetic wake turn** it injects into a chat/session when
a watched board task changes status: the base notification body (`gateway.kanban.wake.message`), the
review/request-changes detail block (`gateway.kanban.wake.review_detail`), and the standing
anti-re-decomposition guidance suffix (`gateway.kanban.wake.guidance`).
Deliberately left to sibling shards: the notifier loop's cursor/claim/rewind machinery and the
dispatcher (`gw-core.kanban-watchers`), the passive platform ping strings (`gw-slash`), the
`hermes kanban notify-subscribe` CLI and board schema (`automation`), and `gateway/wake.py`'s
push-vs-self-post transport choice (`gw-core` / `platforms-*`).

### Kanban wake notification — base message body  `id: gapfill-gw-core-r0.kanban-wake-message`
- **Surface:** Gateway/Telegram
- **Where:** Appears as an **incoming user turn in the chat/session that subscribed to the task** (Telegram/Discord/Slack/plugin platform DM, group or thread; on the API-server platform it is self-posted into the raw `X-Hermes-Session-Id` session). It is not typed by anyone — the gateway forges it. Verbatim template, `i18n: gateway.kanban.wake.message` (`locales/en.yaml:198`):

  ```
  [kanban] Task {task_id} {status}.
  Title: {title}
  Assignee: @{assignee}
  Board: {board}

  Check the result or decide the next step.
  ```

- **What it does:** When a subscribed kanban task reaches a decision-bearing state, the gateway wakes the originating agent session with this message so the agent takes a real turn (reads the board, inspects the result, replies) instead of the user only getting a one-line passive ping. It names the task, its new status, its title, the worker that owned it and the board it lives on.
- **How it works:** Built in `gateway/kanban_watchers.py:888` inside `GatewayKanbanWatchersMixin._kanban_notifier_watcher` (declared `gateway/kanban_watchers.py:224`, spawned as the supervised task `kanban_notifier_watcher` at `gateway/run.py:14320`, tick `interval: float = 5.0` seconds). Flow per tick: for every board on disk the notifier claims unseen `task_events` rows past each subscription's cursor whose kind is in `TERMINAL_KINDS = ("completed","blocked","gave_up","crashed","timed_out","status","archived","unblocked","block_loop_detected","review_requested","changes_requested")` (`gateway/kanban_watchers.py:267`). A separate, narrower tuple decides whether to *wake*: `_WAKE_KINDS = ("completed","gave_up","crashed","timed_out","blocked","review_requested","changes_requested","block_loop_detected")` (`gateway/kanban_watchers.py:843`) — `status`, `archived` and `unblocked` are delivered but are deliberately bookkeeping-only and never wake. Waking is enabled when the subscription's `delivery_mode` is `notify+wake` or `wake` (`wake_agent = mode in ("notify+wake","wake")`, `gateway/kanban_watchers.py:566`; valid modes `_NOTIFY_DELIVERY_MODES = ("notify","notify+wake","wake")` at `hermes_cli/kanban_db.py:11358`, column `delivery_mode TEXT NOT NULL DEFAULT 'notify'` on `kanban_notify_subs`, `hermes_cli/kanban_db.py:1510`).
  Composition (`gateway/kanban_watchers.py:872-913`): `_title = (task.title if task else sub["task_id"])[:120]`; `_assignee = task.assignee if task else ""`; `board` = the board slug of the subscription. The `{status}` slot is the **join of one localized phrase per distinct wake kind seen in this claim**, joined with `gateway.kanban.wake.status_joiner` = `", "`, falling back to `gateway.kanban.wake.status_default` = `"status changed"` when the set is empty. The per-kind phrases (all `locales/en.yaml:186-195`) are: `completed` → `"completed"`, `gave_up` → `"gave up (retries exhausted)"`, `crashed` → `"crashed (worker exited); dispatcher will retry"`, `timed_out` → `"timed out; dispatcher will retry"`, `blocked` → `"blocked; needs attention"`, `review_requested` → `"handed off for review; the implementation is done"`, `changes_requested` → `"review requested changes (BLOCK); implementation is not approved"`, `block_loop_detected` → `"routed to triage after repeated blocks; needs a decision"`.
  Optional appended blocks, in this order: (1) the worker handoff line `gateway.kanban.wake.handoff` = `"Result: {summary}"` when the `completed` or `review_requested` event payload carried a `summary` (first line, 200 chars; legacy fallback `task.result`, first line, 160 chars) — `gateway/kanban_watchers.py:900`; (2) the review detail block (see `gapfill-gw-core-r0.kanban-wake-review-detail`); (3) the guidance suffix, always (see `gapfill-gw-core-r0.kanban-wake-guidance`).
  Delivery is chosen by `gateway/wake.py`: `adapter_supports_push(adapter)` reads the adapter class flag `supports_async_delivery` (default True). Push-capable adapters get a synthetic `MessageEvent(text=_synth, message_type=MessageType.TEXT, source=SessionSource(...), internal=True)` handed to `adapter.handle_message`; the non-push API-server adapter gets a self-`POST /v1/chat/completions` carrying the raw session id in `X-Hermes-Session-Id` (`gateway/wake.py:1-24, 56-90`), with `WAKE_TURN_TIMEOUT_SECONDS = 600.0` and retry backoff `_RETRY_DELAYS_SECONDS = (2.0, 5.0, 10.0)`.
  Session targeting: push adapters wake `task.session_id`; non-push adapters wake `sub["chat_id"]` (the raw subscriber session id), falling back to `task.session_id` only for legacy rows (`gateway/kanban_watchers.py:855-870`). The push `SessionSource` is rebuilt from `sub["chat_type"]` (then `delivery_metadata["chat_type"]`, then `"group"`), plus `thread_id`, `user_id`, `user_id_alt`, `profile` and `scope_id=_wake_scope_id(adapter, sub)` (`gateway/kanban_watchers.py:963-1001`; `_wake_scope_id` at `:173` prefers `delivery_metadata["scope_id"|"slack_team_id"|"team_id"]`, then `adapter.scope_id_for_chat(chat_id)`).
- **Inputs / options:** Template placeholders, all five: `{task_id}`, `{status}`, `{title}`, `{assignee}`, `{board}`. Governing subscription fields: `delivery_mode` (`notify` | `notify+wake` | `wake`), `platform`, `chat_id`, `thread_id`, `chat_type`, `user_id`, `user_id_alt`, `notifier_profile`, `delivery_metadata`, `cursor`. Wake-triggering event kinds, all eight: `completed`, `gave_up`, `crashed`, `timed_out`, `blocked`, `review_requested`, `changes_requested`, `block_loop_detected`. Non-waking but delivered kinds: `status`, `archived`, `unblocked`. Status phrases available for the `{status}` slot, all nine including the fallback: `"completed"`, `"gave up (retries exhausted)"`, `"crashed (worker exited); dispatcher will retry"`, `"timed out; dispatcher will retry"`, `"blocked; needs attention"`, `"handed off for review; the implementation is done"`, `"review requested changes (BLOCK); implementation is not approved"`, `"routed to triage after repeated blocks; needs a decision"`, `"status changed"`; joiner `", "`.
- **Outputs / side effects:** A full agent turn runs in the subscriber's session, with its own tool calls and reply — so the wake can cost tokens and produce visible output. On success the subscription cursor advances (`_kanban_advance`, `gateway/kanban_watchers.py:1108`) which is the dedup mechanism. On the two paths where the wake **is** the delivery (non-push adapters, and `delivery_mode='wake'` push subs) the cursor advances only after the wake succeeds; failure bumps a per-subscription counter and rewinds the claim (`_kanban_rewind`, `:1142`). For `notify+wake` push subs the visible ping is the delivery, the cursor has already advanced, and the wake injection is best-effort (logged at WARNING with traceback). Log lines: `kanban notifier: woke agent for %s on %s/%s profile=%s events=%s`, `kanban notifier: wake self-post failed for %s (attempt %d/%d): %s`, `kanban notifier: wake-only delivery failed for %s (attempt %d/%d): %s`, `kanban notifier: wakeup injection failed for %s: %s`, `kanban notifier: dropping subscription %s on %s after %d consecutive wake failures`.
- **Config / env:** `kanban.dispatch_in_gateway` (gates the sibling dispatcher loop, not the notifier — the notifier always runs in a gateway); board selection via `HERMES_KANBAN_BOARD` / `HERMES_KANBAN_DB` / `HERMES_KANBAN_HOME`; locale selection for `agent.i18n.t` (`locales/<lang>.yaml`, key path `gateway.kanban.wake.message`). Subscription rows live in the `kanban_notify_subs` table of the board's SQLite DB (default `~/.hermes/kanban.db`).
- **Edge cases / guards:** Title truncated to 120 chars; handoff summary to 200 chars (legacy `task.result` to 160); the whole message is skipped when no claimed event is in `_WAKE_KINDS` or when `delivery_mode == "notify"`. `MAX_SEND_FAILURES = 12` consecutive failures (~60 s at the 5 s tick) drops the subscription via `_kanban_unsub`; below that the claim is rewound so the event is not lost. Subscriptions are removed only on `archived`, never on `done`, because completed work is reopenable. Adapter disconnected before delivery → rewind, no message. If the adapter has no push channel and `wake_agent` is set, the doomed text `send()` is skipped entirely and the self-post becomes the sole delivery. `chat_type` mismatch degrades to a fresh session rather than raising.
- **Rebuild notes:** Minimal spec: a poll loop over `(subscription, cursor)` rows; claim events atomically past the cursor; map each event kind to a localized status phrase; render a five-slot template; append handoff/review/guidance blocks; deliver as a synthetic inbound message (push) or an authenticated self-request to your own chat-completions endpoint (stateless); advance the cursor **after** the delivery that actually reaches the user, and rewind otherwise. A better version would deduplicate consecutive wakes for one task into a single digest turn, carry structured metadata (task id, board, diff/artifact links) as machine-readable fields alongside the prose so the agent need not re-parse, and let the operator template the message per board.

### Kanban wake notification — review/request-changes detail block  `id: gapfill-gw-core-r0.kanban-wake-review-detail`
- **Surface:** Gateway/Telegram
- **Where:** Extra paragraph appended to the wake message body (above the guidance suffix) whenever the claimed events include a `changes_requested` transition. Verbatim, `i18n: gateway.kanban.wake.review_detail` (`locales/en.yaml:200`):

  ```
  Review feedback: {reason}
  Inspect the existing card and its current review run; return work to the same implementation task. Do not treat this BLOCK as approval and do not create a duplicate task.
  ```

- **What it does:** Tells the woken agent exactly why a reviewer rejected the work, and instructs it to push the fix back through the *existing* card/review run rather than filing a new task or reading the BLOCK as a pass.
- **How it works:** `gateway/kanban_watchers.py:905-909` — appended as `"\n" + t("gateway.kanban.wake.review_detail", reason=wake_review_detail)` when `wake_review_detail` is non-empty. `wake_review_detail` is set at `gateway/kanban_watchers.py:670` while rendering the `changes_requested` event: `reason = _safe_review_reason(payload.get("reason"))`, then `reason_text = reason or "reviewer feedback requires changes"`. `_safe_review_reason` (`gateway/kanban_watchers.py:36-49`) runs `agent.redact.redact_sensitive_text(value, force=True, redact_url_credentials=True)`, replaces local filesystem paths with the literal `[local path]` via `_LOCAL_PATH_RE` (`:29` — matches `/Users|/home|/private|/tmp|/var|/etc|/workspace` prefixes and `C:\…` style Windows paths), collapses whitespace, and truncates to `limit` (default 160) with a trailing `…`. The same event also produces the visible ping `🛑 {board_tag}Kanban {task_id} review requested changes/BLOCK: {reason_text}{provenance}` where provenance is ` — reviewer @{reviewer}` and/or ` → implementer @{implementer}`, each redacted with `_safe_review_reason(..., 48)`.
- **Inputs / options:** Placeholder `{reason}`. Source payload fields on the `changes_requested` event: `reason`, `reviewer`, `implementer`. Truncation limits: 160 chars for `reason`, 48 for `reviewer` / `implementer`. Default reason when the payload has none: `"reviewer feedback requires changes"`.
- **Outputs / side effects:** Adds one paragraph to the synthetic turn; no disk or network side effects of its own. It is what makes the woken agent resume the *same* implementation task instead of creating a duplicate card.
- **Config / env:** `i18n` locale file `locales/<lang>.yaml` key `gateway.kanban.wake.review_detail`; no dedicated config key or env var.
- **Edge cases / guards:** Only `changes_requested` sets it — a plain `blocked` event does not. Secrets and URL credentials are redacted before the text leaves the process (the wake can be delivered to an external chat platform), and absolute local paths are masked. If several events in one claim include `changes_requested`, the last one wins (`wake_review_detail` is overwritten in the event loop). Empty/`None` reason falls back to the default sentence, so the block is never rendered with a blank `{reason}`.
- **Rebuild notes:** Minimal spec: on a review-rejection event, redact and truncate the reviewer's reason, then append it plus an explicit "do not duplicate the card, do not treat this as approval" instruction to the wake turn. A better version would attach the review run id and a diff/comment permalink so the agent can jump straight to the rejected artifact, and would carry the reviewer's per-criterion verdicts as structured fields instead of one prose line.

### Kanban wake notification — standing anti-re-decomposition guidance  `id: gapfill-gw-core-r0.kanban-wake-guidance`
- **Surface:** Gateway/Telegram
- **Where:** Final paragraph of **every** kanban wake message, separated by a blank line. Verbatim, `i18n: gateway.kanban.wake.guidance` (`locales/en.yaml:201`):

  ```
  This is an automatic task-status notification, not a request to decompose the task again. Inspect the current board before creating follow-up tasks; do not recreate tasks or graphs that already exist.
  ```

- **What it does:** Labels the injected turn as machine-generated so the woken agent does not mistake it for a fresh user request and re-plan/re-split work that is already on the board.
- **How it works:** `gateway/kanban_watchers.py:911-913` — unconditionally `_synth += "\n\n" + t("gateway.kanban.wake.guidance")` after the optional handoff and review-detail blocks, so it is the last thing the model reads before it acts. The in-code rationale is recorded at `gateway/kanban_watchers.py:895-899` ("Graph-safe wake turn (#70752): carry the worker's completion handoff into the synthetic turn and label it as an automatic notification so the woken creator inspects the board instead of re-decomposing work that already exists"). Pairs with the handoff line `gateway.kanban.wake.handoff` = `"Result: {summary}"`: the summary tells the agent what already happened, this sentence tells it not to redo the planning.
- **Inputs / options:** No placeholders — a fixed sentence pair. Not user-configurable except by editing/overriding the locale file.
- **Outputs / side effects:** Two extra sentences at the end of the synthetic turn; in practice it suppresses duplicate `kanban_create` / decomposition fan-out from the woken orchestrator session.
- **Config / env:** `locales/<lang>.yaml` key `gateway.kanban.wake.guidance`; no config key, no env var.
- **Edge cases / guards:** Always appended, for every wake kind including `completed` and `block_loop_detected`; there is no flag to suppress it. It is guidance only — it is not enforced by a tool gate, so a model can still ignore it (the `kanban.auto_decompose` toggle, read fresh each dispatcher tick via `_resolve_auto_decompose_settings` at `gateway/kanban_watchers.py:52`, is the hard stop for runaway fan-out).
- **Rebuild notes:** Minimal spec: mark every machine-injected turn as such, in-band, and state the one failure mode you fear most (here: re-decomposition of an existing task graph). A better version would enforce it structurally — pass the wake as a distinct message role/flag the agent runtime understands, and refuse `create task` calls whose title/graph already exists on the board rather than relying on a prose instruction.

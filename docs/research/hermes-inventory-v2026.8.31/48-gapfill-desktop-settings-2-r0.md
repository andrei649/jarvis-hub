# Gap-fill — Hermes Desktop Settings → Gateways: connection modes, Hermes Cloud, connections registry, managed updates (round 0, area `desktop-settings-2`)

Scope: the whole **Settings → "Gateways"** page of the Electron desktop app (`apps/desktop/src/app/settings/gateway-settings.tsx`,
`connections-registry.tsx`, `managed-updates-section.tsx`) — the four connection modes (Local / Hermes Cloud / Remote / SSH), the
Hermes Cloud sign-in + org picker + agent discovery, the remote URL auth probe, the OAuth/password sign-in row, the session-token
box and its plain-text opt-in, the OS-keychain encryption toggle, Diagnostics, the **Registered gateways** registry (list rows,
editor, extra headers, duplicate rules, Update-all, launch mode) and the **Managed updates** transactional SSH updater.
Deliberately left to sibling shards: the Settings frame/nav/search and every schema-driven config field (`desktop-settings.md`),
the non-schema Appearance/Notifications/Plugins rows (`gapfill-desktop-settings-0-r0.md`), the boot-failure recovery overlay that
embeds this same panel and the shared sign-in toasts (`gapfill-desktop-a-r0.md`), the first-run `install.*` remote form
(`gapfill-desktop-main-r0.md`), and the Electron main-process IPC/backing stores themselves (`desktop-main.md`).

### Settings → Gateways page (`GatewaySettings`)  `id: gapfill-desktop-settings-2-r0.gateway-page`
- **Surface:** Desktop app
- **Where:** Settings overlay → left nav entry **"Gateways"** (`i18n: settings.nav.gateway`, `apps/desktop/src/i18n/en.ts:397`), route `/settings?tab=gateway` (`apps/desktop/src/app/settings/index.tsx:229-233`, `:378-381`). Page header: a `Globe` icon + **"Gateway Connection"** (`i18n: settings.gateway.title`) with the intro paragraph **"Local by default. Use remote when this app should drive a Hermes backend elsewhere. Gateway connections are machine-level; profiles are discovered from the gateways you connect."** (`i18n: settings.gateway.intro`). The legacy deep link `/settings?tab=connections` redirects here (`index.tsx:60-61`, `:93-98`, `:378`).
- **What it does:** Chooses which Hermes backend this desktop window talks to and manages every registered gateway. It is the single page that owns connection mode, credentials, the connections registry and managed SSH updates.
- **How it works:** `GatewaySettings({ embedded = false })` at `apps/desktop/src/app/settings/gateway-settings.tsx:154`. On mount it calls `window.hermesDesktop.getConnectionConfig(null)` (IPC `hermes:connection-config:get`, `apps/desktop/electron/preload.ts:174`) and folds the result through `normalizeGatewaySettingsState()` (`:82-91`, merges non-null fields over `EMPTY_STATE` at `:65-80`) plus `savedCloudConnectionUrl()` (`:93`). State fields: `envOverride`, `mode` (`'local' | 'remote' | 'cloud' | 'ssh'`), `remoteAuthMode` (`'oauth' | 'token'`), `remoteOauthConnected`, `remoteTokenPreview`, `remoteTokenSet`, `secureTokenStorage` (default `true`), `remoteTokenPlainText`, `remoteUrl`, `cloudOrg`, `sshHost`, `sshUser`, `sshPort`, `sshKeyPath`, `sshRemoteHermesPath`, `sshRemoteProfile` (`:41-61`). While `loading` the page renders `<SettingsSkeleton sections={[{heading:true,rows:3},{heading:true,rows:3}]} />` (`:1063-1071`). The catalog string **"Loading gateway settings..."** (`i18n: settings.gateway.loading`, `en.ts:841`) is the legacy loading copy for this page and has **no reader in v2026.8.31** — the skeleton replaced it; keep the key for translation parity. Persistence: `connection.json` under Electron `app.getPath('userData')` (`electron/main.ts:823`) for the window connection, `connections.json` for the registry (`main.ts:828`).
- **Inputs / options:** `embedded` prop (boolean, default `false`) — when true the page drops its own header/intro, the **"Save for next restart"** button, the keychain + Diagnostics rows and the registry/managed-update sections, leaving only the connection controls (used by the boot-failure recovery card). No keyboard shortcuts of its own; the Settings frame owns Escape/search.
- **Outputs / side effects:** Reads/writes `connection.json` and `connections.json`; can restart the desktop's gateway connection in place; raises toasts through `notify`/`notifyError`.
- **Config / env:** `HERMES_DESKTOP_REMOTE_URL`, `HERMES_DESKTOP_REMOTE_TOKEN` (either one forces `envOverride`); `HERMES_HOME` (log path root, `main.ts:851`).
- **Edge cases / guards:** If the preload bridge lacks `getConnectionConfig` the page returns an `EmptyState` with title **"Gateway settings unavailable"** (`i18n: settings.gateway.unavailableTitle`) and description **"The desktop IPC bridge does not expose gateway settings."** (`i18n: settings.gateway.unavailableDesc`) — `gateway-settings.tsx:1074-1076`. A failed initial load raises the error toast titled **"Gateway settings failed to load"** (`i18n: settings.gateway.failedLoad`, `:280`). A cancel-flag guards the async load against unmount (`:259-288`).
- **Rebuild notes:** Minimal spec: one page holding {mode, url, credentials} loaded from a machine-level JSON file over IPC, a skeleton while loading, a hard empty state when the bridge is missing, and an embeddable variant for recovery. A better version would stream live connection health into the page instead of requiring a manual Test.

### Environment-override banner  `id: gapfill-desktop-settings-2-r0.gateway-env-override`
- **Surface:** Desktop app
- **Where:** Settings → Gateways, directly under the intro. A destructive-tinted box with an `AlertCircle`, bold line **"Environment variables are controlling this desktop session."** (`i18n: settings.gateway.envOverrideTitle`) and body **"Unset HERMES_DESKTOP_REMOTE_URL and HERMES_DESKTOP_REMOTE_TOKEN to use the saved setting below."** (`i18n: settings.gateway.envOverrideDesc`). Plus a pill **"env override"** (`i18n: settings.gateway.envOverride`) next to the page title.
- **What it does:** Tells the user the saved settings on this page are inert because environment variables are dictating the connection, and disables every control that would change it.
- **How it works:** Rendered when `state.envOverride` is true (`gateway-settings.tsx:1092-1101`); the pill at `:1084`. `envOverride` arrives from the main process in the connection-config payload. Every mode card gets `disabled={state.envOverride}` (`:1109`, `:1117`, `:1125`, `:1133`), the whole cloud/remote/ssh panels are gated on `!state.envOverride` (`:1147`, `:1286`, `:1392`), and both save buttons plus Test remote are disabled (`:1508`, `:1530`, `:1536`).
- **Inputs / options:** None — read-only banner.
- **Outputs / side effects:** Purely visual; blocks mutation.
- **Config / env:** `HERMES_DESKTOP_REMOTE_URL`, `HERMES_DESKTOP_REMOTE_TOKEN`.
- **Edge cases / guards:** The saved config is still displayed underneath (so the user can see what will apply once the vars are unset); the SSH panel is also hidden under env override even though env vars never describe an SSH connection.
- **Rebuild notes:** Compute an `envOverride` boolean in the process that reads the env, ship it with the config, and let the UI fail closed. Better: name which variable is set and offer a one-click "ignore env for this session".

### Connection mode cards (Local / Hermes Cloud / Remote gateway / Connect via SSH)  `id: gapfill-desktop-settings-2-r0.gateway-mode-cards`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → section label **"Connection mode"** (`i18n: settings.gateway.modeTitle`, `gateway-settings.tsx:1105`), then a responsive grid (1 / 2 / 4 columns) of four selectable cards at `:1106-1142`.
- **What it does:** Picks how this desktop window reaches a Hermes backend. Selecting a card swaps the form below it; nothing is persisted until Save/Apply (except Cloud, which applies on agent select).
- **How it works:** `ModeCard()` at `gateway-settings.tsx:98-141` — a `<button type="button">` styled by `selectableCardClass({active, prominent:true})`, showing `icon`, `title`, an optional `HelpCircle` tooltip carrying `hint` (the tooltip swallows the click via `stopPropagation`), a `Check` when active, and `description` beneath. `onSelect` sets `state.mode`; `disabled` comes from `envOverride`.
- **Inputs / options:** Exactly four cards, in DOM order:
  1. **"Local gateway"** (`i18n: settings.gateway.localTitle`), icon `Monitor`, description **"Start a private Hermes backend on localhost. This is the default and works offline."** (`i18n: settings.gateway.localDesc`, `:1110`). No hint.
  2. **"Hermes Cloud"** (`i18n: settings.gateway.cloudTitle`), icon `Cloud`, description **"Sign in once to Hermes Cloud and pick from the agents on your account — no URL to paste."** (`i18n: settings.gateway.cloudDesc`, `:1118`). No hint.
  3. **"Remote gateway"** (`i18n: settings.gateway.remoteTitle`), icon `Globe`, description **"Connect this desktop shell to a remote Hermes backend."** (`i18n: settings.gateway.remoteDesc`, `:1126`), hint tooltip **"Hosted gateways use OAuth or a username and password; self-hosted ones may use a session token."** (`i18n: settings.gateway.remoteAuthHint`, `:1128`).
  4. **"Connect via SSH"** (`i18n: settings.gateway.sshTitle`), icon `Terminal`, description **"Hermes is launched on the remote over SSH and tunneled to this app — nothing to start or expose yourself. Requires working key-based SSH access to the host."** (`i18n: settings.gateway.sshDesc`), hint tooltip **"The first presented host key is trusted and pinned; later changes fail closed."** (`i18n: settings.gateway.sshTrustHint`, `:1137`).
- **Outputs / side effects:** Local state only, until a save. Changing mode also bumps every request-sequence counter and clears the last test line (`:437-452`).
- **Config / env:** Persisted as `mode` in `connection.json`.
- **Edge cases / guards:** All four are disabled under env override. Switching away from `cloud` stops the cloud status/discovery effect (`:750-799` is keyed on `state.mode`); switching into `ssh` triggers `sshConfigHosts()` (`:414-435`).
- **Rebuild notes:** Four radio-like cards over one enum; the hint is a tooltip, not body text, so the card stays scannable. A better version would probe reachability per mode and grey out modes that cannot work on this machine (e.g. no `ssh` binary).

### Hermes Cloud sign-in row  `id: gapfill-desktop-settings-2-r0.gateway-cloud-signin`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Hermes Cloud) first row, title **"Hermes Cloud"** (`i18n: settings.gateway.cloudSignInTitle`, `gateway-settings.tsx:1170`).
- **What it does:** Signs the desktop into the Nous portal once; that single portal session then powers agent discovery and the silent per-agent sign-in cascade.
- **How it works:** Signed-out state renders a primary button **"Sign in to Hermes Cloud"** (`i18n: settings.gateway.cloudSignIn`, `:1165`) with a `LogIn` icon (spinner while `cloudSigningIn`) calling `cloudSignIn()` (`:804-833` → `window.hermesDesktop.cloud.login()`, IPC `hermes:cloud:login`, `preload.ts:214`); on `signedIn: true` it immediately runs `discoverCloud()`. Signed-in state renders the primary pill **"Signed in to Hermes Cloud"** (`i18n: settings.gateway.cloudSignedIn`, `:1155`) with a `Check`, plus an outline button **"Sign out"** (`i18n: settings.gateway.signOut`) calling `cloudSignOut()` (`:837-866` → `cloud.logout()`, IPC `hermes:cloud:logout`). The row description flips between **"Sign in to Hermes Cloud to discover the agents on your account."** (`i18n: settings.gateway.cloudNeedsSignIn`) and **"You are signed in. Pick an agent below; the session refreshes automatically."** (`i18n: settings.gateway.cloudSignedInDesc`) — both at `:1169`. On entering cloud mode an effect reads `cloud.status()` (IPC `hermes:cloud:status`) and, when signed in, restores the persisted `state.cloudOrg` and auto-discovers (`:750-799`). Portal liveness is judged from the Privy cookies `__Host-privy-token` / `__Secure-privy-token` / `privy-token` (`electron/connection-config.ts:46-63`), not the Hermes gateway session cookies.
- **Inputs / options:** Button **"Sign in to Hermes Cloud"**; button **"Sign out"**; pill **"Signed in to Hermes Cloud"** (non-interactive). Both buttons are disabled while `cloudSigningIn`.
- **Outputs / side effects:** Opens the portal login window (main process); on sign-out clears `cloudSignedIn`, `cloudAgents`, `cloudOrgs`, `cloudOrg` and sets discovery back to `idle`, then toasts success titled **"Signed out of Hermes Cloud"** (`i18n: settings.gateway.cloudSignedOutTitle`) with body **"Cleared the Hermes Cloud session."** (`i18n: settings.gateway.cloudSignedOutMessage`) — `:859`.
- **Config / env:** Portal endpoint is fixed (`https://portal.nousresearch.com`); the chosen org is persisted as `cloudOrg` in `connection.json`.
- **Edge cases / guards:** A sign-in failure toasts **"Hermes Cloud sign-in failed"** (`i18n: settings.gateway.cloudSignInFailed`, `:828`); a sign-out failure toasts **"Sign-out failed"** (`i18n: settings.gateway.signOutFailed`, `:862`). A stale `signingSeq` (mode switched mid-flight) drops the result silently. If the preload has no `cloud` bridge the handlers return early and the panel is inert.
- **Rebuild notes:** One shared portal cookie jar in the privileged process, a `status/login/logout` triple over IPC, and UI that treats "signed in" as derived state you re-read rather than cache. A better version would refresh the portal token in the background and never show a signed-out state that is actually renewable.

### Hermes Cloud organization picker  `id: gapfill-desktop-settings-2-r0.gateway-cloud-orgs`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Hermes Cloud, signed in, multi-org account with no org chosen) — heading **"Choose an organization"** (`i18n: settings.gateway.cloudOrgPickerTitle`, `gateway-settings.tsx:1180`) over one row per org. Once an org is chosen, a text button **"Change org"** (`i18n: settings.gateway.cloudOrgChange`, `:1213`) sits in the agent-list header.
- **What it does:** Scopes agent discovery to one organization for users who belong to several, and lets them switch afterwards.
- **How it works:** `discoverCloud(org?)` (`:674-729`) calls `cloud.discover(org)` (IPC `hermes:cloud:discover`, `electron/main.ts:15409`). A response `{ needsOrgSelection: true, orgs }` (NAS 409) stores `orgs`, clears the agent list and renders the picker; otherwise the org is recorded **authoritatively from the response** (`result.org.slug ?? result.org.id`) falling back to the requested `org` (`:707-719`). The selected org is mirrored into `cloudOrgRef` **and** state via `setCloudOrg()` (`:246-249`) so a Connect click in the same render tick persists the freshly resolved org rather than a stale `null`. `selectCloudOrg(org)` (`:736-740`) sets the ref+state and re-runs discovery scoped to it. `changeCloudOrg()` (`:746-750`) clears the org and the agent list and re-discovers with no arg — a multi-org user gets the picker back, a single-org user silently auto-resolves. `DesktopCloudOrg` = `{ id, slug, name, isPersonal, role }` (`src/global.d.ts:1066-1073`).
- **Inputs / options:** Per-org `ListRow` with title = the org `name`, description = **"Role: {role}"** (`i18n: settings.gateway.cloudOrgRole`, e.g. `Role: OWNER`) and a small primary button **"Select"** (`i18n: settings.gateway.cloudOrgSelect`). Header button **"Change org"** (text variant, size sm) — shown whenever an org is selected, deliberately *not* gated on `cloudOrgs.length` so a restore-open still offers it.
- **Outputs / side effects:** Re-runs discovery; the chosen org is persisted only when an agent is connected (sent as `cloudOrg` in `applyConnectionConfig`).
- **Config / env:** `cloudOrg` in `connection.json`.
- **Edge cases / guards:** A refresh that returns `needsOrgSelection` does not clear a previously chosen org list. Discovery failures leave the picker and toast **"Could not load your Hermes Cloud agents"**.
- **Rebuild notes:** Treat "which org" as server-authoritative and echo it in the list response; mirror it into a ref because the connect action can fire in the same tick as discovery resolving. Better: remember the last org per account and skip the picker entirely.

### Hermes Cloud agent list (discover + connect)  `id: gapfill-desktop-settings-2-r0.gateway-cloud-agents`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Hermes Cloud, signed in, org resolved) — header **"Your agents"** (`i18n: settings.gateway.cloudAgentsTitle`, `gateway-settings.tsx:1201`) with **"Change org"** and **"Refresh"** buttons on the right, then one row per discovered agent.
- **What it does:** Lists the agents on the signed-in Hermes Cloud account and connects this desktop window to the one you pick — no URL to paste.
- **How it works:** Rows come from `discoverCloud()`. Each `DesktopCloudAgent` is `{ id, name, status, dashboardUrl (null until provisioned), dashboardGatewayState }` (`src/global.d.ts:1054-1062`). `connectCloudAgent(agent)` (`:874-935`) runs `cloud.agentSignIn(agent.dashboardUrl)` (IPC `hermes:cloud:agent-sign-in`, `main.ts:15414`) — the silent per-agent cascade over the shared portal session — then `applyConnectionConfig({mode:'cloud', remoteAuthMode:'oauth', remoteUrl: agent.dashboardUrl, cloudOrg: cloudOrgRef.current})`, which soft-reconnects in place. The currently-connected agent is detected by `isConnectedAgent()` (`:868-869`) comparing `normalizeCloudUrl()` (trim → drop trailing slashes → lowercase, `:866`) of the agent's `dashboardUrl` against `savedCloudConnectionUrl(state)`; matching rows get a `bg-primary/5 ring-1 ring-primary/25` highlight and lose their Connect button.
- **Inputs / options:** Header: **"Change org"** (`i18n: settings.gateway.cloudOrgChange`), **"Refresh"** (`i18n: settings.gateway.cloudRefresh`, `RefreshCw` icon, disabled + spinner while `cloudDiscover === 'loading'`). Loading line: spinner + **"Loading your agents…"** (`i18n: settings.gateway.cloudLoadingAgents`, `:1231`). Empty state (`AlertCircle` + one sentence split around a link, `:1237-1241`): **"No agents found on this account. Create one in the "** (`i18n: settings.gateway.cloudNoAgents.before`) + external link **"Nous portal"** (`i18n: settings.gateway.cloudNoAgents.linkText`, href `https://portal.nousresearch.com/agents`, `showExternalIcon={false}`) + **", then refresh."** (`i18n: settings.gateway.cloudNoAgents.after`). Per-agent row: title = agent `name`, description = **"Status: {dashboardGatewayState}"** (`i18n: settings.gateway.cloudStatusLabel`; values `active` / `degraded` / `down` / `unknown`), action = either the pill **"Connected"** (`i18n: settings.gateway.cloudConnectedPill`) or a button reading **"Connect"** (`i18n: settings.gateway.cloudConnect`), **"Connecting…"** (`i18n: settings.gateway.cloudConnecting`) while this agent is connecting, or **"Provisioning…"** (`i18n: settings.gateway.cloudAgentProvisioning`) when `dashboardUrl` is null. Connect buttons are disabled while any agent is connecting.
- **Outputs / side effects:** Writes a cloud-mode connection to `connection.json` and reconnects the window; success toast titled **"Connected"** (`i18n: settings.gateway.cloudConnectedTitle`) with body **"Connected to {name}."** (`i18n: settings.gateway.cloudConnectedTo`).
- **Config / env:** `mode=cloud`, `remoteUrl`, `remoteAuthMode=oauth`, `cloudOrg` in `connection.json`.
- **Edge cases / guards:** A connect that returns `connected: false` warns with the shared **"Sign-in incomplete"** / **"The login window closed before authentication finished."** pair (`i18n: boot.failure.signInIncompleteTitle` / `signInIncompleteMessage`). A thrown error carrying `needsCloudLogin` flips the panel back to signed-out. Failure toast: **"Could not connect to that agent"** (`i18n: settings.gateway.cloudConnectFailed`, `:932`). Discovery failure toast: **"Could not load your Hermes Cloud agents"** (`i18n: settings.gateway.cloudDiscoverFailed`, `:730`). The bottom Test/Save action row is hidden entirely in cloud mode (`:1494`) because selecting an agent already applies.
- **Rebuild notes:** Discovery returns a list of `{id,name,dashboardUrl,state}`; connect = silent cascade then persist a remote-shaped OAuth connection at that URL. Normalize both URLs identically before comparing or the "connected" highlight breaks on host casing. A better version would show region/version per agent and allow connecting a *second window* to another agent without switching this one.

### Remote URL field  `id: gapfill-desktop-settings-2-r0.gateway-remote-url`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Remote gateway) first row: title **"Remote URL"** (`i18n: settings.gateway.remoteUrlTitle`), description **"Base URL for the remote dashboard backend. Path prefixes are supported, for example /hermes."** (`i18n: settings.gateway.remoteUrlDesc`, `gateway-settings.tsx:1302`), input placeholder `https://gateway.example.com/hermes` (`:1298`).
- **What it does:** Sets the base URL of the remote Hermes backend this desktop shell should drive.
- **How it works:** Controlled `Input` writing `state.remoteUrl`; every consumer uses `trimmedUrl = coerceRemoteUrlScheme(state.remoteUrl)` (`:302`), which prepends `http://` to a scheme-less `host:port` so a pasted Tailscale IP or LAN name parses (mirrored main-side in `normalizeRemoteBaseUrl`, `electron/connection-config.ts:66-84`). The URL is the dedupe key and the probe target.
- **Inputs / options:** One text input (height `h-8`, `CONTROL_TEXT`), disabled under env override. No explicit scheme required.
- **Outputs / side effects:** Drives the debounced auth probe and, on save, the persisted `remoteUrl`.
- **Config / env:** `remoteUrl` in `connection.json`; overridden by `HERMES_DESKTOP_REMOTE_URL`.
- **Edge cases / guards:** Only `^https?://` URLs are probed (`:311-318`); explicit non-http schemes (`ftp://`, `file://`) are rejected by the main-process normalizer.
- **Rebuild notes:** Accept scheme-less input and coerce; support path prefixes because reverse proxies mount Hermes under `/hermes`. Better: validate and preview the resolved base URL live.

### Remote auth-mode probe (probing / probe error)  `id: gapfill-desktop-settings-2-r0.gateway-auth-probe`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Remote gateway) directly under the Remote URL row. Two mutually exclusive status lines: a spinner + **"Checking how this gateway authenticates…"** (`i18n: settings.gateway.probing`, `gateway-settings.tsx:1309`) and an `AlertCircle` + **"Could not reach this gateway yet. Check the URL — the auth method will appear once it responds."** (`i18n: settings.gateway.probeError`, `:1316`).
- **What it does:** Asks the typed gateway how it authenticates so the page can show the right control — an OAuth/password sign-in button or a session-token box — instead of guessing.
- **How it works:** A 500 ms debounced effect (`:311-350`) calls `probeConnectionConfig(trimmedUrl)` (IPC `hermes:connection-config:probe`, `preload.ts:207`), which reads the gateway's public `/api/status`. A monotonic `probeSeq` drops stale results. `probeStatus` ∈ `idle | probing | done | error`. `authMode` (`:354-360`) prefers a finished probe whose `authMode !== 'unknown'`, else the saved `state.remoteAuthMode`. `authResolved` (`:375-381`) is true when the probe finished, **or** when we are idle but showing a previously-saved remote (token set or OAuth connected) — this exists so the token box does not flash for OAuth gateways during the idle/probing window. `providerLabel` (`:382-394`) is the single provider's `displayName || name`, or all of them joined with `' / '`, or the fallback **"your identity provider"** (`i18n: boot.failure.identityProvider`). `isPasswordProvider` (`:396-401`) is true only when **every** advertised provider has `supportsPassword`.
- **Inputs / options:** No controls — status text only.
- **Outputs / side effects:** One `GET /api/status` per settled URL; sets which auth control renders.
- **Config / env:** n/a
- **Edge cases / guards:** Probing only runs in `remote` mode with a syntactically plausible `http(s)` URL; a missing `probeConnectionConfig` bridge no-ops. A probe error never blocks saving — it only withholds the auth control.
- **Rebuild notes:** Public unauthenticated status endpoint advertising `auth_required` + a provider list; debounce, sequence-guard and prefer live over saved. A better version would cache probe results per origin and retry on focus.

### Remote authentication row (OAuth / username-and-password sign-in)  `id: gapfill-desktop-settings-2-r0.gateway-remote-auth-row`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → (mode = Remote gateway, `authResolved && authMode === 'oauth'`) row titled **"Authentication"** (`i18n: settings.gateway.authTitle`, `gateway-settings.tsx:1350`).
- **What it does:** Signs this desktop app into a gated remote gateway through the gateway's own login window, and shows/clears that session.
- **How it works:** Signed out → primary button labelled **"Sign in"** (`i18n: settings.gateway.signIn`) when `isPasswordProvider`, else **"Sign in with {provider}"** (`i18n: settings.gateway.signInWith`), with a `LogIn` icon; disabled while signing in, under env override, or with no URL (`:1335`). `signIn()` (`:585-637`) first `saveConnectionConfig({mode, remoteAuthMode:'oauth', remoteUrl})` — save, not apply, so the login window has a URL without flipping the live connection — then `oauthLoginConnectionConfig(trimmedUrl)` (IPC `hermes:connection-config:oauth-login`), then re-reads the config. Signed in → primary pill **"Signed in"** (`i18n: settings.gateway.signedIn`) with a `Check`, plus an outline **"Sign out"** (`i18n: settings.gateway.signOut`) calling `signOut()` (`:639-672` → `oauthLogoutConnectionConfig`). Row description, four variants (`:1341-1348`): **"This gateway uses OAuth. You are signed in; the session refreshes automatically."** (`i18n: settings.gateway.authSignedInOauth`), **"This gateway uses a username and password. You are signed in; the session refreshes automatically."** (`i18n: settings.gateway.authSignedInPassword`), **"This gateway uses a username and password. Sign in to authorize this desktop app."** (`i18n: settings.gateway.authNeedsPassword`), and **"This gateway uses OAuth. Sign in with {provider} to authorize this desktop app."** (`i18n: settings.gateway.authNeedsOauth`). A password-style gateway authenticates via `POST /auth/password-login` on its own `/login` page but rides the same sign-in window, cookie and ws-ticket machinery — only the button copy changes. Session cookies: `hermes_session_at` / `hermes_session_rt` with `__Host-` / `__Secure-` variants (`electron/connection-config.ts:36-37`).
- **Inputs / options:** Button **"Sign in"** / **"Sign in with {provider}"**; button **"Sign out"**; pill **"Signed in"**.
- **Outputs / side effects:** Persists `remoteUrl` + `remoteAuthMode: 'oauth'` before opening the window; on success toasts **"Signed in"** with **"Connected to {baseUrl}"** (`i18n: settings.gateway.connectedTo`); on sign-out toasts **"Signed out"** (`i18n: settings.gateway.signedOutTitle`) with **"Cleared the remote gateway session."** (`i18n: settings.gateway.signedOutMessage`, `:656`).
- **Config / env:** `remoteAuthMode`, `remoteOauthConnected` in `connection.json`.
- **Edge cases / guards:** Sign-in with an empty URL warns **"Remote gateway incomplete"** (`i18n: settings.gateway.incompleteTitle`) / **"Enter a remote URL first."** (`i18n: settings.gateway.enterUrlFirst`, `:589`). - **Where:** Settings → Gateways → Registered gateways → an inline bordered card that replaces the Add/Update row, opened by **"Add connection"** or a row's **"Edit"** (`connections-registry.tsx:754-957`).
- **What it does:** Creates or edits one registered gateway: its kind, display name, address and credentials.
- **How it works:** `EditorState` (`:48-66`) holds `{id, kind, label, url, authMode, token, host, keyPath, remoteProfile, headers[]}`. `editorFromConnection()` (`:68-85`) rebuilds the composite SSH host string `user@host:port` and hydrates header names with `stored: true`; `emptyEditor(kind)` (`:87-99`) starts a blank remote. The save payload deliberately sends **only** the composite host for SSH (never separate `user`/`port`), because the main-process normalizer gives explicit fields precedence and would resurrect old values (`:70-77`, `:434-437`). `save()` (`:373-481`) checks duplicates locally, builds a `DesktopRegistryConnectionInput`, and calls `bridge.save(payload)` (IPC `hermes:connections:save`).
- **Inputs / options:** **Kind buttons** (a 2-column / 4-column grid): on create all four are offered in order **"Local"** (`i18n: settings.connections.kindLocal`), **"Hermes Cloud"** (`i18n: settings.connections.kindCloud`), **"Remote gateway"** (`i18n: settings.connections.kindRemote`), **"SSH"** (`i18n: settings.connections.kindSsh`); on edit only the current kind renders and it is disabled (kind is immutable after creation). Under them, the selected kind's description: **"The Hermes runtime managed by this app."** (`kindLocalDesc`), **"A hosted instance discovered through your Hermes Cloud account."** (`kindCloudDesc`), **"A Hermes gateway reachable over HTTP(S) — LAN, Tailscale, or the internet."** (`kindRemoteDesc`), **"A Hermes install reached over SSH."** (`kindSshDesc`). When creating a Cloud entry an extra hint appears: **"Tip: signing in under Hermes Cloud above discovers your agents automatically — use this form only to register a known instance URL by hand."** (`i18n: settings.connections.cloudAddHint`, `:780`). **Name** row — title **"Name"** (`i18n: settings.connections.labelTitle`), description **"Required. Shown everywhere this instance appears; must be unique (e.g. “Homelab”, “Work laptop”)."** (`i18n: settings.connections.labelDesc`), placeholder **"Homelab"** (`i18n: settings.connections.labelPlaceholder`). **Gateway URL** row (remote/cloud only) — title **"Gateway URL"** (`i18n: settings.connections.urlTitle`), placeholder `http://homelab.lan:9119`. **Authentication** row (remote only) — title **"Authentication"** (`i18n: settings.gateway.authTitle`) with two toggle buttons, **"Session token"** (`i18n: settings.gateway.tokenTitle`) and the literal **"OAuth"**. In token mode a **"Session token"** row with placeholder **"Paste session token"** (`i18n: settings.gateway.pasteSessionToken`, `:835`), `type="password"`, and description **"The dashboard session token used for REST and WebSocket access. Leave blank to keep the saved token."** (`i18n: settings.gateway.tokenDesc`, `:840`). In OAuth mode an **"Authentication"** row with either the **"Signed in"** pill or a **"Sign in"** / **"Sign in with {provider}"** button (`signInOauth()` at `:325-370`), described by **"This gateway uses OAuth. You are signed in; the session refreshes automatically."** (`i18n: settings.gateway.authSignedInOauth`, `:864`), **"This gateway uses a username and password. You are signed in; the session refreshes automatically."** (`authSignedInPassword`), **"This gateway uses a username and password. Sign in to authorize this desktop app."** (`i18n: settings.gateway.authNeedsPassword`, `:866`) or **"This gateway uses OAuth. Sign in with {provider} to authorize this desktop app."** (`authNeedsOauth`). **SSH host** row (ssh only) — title **"SSH host"** (`i18n: settings.connections.sshHostTitle`), placeholder `user@host:22`. Footer buttons: ghost **"Cancel"** (`i18n: settings.connections.cancel`) and primary **"Save connection"** (`i18n: settings.connections.save`), which reads **"Saving…"** (`i18n: settings.connections.saving`) while in flight and is disabled with an empty name.
- **Outputs / side effects:** Writes/updates one entry in `connections.json` (token and header values encrypted at rest); the editor closes on success.
- **Config / env:** `connections.json`; `secureTokenStorage` gates the plain-text detour.
- **Edge cases / guards:** The OAuth probe (400 ms debounce, `:283-311`) only runs while the OAuth row is on screen; changing the URL or flipping the auth mode resets `oauthConnected` to false (`:317-319`) so a stale "Signed in" pill cannot survive. Signing in with no URL warns with title **"Authentication"** and body **"Enter a remote URL first."** (`i18n: settings.gateway.enterUrlFirst`). Save failures toast **"Could not save the connection"**; on a keyring-less machine with a typed token the same plain-text `ConfirmDialog` is raised instead (`:462-473`).
- **Rebuild notes:** One editor state object, kind immutable after create, secrets never round-tripped to the renderer, and a single composite host string for SSH. A better version would let the user paste a full `hermes://` invite link and fill every field.

### Extra gateway headers editor  `id: gapfill-desktop-settings-2-r0.connections-headers`
- **Surface:** Desktop app
- **Where:** Inside the connection editor for remote/cloud kinds: heading **"Extra gateway headers"** (`i18n: settings.connections.headersTitle`, `connections-registry.tsx:878`) with the note **"Sent with every HTTP and WebSocket request to this gateway — for access proxies such as Cloudflare Access (CF-Access-Client-Id / CF-Access-Client-Secret). Values are stored encrypted. Headers Hermes manages (Authorization, Cookie, Host…) are ignored."** (`i18n: settings.connections.headersDesc`), then zero or more name/value rows and an **"Add header"** button.
- **What it does:** Attaches custom request headers (typically Cloudflare Access service-token pairs) to every REST and WebSocket call this app makes to that gateway.
- **How it works:** `editor.headers` is a list of `{name, stored, value}`. Rows hydrated from `conn.headerNames` carry `stored: true` and an empty value (header *values* never cross the IPC boundary — `src/global.d.ts:883-886`). On save (`:439-452`) rows are trimmed, empty-named rows dropped, and the authoritative map is built as `name → value` when a value was typed, `null` when a stored row was left blank (meaning "keep the saved secret"), or `''` for a new row with no value; a **removed** row is simply absent from the map, which clears it server-side. The map is only sent when there is at least one entry or the list was emptied outright (`:448`).
- **Inputs / options:** Per row: a name `Input` with placeholder `CF-Access-Client-Id`, a value `Input` of `type="password"` whose placeholder is **"Saved — leave blank to keep"** (`i18n: settings.connections.headerValueSaved`) for stored rows and **"Value"** (`i18n: settings.connections.headerValuePlaceholder`) for new rows, and a ghost button **"Remove"** (`i18n: settings.connections.headerRemove`, `:911`). Below the rows, an outline button **"Add header"** (`i18n: settings.connections.headerAdd`, `:923`) appends a blank `{name:'', stored:false, value:''}` row.
- **Outputs / side effects:** Header values are stored encrypted at rest alongside the connection; they are then injected into every HTTP request and WebSocket handshake for that gateway (`electron/remote-ws-headers.ts`).
- **Config / env:** `headers` on the registry entry; `headerNames` is the only part echoed back to the renderer.
- **Edge cases / guards:** Headers Hermes itself manages (`Authorization`, `Cookie`, `Host`, …) are ignored by the main process. Duplicate names collapse in the `Object.fromEntries` map — the last row wins. Rows are keyed by array index, so removing a middle row re-renders the rest.
- **Rebuild notes:** Model the header map as authoritative-on-write with an explicit `null` = "keep", and never send stored values back to the UI. A better version would validate header names against the ignored set inline and offer a Cloudflare Access preset.

### Duplicate-connection rules and inline rejection  `id: gapfill-desktop-settings-2-r0.connections-duplicates`
- **Surface:** Desktop app
- **Where:** Inside the connection editor: a small destructive line under the fields (`connections-registry.tsx:943`), plus the muted hint **"Local is unavailable: the managed local connection already exists (there is only ever one)."** (`i18n: settings.connections.localAddHint`, `:778`) shown when adding while a local entry exists.
- **What it does:** Stops the user registering the same backend twice, and explains why the Local kind is greyed out.
- **How it works:** `findDuplicateConnection(editor, connections)` (`:138-184`) implements three rules mirrored by the main process's `normalizeConnectionInput`: (1) at most **one** `local` entry ever; (2) `remote` and `cloud` entries collide when `normalizeGatewayUrl()` (trim → strip trailing slashes → lowercase, `:102-104`) matches — cross-kind, so a cloud entry and a remote entry at the same URL collide; (3) `ssh` entries collide on `sshCompositeKey()` (`:111-131` — lowercase, split on the last `@`, default the port to `22`, yielding `user@host:port`, so `box` and `box:22` collide) **plus** an equal trimmed `remoteProfile`. `save()` runs the check *before* anything crosses the IPC boundary and sets `dupeError` (`:381-410`). The Local kind button is additionally disabled whenever `hasLocal` (`:764`).
- **Inputs / options:** No controls; the messages are: **"This app already manages a local connection — there can only be one."** (`i18n: settings.connections.duplicateLocal`, `:402`), **"A connection to this gateway URL already exists (“{label}”)."** (`i18n: settings.connections.duplicateUrl`), **"A connection to this SSH host already exists (“{label}”)."** (`i18n: settings.connections.duplicateSsh`). `dupeError` is cleared when the editor opens, when the kind changes, and on every keystroke in the URL or SSH host field.
- **Outputs / side effects:** Blocks the save; nothing is written.
- **Config / env:** n/a
- **Edge cases / guards:** The same rules are enforced main-side so a crafted IPC payload cannot slip past the UI. An empty URL or empty SSH host is never treated as a duplicate (the key is empty → `null`).
- **Rebuild notes:** Define one normalization function per kind, use it as the dedupe key in both the UI and the privileged writer, and surface the colliding entry's name. A better version would offer "merge into the existing entry" instead of a flat rejection.

### "Add connection" and "Update all instances"  `id: gapfill-desktop-settings-2-r0.connections-add-updateall`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → Registered gateways, the row shown when the editor is closed (`connections-registry.tsx:958-990`): outline button **"Add connection"** (`i18n: settings.connections.addConnection`, `Plus` icon) and, when more than one connection is registered and the bridge exposes `updateAll`, outline button **"Update all instances"** (`i18n: settings.connections.updateAll`, `RefreshCw` icon).
- **What it does:** Opens a blank editor for a new gateway; or fans `hermes update` out to every eligible registered instance at once.
- **How it works:** Add fires `triggerHaptic('selection')` then `openEditor(emptyEditor('remote'))` — new entries default to the Remote kind. `updateAll()` (`:572-593`) calls `bridge.updateAll()` (IPC `hermes:connections:update-all`, `preload.ts:194`) and walks the returned `results`, raising **one toast per connection** so a single dead box cannot hide the others.
- **Inputs / options:** Two buttons. **"Update all instances"** is disabled while running and its label becomes **"Updating all instances…"** (`i18n: settings.connections.updateAllRunning`) with a spinner.
- **Outputs / side effects:** Per-result toasts: success → title = the connection label, body = `row.detail` or **"Updates dispatched"** (`i18n: settings.connections.updateAllDone`); a `skipped` row with `reason === 'cloud-managed'` → body **"Managed by Hermes Cloud"** (`i18n: settings.connections.updateSkippedCloud`); anything else → error toast titled **"Update fan-out failed"** (`i18n: settings.connections.updateAllFailed`) carrying `row.error || row.detail || row.reason || row.label`.
- **Config / env:** n/a
- **Edge cases / guards:** The Update-all button is hidden entirely when only one connection exists or the Electron main predates the bridge. A throw from the whole call raises a single **"Update fan-out failed"** toast.
- **Rebuild notes:** Fan out concurrently, return a per-target result row, and report each independently. A better version would render a live per-target progress table instead of a toast storm.

### Launch-mode toggle ("At startup, return to Sessions on the last-used gateway")  `id: gapfill-desktop-settings-2-r0.connections-launch-mode`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → Registered gateways, below a top border: a `ToggleRow` labelled **"At startup, return to Sessions on the last-used gateway"** (`i18n: settings.connections.launchModeTitle`, `connections-registry.tsx:1002`) with description **"When off, Sessions opens on the Primary gateway."** (`i18n: settings.connections.launchModeDesc`).
- **What it does:** Chooses whether the app reopens on whichever gateway you used last, or always on the gateway marked Primary.
- **How it works:** `checked = registry.launchMode === 'last-used'`; `onChange` calls `setLaunchMode(enabled ? 'last-used' : 'primary')` (`:521-540`) → `bridge.setLaunchMode(mode)` (IPC `hermes:connections:set-launch-mode`), and the returned registry is republished. Main-side, `setConnectionLaunchMode()` (`electron/connection-registry.ts:1605-1611`) rejects anything but the two literals; the registry defaults to `'primary'` for old installs (`:1203`, `:1355`). `lastUsed` is written by the Sessions workspace on a successful open.
- **Inputs / options:** One switch, disabled while `launchModeBusy` or when the bridge lacks `setLaunchMode`.
- **Outputs / side effects:** Writes `launchMode` in `connections.json`.
- **Config / env:** `launchMode` (`'last-used' | 'primary'`), `lastUsed` in `connections.json`.
- **Edge cases / guards:** Deliberately **not** gated on `connections.length > 1` — a registry that drifted down to local-only is exactly where a user needs this control, and hiding it left hand-editing `connections.json` as the only recourse (`:993-996`). Failure toasts **"Could not save the connection"**.
- **Rebuild notes:** Store the last successfully opened source and a mode enum; validate the enum in the writer. Better: remember last-used *per window* so multi-window setups restore independently.

### "Managed updates" section  `id: gapfill-desktop-settings-2-r0.managed-updates-section`
- **Surface:** Desktop app
- **Where:** Settings → Gateways, last section: `SectionHeading` with a `Download` icon and **"Managed updates"** (`i18n: settings.managedUpdates.title`, `managed-updates-section.tsx:94`), followed by **"Update Desktop-managed SSH installs transactionally: sessions drain, the remote checkout updates, and every profile is restored with a correlated receipt."** (`i18n: settings.managedUpdates.intro`), then one row per registered SSH connection.
- **What it does:** Updates the Hermes install on each Desktop-managed SSH host as a transaction — draining sessions, updating the remote checkout, restoring every profile — and shows the resulting receipt.
- **How it works:** `ManagedUpdatesSection()` (`apps/desktop/src/app/settings/managed-updates-section.tsx:41`) reads `$connectionsRegistry` and `$managedUpdates` (nanostores) and filters the registry to `kind === 'ssh'`. Row title = the connection `label` plus a status pill; row description = `user@host` (or just `host`) via `sshTarget()` (`:29-35`), falling back to **"Desktop-managed SSH install"** (`i18n: settings.managedUpdates.sshConnection`) when the entry has no host. Pill tone comes from `stateTone()` (`:17-27`): `muted` when idle, `primary` for `updating`/`updated`, `warn` otherwise.
- **Inputs / options:** No section-level controls; each row carries the Update button described below.
- **Outputs / side effects:** None until a row's Update is pressed.
- **Config / env:** Requires `window.hermesDesktop.connections.updateManaged` (IPC `hermes:connections:update-managed`, `preload.ts:191`).
- **Edge cases / guards:** Fails closed: the section returns `null` when `managedUpdatesSupported()` is false (older Electron main without the transactional bridge — no fake button that could mutate a live serve process) or when no SSH connection is registered (`:48-51`). Remote-URL and Cloud connections are never eligible.
- **Rebuild notes:** Gate the whole surface on capability detection, key state by connection id in a store, and never render an action you cannot actually perform. A better version would stream phase-by-phase progress instead of one opaque in-flight state.

### Per-connection "Update" button and its states  `id: gapfill-desktop-settings-2-r0.managed-update-run`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → Managed updates → each row's action: a primary button **"Update"** (`i18n: settings.managedUpdates.update`, `Download` icon, `managed-updates-section.tsx:117`), replaced while running by a disabled secondary button **"Updating…"** (`i18n: settings.managedUpdates.updating`) with a spinner. While updating, the row's `below` area shows **"Draining sessions, updating the remote install, and restoring profiles…"** (`i18n: settings.managedUpdates.progress`, `:126`).
- **What it does:** Runs the transactional update for that one SSH install and reports its terminal outcome.
- **How it works:** `runManagedUpdate(connectionId)` (`apps/desktop/src/store/managed-updates.ts:95-146`) publishes an `updating` state, calls `connections.updateManaged(id)` and folds the result through `terminalState()` (`:70-90`). Status derivation: `ok` → `updated`; `outcome === 'refused'` → `refused`; `updateOk && !restoreOk` → `partial`; otherwise `failed`. An in-flight promise is memoised in a `Map` so a repeat click **joins** the running promise rather than triggering the main process's busy gate and painting a scary failure row (`:96-99`). Main-side ordering (`electron/managed-ssh-update.ts:1-15`): gate dials → drain every captured scope → detached `hermes update` → correlated terminal marker + durable receipt → restore every scope → lift the gate. Timeouts: 60 min update, 5 min clearance, 1 s poll, 15 s receipt grace (`:21-25`); exit code `75` marks an independent handoff.
- **Inputs / options:** One button per SSH row. No arguments, no confirmation dialog.
- **Outputs / side effects:** Mutates the remote install over SSH; writes a durable receipt on the remote; the row's pill and detail lines update. Pill labels by state (`statusLabel()`, `:53-72`): **"Updating…"**, **"Updated"** (`i18n: settings.managedUpdates.updated`), **"Updated — restore failed"** (`i18n: settings.managedUpdates.partial`), **"Refused"** (`i18n: settings.managedUpdates.refused`), **"Update already in progress"** (`i18n: settings.managedUpdates.alreadyRunning`) and **"Update failed"** (`i18n: settings.managedUpdates.failed`). When not updating, any `state.message` from the result is printed verbatim under the row.
- **Config / env:** n/a
- **Edge cases / guards:** The busy gate is recognised two ways — a `refused` result whose message matches `/managed[\s-]update[\s\w]*\bin[\s-]progress|managed-update-in-progress|already in progress/i` and a thrown error whose `code` is `managed-update-in-progress` (`store/managed-updates.ts:31`, `:129-131`) — and is rendered as **"Update already in progress"** rather than a failure. If the bridge is missing at click time the state goes straight to `failed`. There is no streaming progress channel, so `updating` is a single honest state.
- **Rebuild notes:** Gate → drain → update → receipt → restore → ungate, with the busy collision distinguished from a real failure and repeat clicks joined to the in-flight promise. A better version would expose phase events and allow cancelling during the drain window.

### Managed-update receipt and per-profile restore lines  `id: gapfill-desktop-settings-2-r0.managed-update-receipt`
- **Surface:** Desktop app
- **Where:** Settings → Gateways → Managed updates → the `below` block of a row once an update has finished (`managed-updates-section.tsx:122-136`): a monospace receipt line, then restored/unrestored profile lines.
- **What it does:** Proves what the update actually did — a correlation id, the outcome, the version transition and which profiles came back.
- **How it works:** `receiptLine(state)` (`:74-91`) joins with ` · `: **"Receipt {id} · {outcome}"** (`i18n: settings.managedUpdates.receipt`, using the first 8 characters of `receipt.correlationId`), then **"{preVersion} → {postVersion}"** (`i18n: settings.managedUpdates.receiptVersions`) when both are present, then `receipt.stopReason` verbatim when present. Scope lines: **"Restored profiles: {a, b, c}"** (`i18n: settings.managedUpdates.scopesRestored`) for every scope with `restored === true`, and one line per unrestored scope reading **"Profile “{profile}” not restored: {error}"** (`i18n: settings.managedUpdates.scopeNotRestored`), falling back to **"Update failed"** when the scope carries no error. Receipt shape (`electron/managed-ssh-update.ts:29-39`): `{correlationId, outcome, startedAt, finishedAt, preSha, postSha, preVersion, postVersion, stopReason}`; correlation ids are validated against a UUID regex (`:25`). Outcomes: `updated`, `update-failed`, `restore-failed`, `update-and-restore-failed`, `refused` (`:27`).
- **Inputs / options:** None — read-only output.
- **Outputs / side effects:** Display only; the durable receipt lives on the remote host.
- **Config / env:** n/a
- **Edge cases / guards:** Nothing renders when `state.receipt` is null. Restored/unrestored lines are suppressed while the update is still running. The block only mounts at all when there is something to show (`updating || message || receipt || scopes.length > 0`).
- **Rebuild notes:** Emit a correlated, durable receipt on the remote and echo a truncated id back so support can match logs; list per-profile restore results individually. A better version would link the receipt id to the remote log file and offer a one-click re-restore of a failed profile.

## Existing boundary and required choice

The queue persists a canonical **unsigned** smart DENY while leaving the terminal task `BLOCKED` (`queue.py:2949-3083`). Its ordinary decision card still has `accept/edit/reject/defer` (`inbox.py:74-126`), and generic `apply_decision(accept)` would promote that row to `APPROVED` with only unsigned `human_decision` metadata (`worker.py:1918-2020`, `queue.py:1931-2003`). This is not a once-only continuation. The pinned Hermes gate instead records the DENY, offers an interactive owner **once/deny** choice, permits no session/permanent persistence, and refuses unattended/timeout/cancelled requests (`tools/approval.py:756-925` in pinned `59b2aeef6c7a`).

Decision for this slice: retain the DENY row and its denial event. Only a new, server-created offer for that exact DENY can become a one-use owner permit. Do **not** reinterpret `accept`, `edit`, `session`, or `always` as once, and do not reuse the unsigned `human_decision` or smart-APPROVE receipt as authority. A true owner-once grant is eligible only while the original authenticated tool turn is live; otherwise the old DENY remains a refusal and a later request needs a new operation/review. A Telegram callback lane unable to answer while that turn is held must be fixed or explicitly reported unavailable; extending the lease past turn closure is not a fallback.

## Durable shape and nonserialized capability

Add `task_owner_once` (one row per task, FK/cascade and terminal-row retention cleanup): `task_id` PK; `task_birth`; `denial_snapshot_sha256`; `denial_annotation_sha256`; `origin_turn_id`, `session_id`, `session_instance`, `principal_key`, `intent_sha256`; `offer_nonce_sha256`; `deadline_at` UTC; `state` in `offered/accepted/claimed/dispatching/revoked`; nullable `owner_decision_id`, `owner_channel`, `owner_turn_id`, `owner_principal_key`, `approved_execution_sha256`, `approval_receipt`, `signature`, `mediation_execution_id`, `claimed_at`, `dispatch_at`. The queue must reject `hold` at offer/accept as well as claim; `off` requires the detached signer and a genuinely unmediated task. Bound the offer to the earlier of the task approval deadline and a fixed 120-second owner window; an absent task deadline does not make an unbounded offer. Store only a SHA-256 of a fresh 128-bit offer nonce. Its raw nonce appears only in the owner callback/POST, never in task payload, task JSON, model response, or a reusable preference.

`OwnerDecisionContext` is a trusted route-minted object containing the verified owner sender/session and matching originating principal; it is never accepted from request JSON. `OwnerOnceClaim` is an in-process, nonserializable capability holding the raw nonce, original `ApprovalTurnContext` identity/lifetime, and authenticated owner-choice identity. It is issued only by the server owner-choice handler after the CAS below. It cannot be reconstructed after restart, copied from task fields, or supplied by a ToolRPC payload. A lost process therefore leaves `accepted` or `claimed` rows inert; housekeeping revokes them. The decision UI exposes only `once`/`deny` and a redacted exact command/target. Generic card rendering must not show `accept/edit` for a current exact smart DENY. No offer is generated for ESCALATE, static hardline/owner-policy DENY, stale/malformed annotation, task without ready authenticated chat association, an origin without a proven bidirectional owner reply transport, or already closed turn. An authenticated web admin endpoint alone is not proof of a reply path.

The signed owner approval receipt has a distinct purpose, e.g. `nerva.owner-once-terminal-approval`, schema 1. Canonical bytes bind task ID/birth, DENY snapshot and annotation digests, exact `chat_approval_tasks` intent and origin tuple, offer nonce hash/deadline, owner decision ID/channel/turn/principal, target+command digest, kernel intake digest, the optional exact B7 receipt/policy revision (absent together in `off`), and the *post-decision* `APPROVED` execution fingerprint. It carries no scope or wildcard. `decision='owner-once'`, `decided_by='owner_once'` segregate this path from generic human `accept/edit`; `human_decision` may be written for audit but is never proof. The original unsigned DENY stays in `task_smart_approvals`. A one-use human acceptance does not erase that denial event or silently reset its breaker tally; existing generic human reset behavior is unchanged.

## Exact queue API and CAS points

1. `offer_owner_once(task_id, snapshot_sha256, *, turn, live_check) -> OwnerOnceOffer | None`: `BEGIN IMMEDIATE`; require exact `BLOCKED` pending policy/needs-approval task, `_smart_terminal_args`, valid current canonical unsigned DENY (reuse `_unsigned_smart_hold_verdict`), matching `approval_snapshot_digest`, valid mediation and ready `chat_approval_tasks` birth/intent/origin. Require `turn is current_approval_turn()`, `turn.live()`, and exact association session/instance/principal/turn. `live_check` is trusted config-only: same opted-in judge route/policy revision and `smart_current(DENY,snapshot)`, command floor. Insert one offer only. Duplicates return no new offer or notification (the raw nonce is not recoverable from its stored hash); changed snapshot/birth/turn revokes old offer and requires a fresh review. Never call a queue-reading callback while holding the queue transaction.
2. `decide_owner_once(task_id, nonce, choice, *, authenticated_owner, live_check) -> OwnerOnceClaim | None`: server verifies `choice` is exactly `once` or `deny`; ingress proves owner **at decision time** (a proven bidirectional owner channel, presently coordinator `_callback_is_owner` with fresh Telegram destination/allowlist settings; `admin_guard`, `Principal.admin`, or card possession alone is insufficient). `BEGIN IMMEDIATE`; require offered row, correct nonce hash, deadline, original live turn and session instance, current exact task/association/snapshot/DENY/mediation, fresh config/policy check, and no pending edit. `deny` CAS revokes offer and rejects task; `once` atomically signs receipt, sets `accepted`, and promotes `BLOCKED -> APPROVED` with `owner-once` markers. No preference/pattern/session persistence. Two owners or duplicate taps yield at most one accepted receipt.
3. `claim_owner_once(task_id, claim, *, execution_id, live_check) -> Task | None`: **one `BEGIN IMMEDIATE` transaction**. Require mode `off` or `enforce`, exact claim object + nonce, accepted receipt signature and every bound field, live originating turn/session/owner context, deadline/config/command floor, no halt. CAS `accepted -> claimed` and `APPROVED -> RUNNING` once. In `enforce`, compose this with the existing validated B7 claim and governed event atomically; in `off`, require no B7 provenance and use a direct expected-status CAS with the private owner claim. `hold` refuses. Generic `runnable`/scheduler `claim_mediated` must skip/return None for `owner-once` rows without the claim; a named tick must receive the trusted claim through a private worker entrypoint. Do not weaken ordinary `tick` or generic manual approvals. Retry is forbidden: any failure after claim ends this one operation, never `RUNNING -> APPROVED` for a second attempt.
4. `owner_once_dispatch_current(task_id, claim, actual_request, actual_action, *, live_check) -> bool` re-reads durable `RUNNING` row and signed receipt, claim/execution ID, live turn/owner identity, deadline, fresh config, exact ToolRPC request/target, and kernel action binding. It is used in `_approved_execution_context`, `_durable_terminal_approval`, kernel `approval_check(Action)`, and the final physical-send guard. The physical-send gate performs `claimed -> dispatching` once, with the actual request digest, before the backend's spawn/send; a second dispatch is refused. Cancellation/turn close/expiry/settings change revoke any **unclaimed or undispatched** offer/permit synchronously and fail all subsequent gates. A transport held before egress must recheck at its actual spawn/send boundary; checking only in `GovernedTargetRunner` before `await transport.run` leaves a cancellation window. Once physical dispatch has begun, cancellation must cancel the in-flight transport; it cannot retroactively claim no execution. This is the linearization limit to document and test.
5. `verify_owner_once_terminal_approval(task_id, actual_action=None)` verifies the accepted/claimed signed receipt and current binding (no smart-APPROVE receipt). `issue_owner_once_terminal_result(task, result)` and `verify_owner_once_terminal_result(task_id)` use a **separate purpose/key namespace** (e.g. `nerva.owner-once-terminal-execution`) and `_owner_once_execution` key in `task.result`. Worker issues proof only after the real handler returns outer `status=='ok'` and nested `result.ok is True`, before `DONE`; proof binds task ID/birth, exact `RUNNING` fingerprint, optional B7 execution ID (absent in `off`), kernel intake digest, owner approval receipt digest, exact result-body hash, fresh nonce and signer. Verifier requires durable `DONE`, exact proof shape/signature/receipt/result, and one `dispatching` record. Synthetic `APPROVED->RUNNING->DONE`, tampered result, copied proof, or smart `_smart_execution` cannot report success. Model-facing reply copies only the nested result, never proof/nonce.

All methods fail closed on malformed rows, unavailable signer/store, missing exact association, failed callbacks, timeouts and exceptions. `transition_with_group`/`update_payload_policy_with_group` should reject `accept/edit` on an intact current smart DENY when they would bypass this path; `reject`/`defer` may remain generic but must revoke any outstanding offer. Edits create a new snapshot and require a new guardian review. Expiry, quarantine, mediation-mode change, owner-setting revocation, task deletion and turn closure revoke the permit. Retention purges orphan offer rows. This guard must also live in the queue, not just router/UI, because `worker.apply_decision` has other callers.

## Worker/kernel/target integration and policy floors

Add `worker.resume_owner_once(claim)` (or private equivalent) that uses the existing `tick` execution body after `claim_owner_once`, with one attempt and no retry. Ordinary scheduler ticks neither receive a claim nor execute `owner-once` approved rows. Existing `_ExecutionPermit` and `validate_mediated_execution` remain mandatory in `enforce`. In `off`, `worker.execution_allowed` currently returns True immediately; add an owner-once branch *before* that return that consumes the private claim and verifies the exact durable RUNNING receipt. This does not change ordinary off-mode execution. Coordinator classifies `owner-once` as a **strict terminal** marker, distinct from smart machine approval but routed through the same action-bound kernel aperture; no downgrade to legacy manual Docker if the owner receipt is revoked. `GovernedTargetRunner` must supply `approval_check(Action)` only when it verifies the actual action against the owner-once receipt and current request. Kernel `authorize` itself stays unchanged: e-stop/capability/budget/loop DENY first; only ordinary terminal.exec ASK in effective `auto` may become GRANT; taint after policy still QUEUE (`kernel/__init__.py:146-250`). Keep hardline, trusted owner command deny, target policy, backend flags, local/SSH path/argv checks and Docker active-backend check. Current target runner has a final request check before local/SSH/Docker transport (`environments/execution.py:169-230,305-417`); add the physical-send gate at the transport boundary or a narrower non-awaiting guarded spawn. No new `approved_task_id`-only authority.

The interactive response should await the owner decision and named worker completion only while the originating turn is live and within the bounded deadline, mirroring `terminal_review.py:21-125`. Silence, callback failure, cancellation or stale offer returns a definitive DENY/held answer with no execution. The generic approval inbox remains available for ordinary tasks and ESCALATE. The only outstanding UX dependency is whether Telegram callbacks can be processed while the same chat lane is awaiting this choice; if not, this path must fail closed rather than queue delayed execution, or the callback must be delivered on an independent lane with the same owner checks.

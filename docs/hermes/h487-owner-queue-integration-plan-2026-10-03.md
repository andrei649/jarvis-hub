## Proposed localized interfaces

1. `TaskQueue.pending_consent_offer(task_id) -> ConsentOffer | None` returns an internal immutable offer only when `_read_current_locked` succeeds, category classification is nonempty and catalog-valid, the source producer's registration key is still live, and trusted current policy/target scope equal the source-bound values. Include `task_id`, birth, approval snapshot, optional group id/snapshot and exact member ids, category keys/permanence, context identity, deadline and an opaque offer revision. A public projection may expose only reviewed category descriptions/choice availability and exact group count; never signer material, registrar key, chat principal key, raw source, or receipt. If the current policy/target/registration verifier is unavailable, omit reusable choices and preserve the ordinary once path.
2. `TaskQueue.decide_reusable_consent(offer, *, choice: Literal['session','always','deny'], actor: AuthenticatedOwnerDecision, reason=None, live_check) -> ConsentDecisionResult | None` is the sole mutation API. The transport/coordinator creates `AuthenticatedOwnerDecision` after `admin_guard` or a fresh Telegram destination+sender check; do not accept `decided_by` or principal from JSON/model payload. The queue rechecks actor and `live_check` just before mutation, under its lock and one `BEGIN IMMEDIATE`. It rereads the leader and every candidate from stored group membership (never trusts submitted member IDs), verifies group snapshot, per-task birth/snapshot/deadline/association/signed source, exact request/policy/registration/category/target/context equality and each independent B7 receipt/head. Cap the batch at 64. Mixed or changed members fail the whole reusable choice; ordinary individual once stays available. Do not run arbitrary external awaits while holding the transaction.
3. Construct one `ConsentContext` from trusted source/current registration and owner principal: surface, session id/instance, stable registration key, current policy revision and canonical target scope (`consent_ledger.py:30-44,76-81`). The source must carry or deterministically bind the server-resolved target identity/config digest and category result; its current `producer`/`policy` fields alone do not prove those. For terminal, derive from stored command and current reviewed classifier with explicit trusted home/lifecycle inputs, then compare to the enqueue-captured category/target evidence. Do not infer a broad target from the model's `target` string. Reject empty/unknown/malformed categories and changed registration, policy, target or origin. `always` for nonpermanent categories is session-scoped by the ledger (`:274-285`).
4. For `session`/`always`, call the production `ConsentLedger` using the queue's *same SQLite connection*, trusted category catalog and a separate required `make_consent_head_anchor()` file; use one decision id tied to the actual authenticated owner action. `grant()` already uses a savepoint and leaves the outer transaction to the caller (`consent_ledger.py:286-313`). On success, CAS each exact still-BLOCKED member to APPROVED and write an explicit per-task human decision record linked to the one owner choice; withdraw each group membership and record promotion effects only for members remaining pending. The member receipts/events stay untouched and individual. If grant, row CAS, signer, anchored CAS or commit fails, no member is approved; an external-head advance followed by SQLite rollback makes the ledger unavailable and requires operator recovery, never silent re-adoption (`h487-consent-revocation-plan-2026-10-03.md:28-39`). For `deny`, do not grant; reject exact matching members in the same queue transaction with bounded normalized reason and true owner attribution. Once continues through existing `worker.apply_decision`/`transition_with_group` for ordinary asks and only decides one task, causing normal follower promotion. Smart DENY continues its separate `aut1` once/deny contract.
5. Future requests with matching category consent need a *separate* queue admission path, e.g. `TaskQueue.approve_with_current_consent(task_id, current: TrustedConsentEvidence)`, where a newly created request still receives its own B7 enqueue receipt and current kernel/policy/target classification. Extend the ledger with an internal `current_witness(context, categories) -> {category_key: decision_id} | None` that performs the current signed and anchored lookup and returns the exact active decision ID covering each category. Do not key task validity to the entire external head revision: an unrelated grant should not invalidate it. Under queue lock, the admission reads the current anchored witness and fresh task/source snapshot, then moves only that row to APPROVED with `decision='auto-consent-session'|'auto-consent-always'`, `decided_by='consent'`, `human_decision=NULL`, and a private signed task-specific proof binding task birth, pre-claim execution fingerprint, context, categories and category→decision IDs. It must not invoke `_human_decision_record`, reset a human-denial breaker as if clicked, or record an owner acceptance preference. The original human choice remains in the ledger; this later task was machine-admitted under that choice. A missing/mismatched/revoked witness holds an ordinary ask. Regrant after revoke has new decision IDs and cannot revive an older staged task. No auto path for Smart DENY.
6. At claim and actual physical egress, verify the signed task proof against the appropriate task phase and re-resolve the *same* category→decision IDs against the CURRENT anchored ledger, plus registration/policy/target/category and e-stop/kernel/hardline/taint/budget floors. `TaskQueue.execution_fingerprint` includes `mediation_execution_id` (`queue.py:1017-1055`), which changes at claim; the proof therefore needs explicit pre-claim and claimed binding, or a separate immutable-intent digest plus a claim record bound to the resulting execution ID. Never compare one pre-claim fingerprint unchanged after claim. `worker.py:1606-1725` claims each mediated task with its own `claim_mediated`/execution permit; `queue.py:1772-1862` validates the exact receipt/event at dispatch. The terminal runner already rechecks exact request and target policy at `environments/execution.py:173-202,316-361` and has local/SSH/Docker send seams. Add the narrow consent check there, beside the existing request/target checks, so revocation or policy/target change before effect refuses. No receipt, grant, task id, or approval marker alone bypasses the kernel or transport gates.

## Coordinator dispatch constraints after source inspection

The next implementation must form a connected terminal vertical path (real
producer -> authenticated owner choice -> same-transaction grant/followers ->
later category reuse -> private worker claim -> current physical dispatch), not
another standalone storage milestone. Other accepted producers/channels remain
required afterward; no H487 equivalent verdict from a terminal-only result.

`TaskQueue._chat_intent_locked` excludes mutable human/decision and execution-id
fields but binds original tool intent, receipt, kernel intake and edit revision.
Use that existing association as an independent check; do not reconstruct an
original task by trusting a caller-provided snapshot. Signed future task proofs
need a distinct purpose and source hash plus current category-to-decision IDs.
The entire external head may advance for unrelated grants while those IDs remain
valid. A new grant with new IDs cannot resurrect a task staged under a revoked
decision. The ledger witness must distinguish session and always grants as well
as category identity without trusting unsigned rows.

Real owner session/always decisions also require a distinct durable consent
marker/proof. They must not fall back to ordinary human accept if their private
proof is missing or corrupt. Their actual human metadata must preserve the real
click and chosen scope; future reuse has no human decision. Generic transitions
and ordinary mediated claim must refuse consent-specific authority markers; the
consent-aware queue claim revalidates current grant, source and independent B7
evidence. Worker execution_guard must enforce this even with mediation off, as
the owner-once path already does. Enforce retains its own consumed B7 permit.

The current local, SSH and Docker subprocess seams already call the separate
owner-once physical gate. Add an adjacent consent scope/gate or carefully typed
shared implementation preserving owner-once semantics. It must bind the original
async task, exact transport instance/backend/argv/cwd/timeout/target, one-use
dispatch nonce and the worker claim, then revalidate current anchored grant and
registration/policy/target/kernel/e-stop/taint/hardline floors synchronously at
that seam. A descendant context, changed transport or missing proof is a refusal,
never ordinary transport fallback. Preserve owner-once single-use completion
proof and Smart DENY once/reject without introducing a reusable DENY override.

Terminal target evidence must include a canonical target configuration digest
and transport-relevant configured identity, not merely a model-chosen name.
Derive bounded nonsecret inputs without starting or authenticating a transport.

for passive consent metadata. Homes/lifecycle detector inputs are trusted and
explicit. Missing declared target/configuration retains the ordinary ask.

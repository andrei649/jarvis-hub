# OpenRouter, Krea, xAI and DeepInfra images

These providers use the existing Images panel, `image_generate`, and `/api/media/generate`. Selecting cloud generation creates an immutable Decision Inbox task. No generation call occurs before an owner approves it. No provider is enabled by this implementation.

OpenRouter offers the pinned Hermes catalog of twelve image models. Chat image models use the chat surface; the ten dedicated models use the [current Images API](https://openrouter.ai/docs/guides/overview/multimodal/image-generation). Selection stays explicit: a timeout, unavailable model or lost catalog never selects a second provider or sends another POST. Generated artifact IDs can be supplied as model-bounded references; their actual bytes and hashes are bound to approval.

Krea offers `krea-2-medium`, `krea-2-large`, and `krea-2-medium-turbo`. The panel supports text generation and style-guided generation with explicit HTTPS style URLs and `raw`, `low`, `medium` or `high` creativity. This is style guidance, not generic image editing. URL strings use strength 0.6; the API/tool also accepts exact `{url, strength}` objects with strength from -2 to 2. At most ten unique references are accepted. They are serialized canonically inside the signed task to preserve the queue's nesting limit, and displayed in the approval card.

An owner can configure independent `OPENROUTER_API_KEY` or `KREA_API_KEY` sources and enable the corresponding `cloud-image-openrouter` or `cloud-image-krea` manifest through the existing PermissionGate. Status checks use local configuration only, report reachability as unprobed, and do not read disabled-provider credentials. Image generation may consume provider credit after approval; this workflow does not change chat subscription routing.

The manifests admit `openrouter.ai`, and Krea's `api.krea.ai` plus `gen.krea.ai`, respectively. The latter result origin is documented in the [official Krea API reference](https://www.krea.ai/docs/api-reference/image-enhance/krea-enhance). A provider result URL is an untrusted candidate. Its host must be explicitly admitted by the live PermissionGate or an existing owner domain registration; public DNS is pinned, redirects are refused, and the result GET carries no API credential. No further CDN allowlist is inferred from responses, donor fixtures or marketing assets.

Krea submits once and writes the returned job ID durably before the first GET. Polling uses the same API origin and credential, with bounded donor backoff and retries only for transient GET errors. Configuration, approval and emergency-stop checks run around waits and requests. Failed or interrupted polling retains the job ID and never repeats the generation POST. The Images panel offers **Continue saved Krea job** only when local records prove an interrupted, inactive job. This creates a fresh GET approval, bound to the original prompt, model, job and human execution identity. API/tool callers use `cloud=true, backend=krea, prompt="", resume_task_id=<original task ID>` without new generation options. One portable source lock prevents concurrent execution; approved continuations share the original completion, artifact and gallery row. A blocked, rejected or unexecuted continuation cannot inherit a ready result. Legacy jobs without the private execution proof remain non-resumable; there is no automatic migration or replay.

After a completed Krea generation, **Propose Enhance 2×** creates a separate paid POST proposal. API/tool callers use only `cloud=true, backend=krea, prompt="", enhance_task_id=<original task ID>`. The runtime retains the original provider URL privately and binds it, the original artifact hash, prompt, model and actual human execution identity into the new approval. Source URLs are limited to 1024 characters; current source host admission and authority are rechecked before requests and publication. The native POST contains only the source URL, factor 2 and original prompt. An interrupted Enhance job uses the existing fresh GET continuation and does not resubmit. Failures preserve the original artifact and gallery row; a successful pass creates a distinct result. Enhance may change fine detail. The panel keeps the original preview through the new task's pending/result states in the current session; a reload opens the selected task alone. Historical completions without a saved result URL are not automatically migrated, expired remote URLs may fail, and Enhance output cannot be used as a nested Enhance source.

xAI offers `grok-imagine-image`, `grok-imagine-image-2.0` and `grok-imagine-image-quality` through a separate default-off `cloud-image-xai` manifest and `XAI_API_KEY`. Generation uses the native image endpoint; editing accepts local generated artifact IDs and binds their exact bytes. The 2.0 model supports at most five references and optional `auto`, `low` or `medium` quality; the other models accept at most three references. Generation accepts `1k` or `2k` resolution, while edits reject a resolution knob. The manifest admits `api.x.ai` and the result host `imgen.x.ai` documented in the [official REST reference](https://docs.x.ai/developers/rest-api-reference/inference/images). Result downloads remain credential-free, DNS-pinned and redirect-free. This host evidence is not a live billing or service-availability test.

DeepInfra preserves Hermes' dynamic model discovery. No fixed catalog is guessed. A default-off `cloud-image-deepinfra` manifest and independent `DEEPINFRA_API_KEY` allow **Refresh model catalog** to queue an explicit GET approval. API/tool callers use `cloud=true, backend=deepinfra, prompt="", refresh_catalog=true`. Only `image-gen` tagged rows from the fixed models endpoint are retained, with bounds of 512 rows and 512 KiB. The private cache binds the task, execution identity, result digest and credential generation. Status reads the local cache without dialing; an absent, changed or untrusted cache makes generation unavailable. Each generation binds the exact cached catalog digest and selected model, rechecked before dispatch. DeepInfra currently supports text-to-image with one result; no edit/reference support is inferred. Catalog tasks have no image-watch link. Undocumented result CDN hosts still require owner admission.

Only a decoded static raster, stripped of provider metadata and saved as a bounded local PNG, is reported ready. Normal generation, uploads and edit references retain the 16 MiB/2048-pixel limit. Krea Enhance alone accepts up to 4096 pixels per dimension, still at most 16 MiB. Its authenticated download, gallery and export require a private completion proof bound to the exact pixels; an unrelated 4K file does not gain admission. Artifact dimensions come from validated pixels; the size selector supplies an aspect preference for these providers. Explicit OpenRouter 4K requests remain refused before enqueue. Supported dedicated knobs include model-bounded exact aspect ratio, resolution up to 2K, quality, background, output compression, seed, and `n=1`. Unsupported knobs refuse rather than disappear.

Local injected-HTTP evidence covers the authenticated route, registered tool, real signed queue, composed worker, PNG and catalog. It is not evidence of live provider or billing acceptance. No remote call or provider activation was performed.

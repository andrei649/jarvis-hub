## The deadlock and the available surface

The Telegram poll loop flushes held turns, then sends **every** callback into `_in_chat(chat, ...)` (`agents/core/channels/telegram.py:581-587`). `ChatLanes.submit` waits for the previous task in that chat to finish (`agents/core/channels/chat_lanes.py:36-57`). The owner’s `_run_turn` occupies that same lane while its ToolRPC `review_terminal_task` waits (`telegram.py:833-866`; `agents/core/autonomy/terminal_review.py:56-82`). A generic owner tap cannot run until that turn ends, so adding a waiter alone deadlocks until timeout. H117 guest bursts and H487 reason replies depend on ordinary lane ordering (`telegram.py:611-642,819-850`); do not bypass them.

Today `AutonomyCoordinator.wire` installs a generic notifier and `on_callback` only when a Telegram channel and destination exist (`agents/core/autonomy_coordinator.py:191-225`). The generic card uses `aut:<task_id>:<accept|edit|reject|defer>` (`agents/core/autonomy/inbox.py:20-28,113-138`). `_on_callback` already obtains trusted `chat_id`/`user_id` from the channel and checks current owner identity before applying a decision (`autonomy_coordinator.py:260-292,418-445`). Its new owner read is a single read-only SQLite snapshot with `timeout=0` and fail-closed error behavior (`agents/core/settings_db.py:701-718`; `agents/core/orchestrator.py:1368-1378`); destination remains env-first through `_owner_chat_id` (`agents/core/channels/outbound.py:60-76`). The callback acknowledgment now says OK only when the coordinator returned a nonempty success string (`telegram.py:911-931`). Preserve those contracts.

## Minimal new server-owned interfaces

1. **Source capability:** Telegram `_run_turn` may bind an internal, short-lived `TelegramReplySource(channel identity, channel generation, chat_id, sender_id, running-turn lifetime)` alongside its existing `_RUNNING_TURN` scope (`telegram.py:852-866`). It is not a tool argument, message text, stored task field or mutable `Principal.admin` flag. The coordinator offers `owner_once_reply_capability()` only while that source is live, `current_approval_turn()` is the same live session-instance/turn (`agents/core/approval_outcomes.py:32-97`), the channel is the currently registered channel with the exact callback hook, `_running` and `_poll_task` are live, and a **fresh** destination+sender check succeeds. Recheck after awaited delivery and immediately before decision CAS. If a copied context outlives `_run_turn`, a restart changes generation, the registered hook changes, or owner storage is locked/unreadable, capability is absent/revoked. This proves an answerable registered reply path, not that the person has read the prompt; only an authenticated callback is consent. A Telegram guest’s ordinary chat remains admitted with `allowed_users=[]`, but never gains this capability.
2. **Separate callback namespace:** reserve `aut1:<32-lowercase-hex-nonce>:<a|r>` (39 ASCII bytes, under Telegram’s 64-byte `callback_data` limit). `a` means approve this task once, `r` reject; no edit/defer/session/always alias, and the old `aut:<id>:action` parser and card remain byte-compatible. The nonce indexes a bounded server-owned active prompt for one `(task_id, task_birth, snapshot_digest, turn/session instance, channel generation, destination, owner sender, deadline)`, not permission by possession. Require the delivered Telegram `message_id` and the callback’s `message.chat.id` plus `message.message_id` to match as well. The final queue transaction independently rechecks the exact prompt, current task/mediation/revision, nonce, deadline, authentic sender and **fresh** owner setting; a syntactically valid callback alone never authorizes. A duplicate or stale tap gets neutral refusal, not `OK`.
3. **Dedicated once-card send:** coordinator uses the existing channel instance but a distinct `send_owner_once_card` returning `(chat_id, message_id)` only for HTTP success **and** a Telegram JSON `ok: true` with positive integer `result.message_id`; `send_card` currently checks only HTTP status and returns `bool` (`telegram.py:482-491`), and `_message_id_of` alone does not check `ok` (`:217-225`). Build the card from the stored exact task, with bounded redacted command/target summary and explicit guardian DENY, two buttons only. The notifier must be bound to the same channel generation and registered callback, and the channel’s poll loop must still be live after the send. Record the message ID into the prompt’s exact delivery CAS before beginning the owner wait. A callback racing that CAS may be refused and retried; it must never be buffered as authority. Failed/malformed send, unavailable poller or registration change means no live channel and terminal DENY refusal, not an unanswered pending approval. The `answerCallbackQuery` result is cosmetic and never proof of the owner decision.

## Lane bypass, boundedness and ordering

In `TelegramChannel._handle_update`, classify only the reserved `aut1` shape **and** an already registered live nonce before the ordinary callback branch. Ask a side-effect-free coordinator predicate for fresh owner sender/destination and current channel-generation binding; a guest, stale nonce, malformed payload or old generic `aut:` tap follows the existing `_flush_all_turns` + `_in_chat` path. For an eligible once reply, flush held batches as today, then dispatch the exact callback outside `ChatLanes` in a separately tracked, bounded task (one in-flight task per nonce; global bound no larger than the existing 32 pending reviews). Do not await its Telegram acknowledgment in the poll loop; HTTP or SQLite delay must not freeze updates for other chats. The coordinator’s dedicated `on_owner_once_callback(nonce, choice, chat_id, user_id, message_id)` re-authenticates and invokes the exact queue CAS, then wakes the waiter **after commit**. The ordinary `_handle_callback` remains unchanged for generic cards, as do H117 text/guest batching and H487 reason-reply stamping/lane ordering. The intentional exception is that the exact owner-once decision may overtake an earlier still-running message in its own chat to release that message’s wait; no other input can do so. If the side-effect-free predicate cannot finish immediately (including an owner-store lock), fail closed to the ordinary path rather than blocking the poll loop.

Fast-path tasks are tied to channel generation. `stop()` must mark the channel inactive and revoke pending prompts before cancelling/draining these tasks, then bound their cleanup alongside the existing lane drain (`telegram.py:325-351,530-575`). The callback CAS checks live generation again; a callback already committed before stop is a real owner decision and follows the earlier design’s accept/cancel race boundary. After the parent turn ends or is cancelled, its source lifetime closes, prompt is revoked/settled, and a late callback has no executable effect. Avoid an unbounded nonce map or delivery-task registry; the queue’s pending deadline and channel shutdown own cleanup.

## Avoid duplicate generic DENY cards

`AutonomyWorker.govern_enqueue` schedules `_maybe_push` before the guardian attempt finishes (`agents/core/autonomy/worker.py:1170-1210`). `_maybe_push` joins the same review, then could race the ToolRPC continuation and send a generic four-choice card (`:1326-1406`), while `review_terminal_task` currently returns DENY immediately (`terminal_review.py:62-82`). A UI-only suppression after send is too late. Add a shared exact DENY disposition/reservation at the queue/worker seam: after the bounded review, `_maybe_push` re-reads the canonical current smart DENY and skips generic delivery **before** delivery-broker dispatch, budget charge and `mark_pushed` if the owner-once path owns it. For no live capability, delivery failure, changed turn, registration or timeout, settle that exact still-BLOCKED DENY to definitive refusal rather than releasing a late generic accept card. At the broker’s actual dispatch callback, recheck prompt/reservation and task revision again; neither a background notifier nor grouped promotion may send a stale generic card. ESCALATE, judge failure and ordinary human asks keep their existing generic card flow. This cross-worker disposition contract is a dependency for same-turn transport work; merely adding a fast callback without it leaves contradictory owner controls.

## Web decision

The current web chat is HTTP `POST /chat` or streamed `/chat/stream` SSE (`agents/web.py:1215-1272,1280-1350`); `_web_principal` calls an admin credential or local fresh-box client an admin (`:1200-1212`). The HUD Decision Inbox sends a **separate** admin `POST /autonomy/tasks/{id}/decision` (`agents/core/routers/autonomy.py:277-291`; `frontend/src/gap.tsx:3172,3255`). There are no WebSocket routes (`agents/web.py:798-799`) and no current server push/ack for an exact guardian DENY card tied to the still-open chat invocation. Thus web has durable manual task decisions, but **no proven context-bound bidirectional owner reply capability** for this slice. An authenticated web request, admin token, open HUD tab, SSE model-token stream or background polling is not human presence. Treat current web, cron and other unattended origins as no-channel immediate DENY. A future web adapter could use an authenticated live chat SSE prompt plus a nonce-bound response POST and disconnect-bound registration, but that is new transport work with its own tests, not an inference from the existing admin route.

3. `sendMessage` HTTP 200 with `ok:false`, missing/bool/zero `message_id`, failure/timeout, stopped poller, stale notifier or re-registration: no waiting prompt and no execution. A valid message receipt starts the finite wait; `answerCallbackQuery` failure changes no decision. No provider/network outside `httpx.MockTransport`.
4. Give the ordinary notifier and the same-turn continuation a guardian DENY simultaneously. Exactly one once-card is sent and no generic four-choice card, duplicate budget charge or `mark_pushed`; no-channel DENY becomes definitive refusal. ESCALATE still sends one ordinary card. Cancellation, expiry and owner reject revoke the nonce; a late callback cannot reopen it. Shut down while the callback task is in flight and show bounded cleanup with no post-stop approval.

The precise shared queue decision/receipt and signed worker completion are outside this transport note and remain coordinator-owned. A fast callback is an input path only; no amount of Telegram delivery metadata substitutes for durable owner decision and actual worker result.
